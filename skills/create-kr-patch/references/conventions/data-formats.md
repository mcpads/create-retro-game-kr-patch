# 분석·빌드 데이터 시행 규약

텍스트 추출·재삽입·폰트 빌드 사이에서 교환하는 기계 판독 데이터의 기본 구현 규약이다. 전략 문서는 보존해야 할 의미와 통과 조건을 소유하고, 이 문서는 그 의미를 파일 형식·필드·카탈로그로 표현하는 기본 프로필을 소유한다. 프로젝트에 이미 동등한 형식이 있으면 유지해도 되며, 아래 파일 형식과 필드명 자체는 불변식이 아니다. 텍스트 맵·PoC·HITL·QA처럼 사람이 판정을 추적하는 기록의 배치와 필드는 `references/conventions/project-records.md`가 소유한다.

## 목차

1. 공통 규칙
2. 문자 매핑 테이블
3. 제어코드 사양
4. 포인터 카탈로그
5. 재삽입 정책 데이터
6. 폰트 렌더 프로파일
7. 검증 바인딩

## 1. 공통 규칙

- 같은 산출물을 여러 형식으로 중복 소유하지 않는다. 사람이 보는 표와 도구 입력이 모두 필요하면 한쪽에서 다른 쪽을 생성한다.
- 원본 좌표·원본 바이트·포인터 원시값처럼 재현에 필요한 값은 보호 데이터로 취급한다. 번역문이나 표현 파라미터와 섞어 수작업으로 고치지 않는다.
- 구조화 데이터는 타입과 허용 값을 검증하고, 알 수 없는 필드·상태·열거값을 조용히 무시하지 않는다.
- 오프셋·주소·바이트열은 사람이 검토할 때 진법과 폭을 알아볼 수 있게 직렬화한다. 내부 계산에서는 명시적 정수 폭과 엔디언을 사용한다.
- 엔트리와 영역에는 재추출 뒤에도 대조 가능한 안정적인 키를 둔다. 배열 순번만으로 식별하면 빈 슬롯 추가나 정렬 변경 때 이력이 끊긴다.

구조화 산출물의 형식 선택과 기계 판독 입출력 원칙은 `references/conventions/project-conventions.md` §3.2를 따른다. 아래 JSON은 필드 의미를 보여 주는 기본 예시이며, 대용량 표나 기존 도구체인 때문에 다른 형식을 쓰더라도 같은 의미와 검증을 유지한다. 번역자가 편집하는 텍스트 자산의 기본 스키마와 토큰은 `references/conventions/translation-artifacts.md`가 별도로 소유한다.

## 2. 문자 매핑 테이블

커스텀 인코딩의 바이트열과 문자·문자열 대응은 `.tbl`을 기본 교환 형식으로 쓸 수 있다.

```text
41=あ
42=い
F0=のは
FF00=[END]
```

- 왼쪽은 공백 없는 16진 바이트열이며 바이트 경계를 보존한다.
- 오른쪽은 한 글자뿐 아니라 DTE/MTE가 확장하는 여러 글자일 수 있다.
- 도구가 제어코드 이름을 테이블에 함께 두면 대괄호 표기를 쓸 수 있다. 추출 산출물로 내보낼 때는 `references/conventions/translation-artifacts.md`의 가역 토큰으로 정규화한다.
- 미해독 바이트를 문자로 추정해 채우지 않는다. 조사용 덤프에서는 `<XX>`처럼 원시값이 보이는 표기를 쓰고, 편집 가능한 번역 자산에서는 가역 raw 토큰으로 보존한다.
- 테이블이 바뀌면 기존 번역 자산의 보호 필드를 손으로 고치지 않고 재추출해 차이를 검토한다.

`.tbl`을 쓰지 않는 구현도 디코드와 인코드가 같은 매핑 정본을 공유하고, 다대일·일대다 매핑과 미해독 바이트를 손실 없이 표현해야 한다.

## 3. 제어코드 사양

제어코드 사양은 추출기와 재삽입기가 함께 읽는 단일 데이터로 둔다. 최소 의미는 다음과 같다.

- 코드 바이트 또는 식별 패턴
- 인자 개수와 각 인자의 폭·엔디언·보존 방식
- 문자열이나 메시지를 끝내는지 여부
- 사람이 편집하는 토큰 이름과 의미
- 적용되는 파일·영역·렌더러 범위
- 원본 raw에 포함할 인자와 재배치 때 다시 계산할 인자의 구분

별도 형식이 없으면 다음과 같은 구조화 레코드를 기본 프로필로 쓸 수 있다.

```json
{
  "code": "FF05",
  "name": "delay",
  "arguments": [{ "width": 2, "endian": "big", "policy": "preserve" }],
  "terminates": false,
  "scope": "dialog"
}
```

의미가 아직 불명확해도 코드 경계와 인자 폭은 기록한다. 이때 중립적인 이름을 쓰고 바이트열을 통째로 보존한다. 의미 추정이 바뀌어도 파싱 경계가 흔들리지 않게 하는 것이 우선이다.

## 4. 포인터 카탈로그

포인터 카탈로그는 원본 좌표계에서 포인터를 읽고, 새 좌표계에서 다시 쓸 수 있게 하는 전수 목록이다. 최소한 다음을 복원할 수 있어야 한다.

- 포인터 바이트의 원본 저장 위치
- 폭·엔디언과 주소 기준(파일·RAM·뱅크·테이블 상대)
- 원본 raw 값과 해석한 원본 타겟
- splice나 재배치로 저장 위치 자체가 움직이는지 여부
- 보정 뒤 타겟을 검증할 패턴이나 경계 조건
- 문자열 중간 포인터라면 새 번역에서 같은 구조 지점을 찾을 앵커

기본 JSON 프로필은 다음과 같다.

```json
{
  "pointer_id": "dialog/0001/ref-0",
  "storage_offset": "0x000000",
  "width_bits": 16,
  "endian": "little",
  "basis": "ram",
  "base": "0x00000000",
  "raw_value": "0x0000",
  "target_offset": "0x000000",
  "storage_moves": true,
  "target_check": { "kind": "prefix", "bytes": "FF03" },
  "anchor": null
}
```

필드명이나 JSON 사용은 선택 사항이지만, 포인터를 splice 뒤 버퍼에서 다시 읽지 않도록 원본 raw 값과 원본 저장 좌표를 카탈로그 생성 시점에 고정한다. 카탈로그에 없는 포인터를 휴리스틱으로 조용히 보정하거나, 카탈로그 엔트리를 대응 번역 없이 버리는 동작은 빌드 오류로 처리한다.

## 5. 재삽입 정책 데이터

엔트리별 정책은 번역자가 편집하는 문장과 분리해 빌드 데이터로 관리한다. 번역 자산을 확장한다면 안정적인 엔트리 키로 연결하고, 보호 필드로 취급한다.

기본 프로필은 다음 의미를 표현한다.

| 기본 필드 | 의미 |
|---|---|
| `mode` | `fixed`, `relocate`, `grow` 가운데 선택한 길이·배치 정책 |
| `allow_truncate` | 멀티바이트 경계를 지킨 절단을 허용하는지 여부 |
| `pad_byte` | 대상 엔진이 무동작으로 처리한다고 확인한 패딩 바이트열 |
| `pad_position` | 종료 시퀀스 전·후 또는 고정 슬롯 잔여부 가운데 확인된 삽입 위치 |
| `terminator_policy` | 종료자 보존·재생성·부재 등 경계 처리 방식 |
| `alignment` | 엔트리나 블록이 유지해야 하는 바이트 정렬 |

패딩·종료자·정렬 값은 전역 기본값을 둘 수 있지만, 경계 모델이나 렌더러가 다른 영역은 별도 프로필로 나눈다. 위험한 값이 누락됐을 때 임의 기본값으로 진행하지 않고 해당 엔트리의 경계 모델을 확정하도록 실패시킨다.

## 6. 폰트 렌더 프로파일

렌더 타깃이 하나면 폰트 경로와 크기를 `--font`, `--ttf-size` 같은 직접 인자로 받아도 충분하다. 본문·UI·퍼즐처럼 타깃마다 표현 파라미터가 갈리면 타입 검증되는 프로파일로 외부화한다.

프로파일은 타깃별로 필요한 값만 선언한다. 기본 후보는 폰트, 픽셀 크기, 셀 크기, 세로 오프셋, 이진화 임계값, 윤곽선, 비트 깊이, 팔레트 인덱스다. 서로 다른 렌더러의 필드를 거대한 선택적 스키마 하나에 욱여넣지 말고, 타깃 종류별 하위 스키마를 둔다.

```json
{
  "defaults": {
    "font": "<project-relative-font-path>",
    "threshold": 128
  },
  "targets": {
    "dialog": {
      "kind": "fixed-cell",
      "size_px": 16,
      "cell": [16, 16],
      "offset_y": 0,
      "outline_px": 0,
      "bpp": 1
    }
  }
}
```

값의 해석 우선순위는 명시적 CLI override → 프로파일 값 → 코드의 검증된 기본값으로 둔다. 알 수 없는 타깃·필드와 타입 불일치는 오류로 처리한다. 빌드와 비교 시트 생성은 같은 프로파일을 읽어, 튜닝 화면과 실제 산출물이 다른 설정을 쓰지 않게 한다.

메모리 주소·뱅크·인코딩 경계처럼 역공학으로 확정한 구조값은 이 프로파일에 섞지 않는다. 표현을 자주 바꾸는 값과 바이너리 구조의 정본을 분리한다.

## 7. 검증 바인딩

데이터 형식은 다음 검사를 자동화할 수 있을 때만 채택한다.

- 번역 자산의 원문 표기 재인코딩 결과가 보호된 원본 바이트와 같고, 그 바이트가 원본 파일의 기록 위치와 같다.
- 제어코드 사양의 모든 코드가 인자 폭만큼 정확히 소비되며, 미해독·잘림이 0건으로 수렴한다.
- 포인터 raw 값을 기준 주소 규약으로 해석하면 기록한 원본 타겟이 나오고, 역변환하면 같은 raw 값이 나온다.
- 재삽입 뒤 모든 카탈로그 포인터가 유효 범위와 타겟 패턴을 만족하고, 카탈로그 엔트리 수가 예고 없이 변하지 않는다.
- 폰트 프로파일의 모든 타깃이 빌드 산출물과 비교 시트에서 같은 해석 결과를 사용한다.

구체 테스트 코드는 프로젝트 언어와 기존 테스트 구조를 따른다. 필드명을 바꾸면 테스트도 같은 커밋에서 바꾸며, 호환을 위해 알 수 없는 필드를 묵인하는 대신 명시적인 스키마 버전 변환을 둔다.
