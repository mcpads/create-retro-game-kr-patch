# Nintendo DS 국소 사례

## NDS-001

- **관측 범위:** Nintendo DS판 드래곤 퀘스트 IX 일본어판 게임 코드 `YDQJ`, 리비전 0의 캐릭터 메이크 이름 입력 후보와 선택 후 이름 재표시 경로.
- **사고 맥락:** 이름 입력 화면에서 사용하는 폰트로 보이는 NFTR의 `い` 글리프를 바꿨지만 화면은 변하지 않았다. 하나의 입력 화면이므로 후보 표시와 선택 후 재표시가 같은 폰트 자산을 쓴다고 보기 쉬웠다.
- **검증 근거:** 후보 키보드의 BNCG만 바꾼 빌드에서는 후보만 한글로 보이고 입력 필드는 일본어 글리프를 유지했다. BNCG와 같은 코드 슬롯의 MES 글리프를 함께 바꾼 빌드에서는 후보와 입력 필드·상단 이름이 같은 한글로 표시됐고, 확인 화면·첫 전투 UI·필드 이름 태그·메인 메뉴에서도 재사용됐다.
- **확정 결과:** 이 이름 입력 경로에서 후보 키보드는 미리 그려 넣은 BNCG 그래픽, 선택 후 이름 재표시는 MES 글리프가 공급했다. 일관된 입력 UX를 만들려면 같은 문자 슬롯에 대응하는 두 소비 경로를 함께 바꿔야 했다.
- **전이 한계:** 다른 화면은 후보 표시와 결과 표시의 공급 경로를 각각 추적한다. 한 경로에서 반응하지 않은 NFTR을 다른 화면에서 배제하지 않는다.
- **관련 판단 기준:** `references/strategy/font-strategy.md` §5, `references/strategy/runtime-assets.md` §2.

## NDS-002

- **관측 범위:** Nintendo DS판 드래곤 퀘스트 IX 일본어판 게임 코드 `YDQJ`, 리비전 0의 `font_lv5.gp2` 초기화와 그 안의 `f12.mes` 엔트리 직접 추가 빌드.
- **사고 맥락:** 한글 글리프를 대량 추가한 ROM이 타이틀 전에 흰 화면에 머물렀다. 초기 빌드에서는 코드 테이블 정렬, GP2 내부 파일 크기와 엔트리 수가 함께 변해 어느 차이가 실패를 만들었는지 분리되지 않았다.
- **검증 근거:** 코드 순서를 바로잡고 MES 파일별 확장을 분리했다. `f12.mes`가 384엔트리인 빌드는 타이틀에 도달했지만 385엔트리인 빌드는 후보표를 바꾸지 않아도 실패했다. 실패 빌드의 내부 파일 크기 `0x1e28`은 유지한 채 헤더와 데이터 영역을 384엔트리의 일관된 구조로 되돌린 대조 빌드는 다시 타이틀에 도달했다.
- **확정 결과:** 이 빌드 집합의 부팅 실패는 GP2 내부 파일 크기 증가 자체가 아니라 `f12.mes` 내부 구조가 385엔트리로 바뀌는 조건에 붙어 있었다. 컨테이너 크기만 줄이는 것으로 해결할 문제가 아니었다.
- **전이 한계:** 부팅 경계를 만든 후속 구조는 미확정이며, 부팅 성공은 추가 글리프의 소비를 증명하지 않는다.
- **관련 판단 기준:** `references/strategy/font-strategy.md` §3.2, `references/strategy/debugging.md` §2·§3.
