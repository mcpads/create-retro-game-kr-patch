# Saturn 국소 사례

## SATURN-004

- **관측 범위:** Saturn 마도물어의 SEQ 스크립트 포인터 재배치.
- **사고 맥락:** 패턴 스캐너가 `23 01 00 25 13 81`의 opcode 인자 `0x25`를 주소 prefix로 오인해 뒤의 맵 전환 코드를 `13 81`에서 `09 DD`로 바꿨고, 건물 진입이 크래시했다.
- **결정 실험:** 후보가 가리키는 주소의 범위와 워드 정렬을 검사해 홀수 타깃을 거짓양성으로 제외했다. 특정 suffix를 금지하는 우회는 실제 포인터까지 누락해 NPC 텍스트를 잃었으므로 폐기했다.
- **확정 결론:** 이 포맷에서는 prefix나 값 blacklist가 아니라 실제 타깃의 유효 범위·정렬·소비 형식으로 포인터를 판정해야 했다.
- **전이 한계:** 다른 포인터 형식은 유효 범위·정렬·소비 폭을 다시 정한다.
- **관련 판단 기준:** `references/strategy/text-extraction.md` §3.5, `references/strategy/reinsertion.md` §2.

## SATURN-008

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전에서 해제한 `FONT16S.SPR`과 `CSMES.SPR`의 픽셀 데이터 구간.
- **선택 맥락:** 파일 크기와 확장자만으로 bpp나 폭을 정하면 일부 라벨은 읽혀도 뒤 행이 끊기거나 다른 구간과 합쳐졌다. 두 파일은 결과적으로 4bpp였지만, 같은 비트 깊이 안에서도 시작 오프셋, 폭·행 간격, 패딩과 구간 경계가 달라 `bpp × 시작 오프셋 × 폭·행 간격`을 결합한 후보가 필요했다.
- **검증 근거:** 후보마다 기대 구간 길이가 행 바이트 수로 정확히 나뉘는지 검사하고, 행 연속성·반복 패턴·JP/EN 차이 구간·색상 채움과 패딩 경계를 함께 대조했다. 관측된 `FONT16S.SPR`에는 8~48px 혼합 폭 구간이 있었고, `CSMES.SPR`에는 의미를 확정하지 않은 선두 0x58바이트 뒤 232px·40px·248px 폭의 세 구간이 이어졌다.
- **확정 결과:** 두 자산의 픽셀 데이터는 파일 전체의 단일 폭이 아니라 구간별 `bpp·시작 오프셋·폭·행 간격` 조합으로 해석해야 했다. 길이 일치만이 아니라 행과 차이·패딩 경계가 같은 조합을 지지해야 했다.
- **전이 한계:** 선두 미해석 구간의 의미는 아직 열려 있다. 다른 자산은 선행판 차이만으로 경계를 정하지 않고 행 연속성·구간 경계와 가능한 경우 소비 인자를 확인한다.
- **관련 판단 기준:** `references/strategy/graphics-text.md` §1·§2, `references/strategy/initial-survey.md` §2.

## SATURN-009

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전 `MENU1S.SPR`의 같은 배경을 공유하는 메뉴 5개와 이름 3개 4bpp 라벨.
- **선택 맥락:** 원문 없는 clean plate가 없었고 각 변형에서 글자만 달랐다. 바이트 전체의 max나 한 nibble만 보고 바이트 전체를 덮으면 두 픽셀의 선택이 결박됐고, OR는 각 픽셀의 팔레트 인덱스 비트를 합쳐 다른 색을 만들었다.
- **검증 근거:** 배경 좌표와 팔레트가 같은 변형들을 맞춘 뒤 각 픽셀 nibble을 독립적으로 비교해 어두운 글자가 사라지는 최댓값 배경을 만들었다. 새 텍스트도 비배경 nibble만 덮어쓰고 나머지는 복원 배경을 유지해 메뉴와 이름 블록에 적용했다.
- **확정 결과:** 같은 배경·좌표·팔레트를 공유하는 변형은 packed pixel을 픽셀 단위로 분리한 뒤, 각 픽셀의 색 의미에 맞는 극값을 취해 글자 없는 배경을 복원했다.
- **전이 한계:** 변형의 배경 좌표·팔레트가 같아야 하고, 모든 변형에서 글자가 겹친 픽셀은 복원되지 않는다. 팔레트 인덱스 순서가 실제 명암 순서와 다르면 max/min을 쓰지 말고 색 의미에 맞는 선택 함수를 다시 정한다.
- **관련 판단 기준:** `references/strategy/graphics-text.md` §2·§4.

## SATURN-010

- **관측 범위:** Saturn 마도물어의 MP·PT·COMMON·DIARY SEQ 텍스트 성장과 중간 구조 재배치.
- **사고 맥락:** 파일 끝을 패딩해 전체 크기를 원본과 같게 하거나 4의 배수로 맞춰도 CD 진행 멈춤과 옵션 화면 크래시가 남았다. 텍스트 엔트리 사이에는 4바이트 포인터 표·이벤트 기술자·스크립트 코드가 끼어 있었다.
- **결정 실험:** 패치 범위를 격리해 엔트리별 변화량과 다음 구조의 정렬을 비교했다. 변화량을 4의 배수로 맞춘 빌드만 정상 진행했고, 파일 끝만 맞춘 빌드는 중간 경계 170/362개가 어긋났다.
- **확정 결과:** 필요한 지점은 최종 파일 끝이 아니라 **각 중간 소비 경계**였다. 변화량이 2바이트 어긋난 엔트리 안에 유효한 공백 타일을 넣어 이후 구조의 4바이트 정렬을 유지했다.
- **전이 한계:** 4바이트 정렬은 longword 소비가 확인된 중간 구조에만 적용한다. 다른 소비자는 정렬 단위와 패딩 값을 다시 확인한다.
- **관련 판단 기준:** `references/strategy/reinsertion.md` §1.2·§3·§6, `references/conventions/data-formats.md` §5.

## SATURN-011

- **관측 범위:** Saturn 마도물어 `MP0401.SEQ`에서 `FF02 FF3A FF3C`로 끝나는 엔트리의 길이 패딩.
- **사고 맥락:** 엔트리 정렬을 맞춘 뒤에도 해당 이벤트가 하드락했다. 알려진 종료 코드 하나의 뒤에 패딩을 붙이는 로직이 끝의 여러 `FFxx` 워드가 이루는 제어 suffix를 갈라놓고 있었다.
- **결정 실험:** 패딩 위치만 바꿔 비교하고, 바이트열 끝에서 연속된 `FFxx` 워드 전체를 역방향으로 건너뛰었다. suffix 뒤 패딩에서는 하드락이 재현됐고 첫 제어 워드 앞에 유효한 공백 타일을 넣은 빌드에서는 해소됐다.
- **확정 결과:** 마지막 종료자 하나가 아니라 **완전한 trailing control sequence 앞**을 이 엔트리의 패딩 위치로 확정했다.
- **전이 한계:** 다른 파서는 인자 폭과 상태에 맞춰 완전한 token suffix를 식별한다.
- **관련 판단 기준:** `references/strategy/reinsertion.md` §1.1·§6, `references/strategy/text-extraction.md` §3.1.

## SATURN-012

- **관측 범위:** Saturn 마도물어 COMMON·PT SEQ의 `FF00`·`FF09` 구분 기술명·결과 메시지 묶음과 하위 문자열 포인터.
- **사고 맥락:** 여러 이름을 하나의 번역 엔트리로 패치하면서 전체 길이 변화 하나만 계산하자, 앞 이름의 길이 변화가 뒤 이름을 자르거나 내부 포인터를 다른 이름 중간으로 이동시켰다.
- **검증 근거:** 원문과 번역을 같은 구분자 경계로 나누고 하위 항목 수를 대조했다. 고정 슬롯 표는 각 하위 문자열을 원래 길이에 맞춰 패딩하고, 직접 포인터가 있는 표는 각 하위 문자열의 원본 시작과 개별 이동량으로 타깃을 다시 계산했다. `FF00`과 `FF09` 사례 모두 뒤 항목 포인터의 정확한 이동을 테스트하고 실제 기술명 표시를 확인했다.
- **확정 결과:** 번역 파일의 상위 엔트리가 아니라 게임이 직접 순회·참조하는 **하위 문자열**을 길이·포인터 보정의 의미 단위로 사용해 잘림과 중간 진입을 해소했다.
- **전이 한계:** 이 대응은 구분자·하위 항목 수와 소비 방식이 보존된 입력에만 성립한다. 대응할 수 없으면 추정하지 말고 거부하거나 별도 처리한다.
- **관련 판단 기준:** `references/strategy/text-extraction.md` §3.1·§3.3, `references/strategy/reinsertion.md` §1.1·§1.2·§2.

## SATURN-013

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전 `MENU.SEQ`의 일반 페이지형 고정 슬롯과 별도 suffix를 이어 그리는 기술명 엔트리.
- **사고 맥락:** 짧아진 일반 문장 뒤에 원본 tail을 남기면 제어 토큰이 중복돼 phantom page가 생겼다. 반대로 모든 짧은 문자열을 공백 타일로 채우자 게임이 별도 포인터의 `を修得` suffix를 이어 그리는 기술명 사이에 가시적 공백이 생겼다.
- **검증 근거:** 일반 페이지형은 마지막 제어 토큰 전체를 떼고 공백을 앞에 채운 뒤 제어 토큰을 다시 붙여 원본 tail을 제거했다. suffix 연결형은 표시 소비자가 `FF00`에서 멈추고 다른 문자열로 이어짐을 확인해 해당 엔트리에만 무패딩 프로필을 적용했다. MENU 전체의 비패치 영역 동일성과 인게임 표시를 대조했다.
- **확정 결과:** 같은 파일·고정 슬롯 안에서도 일반 페이지형은 **제어 앞 패딩**, 연결형은 **종료 즉시 끝나는 무패딩**으로 정책을 분리해 제어 중복과 연결 공백을 모두 제거했다.
- **전이 한계:** 종료 뒤 소비·후속 문구 합성·trailing token 폭을 엔트리별로 확인해 패딩 프로필을 고른다.
- **관련 판단 기준:** `references/strategy/reinsertion.md` §1.1·§6, `references/conventions/data-formats.md` §5.

## SATURN-014

- **관측 범위:** Saturn 마도물어 `SYSTEM.SPR`의 헤더 없는 픽셀 시트 안에서 오프셋 0x64C0부터 시작하는 56×32 4bpp 레벨업 이펙트·문자 합성 영역.
- **선택 맥락:** 파일 선두부터 하나의 이미지로 해석하거나 비영 픽셀 덩어리만 자르면 주변의 작은 이펙트와 버튼 자산까지 같은 영역으로 묶였다. 목표는 파일 중간에서 시작하고 별 폭발과 문자가 한 비트맵 안에 이어져 있어 bpp·시작 오프셋·폭을 함께 판정해야 했다.
- **검증 근거:** 56px의 4bpp 행 간격 28바이트와 32행이 정확히 896바이트를 소비하는지 확인하고, 앞쪽 이펙트 조각이 끝나는 경계와 뒤쪽 버튼 자산이 시작하는 경계를 대조했다. 해당 구간을 행으로 펼쳤을 때 별 폭발과 문자가 하나의 연속된 56×32 이미지가 됐고, 패치는 이 896바이트만 다시 인코드해 주변 바이트를 보존했다.
- **확정 결과:** 이 시트에서는 `4bpp·파일 중간의 시작 오프셋·56px 폭`의 결합이 목표 영역의 정확한 경계와 이펙트·문자 연속성을 함께 설명했다. 파일 전체가 아니라 확정된 부분 영역만 교체할 수 있었다.
- **전이 한계:** 다른 시트는 주변 경계와 소비 결과로 bpp·시작점·행 구조를 독립 판정한다.
- **관련 판단 기준:** `references/strategy/graphics-text.md` §1·§2·§3, `references/strategy/initial-survey.md` §2.

## SATURN-015

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전 `FONT16B.CEL`의 Zone C와 Zone B, 그리고 Zone B 타일을 참조한 배경·뿌요 SEQ.
- **사고 맥락:** 828개 한글 슬롯을 확보하면서 all-zero 폰트 타일이나 반복 데이터처럼 보이는 Zone B를 그대로 덮어쓸 수 있다고 보기 쉬웠다. 실제로는 빈 타일도 배경의 투명 패턴으로 참조됐고, 가나 타일은 텍스트 밖의 배경 장식과 뿌요 패턴에도 쓰였다.
- **검증 근거:** Zone C에서 회수 가능한 734개를 구분하고, Zone B의 일부 블록을 16×16 배치로 바꾸면서 유지할 블록과 외부 참조를 전수 대조했다. 배경 18개와 뿌요 9개 SEQ의 비텍스트 참조를 새 배치와 충돌하지 않게 함께 바꾼 뒤 Zone B에서 94개를 추가해 총 828개를 확보했다.
- **확정 결과:** 필요한 슬롯을 안전하게 회수하려면 폰트 파일뿐 아니라 실제 소비 중인 비텍스트 참조와 유지 영역도 함께 보정해야 했다.
- **전이 한계:** 다른 폰트 타일은 all-zero나 중복처럼 보여도 비텍스트 소비와 투명·장식 의미를 확인하기 전에는 회수하지 않는다.
- **관련 판단 기준:** `references/strategy/font-strategy.md`, `references/strategy/graphics-text.md`, `references/strategy/runtime-assets.md`, `references/strategy/reinsertion.md`.

## SATURN-016

- **관측 범위:** Saturn 마법기사 레이어스 `STAGE01/ST010.MSG`의 메시지 텍스트와 내장 16×16 4bpp 글리프 풀.
- **사고 맥락:** 글리프 풀이 메시지의 첫 등장 순서로 보였기 때문에, 파일 전체에서 새 코드가 나타날 때마다 다음 글리프 슬롯을 배정하는 전역 표를 만들었다. 초반 앵커는 맞았지만 뒤의 한자 메시지는 다른 글자로 해석됐다.
- **검증 근거:** 전역 스캔은 코드 249종만 찾았지만 풀에는 308개 글리프가 있었고, 같은 코드가 범위에 따라 다른 글리프를 가리켰다. 잘못된 표로 목표 메시지를 렌더하면 문장이 깨졌으며, 런타임 풀 읽기는 해당 메시지의 실제 글리프 슬롯 연속을 별도로 확인했다.
- **확정 결과:** 하나의 전역 표로는 대응을 설명할 수 없었고, 같은 코드는 관측 범위에 따라 다른 글리프를 가리켰다. 정확한 범위 전환 규칙은 미확정이다.
- **전이 한계:** 범위 전환 규칙과 소비자의 인덱스 계산이 확인된 범위만 매핑·변환한다.
- **관련 판단 기준:** `references/strategy/text-extraction.md`, `references/strategy/font-strategy.md`, `references/strategy/debugging.md`.

## SATURN-017

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전의 주 폰트 `FONT16B.CEL`, 대체 폰트 `FONT16R.CEL`·`FONT16S.CEL`과 캐릭터 선택 뒤의 적재 시점·상주 상태.
- **사고 맥락:** 한 폰트의 안전한 글리프 공급량보다 번역 수요가 커서 공통 글리프와 캐릭터별 글리프를 세 파일로 나눴다. 파일명을 바꾼 빌드에서 각 대체 폰트가 실제로 적재됐으므로, 캐릭터를 고르면 해당 폰트도 다시 적재될 것으로 보기 쉬웠다.
- **검증 근거:** 아르르용 폰트가 적재된 빌드에서 루루 경로를 선택했지만 루루 전용 문자는 계속 잘못 표시됐다. 부팅 뒤 캐릭터 선택과 던전 진입을 추적해 폰트 VRAM 적재가 다시 일어나지 않음을 확인했고, 루트별 파일 분할을 버린 뒤 단일 폰트에서 828개 수요와 828개 공급을 맞춰 미할당 문자를 0으로 만들었다.
- **확정 결과:** 당시 캐릭터 선택 경로는 폰트를 다시 적재하지 않았으므로 파일 분할만으로 활성 공급량이 늘지 않았다.
- **전이 한계:** 분할 공급은 전환 시점의 재적재와 새 폰트의 소비 수명을 입증한 경우에만 활성 공급 증가로 계산한다.
