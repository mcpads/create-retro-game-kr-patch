# Saturn 국소 사례

## SATURN-009

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전에서 같은 배경을 공유하는 4bpp 라벨 변형.
- **선택 맥락:** 글자 없는 원본 배경이 없었다. 바이트 단위 최댓값이나 OR 연산은 한 바이트에 담긴 두 픽셀을 따로 고르지 못하거나 색 비트를 섞었다.
- **검증 근거:** 배경 좌표와 팔레트가 같은 변형을 맞춘 뒤 각 4비트 픽셀값을 따로 비교해 글자가 사라지는 배경색을 골랐다. 새 글자도 배경이 아닌 픽셀만 덮어썼다.
- **확정 결과:** 같은 배경·좌표·팔레트를 공유하는 변형끼리 각 4비트 픽셀을 따로 비교해 글자 없는 배경을 복원할 수 있었다.
- **전이 한계:** 모든 변형에서 글자가 겹친 픽셀은 복원되지 않는다. 팔레트 인덱스 순서가 실제 명암 순서와 다르면 최댓값·최솟값 대신 색 의미에 맞는 배경색 선택 규칙을 다시 정한다.
- **관련 판단 기준:** `references/strategy/graphics-text.md` §2·§4.

## SATURN-012

- **관측 범위:** Saturn 마도물어에서 한 번역 항목 안의 하위 문자열을 게임이 별도로 참조하는 묶음.
- **사고 맥락:** 여러 이름을 하나의 번역 항목으로 패치하면서 전체 길이 변화 하나만 계산하자, 앞 이름의 길이 변화가 뒤 이름을 자르거나 내부 포인터를 다른 이름 중간으로 이동시켰다.
- **검증 근거:** 원문과 번역을 같은 구분자 경계로 나누고 하위 항목 수를 대조했다. 고정 슬롯은 하위 문자열별로 채우고, 직접 포인터는 각 하위 문자열의 원본 시작과 개별 이동량으로 다시 계산했다.
- **확정 결과:** 번역 파일의 상위 항목이 아니라 게임이 직접 순회·참조하는 하위 문자열을 길이·포인터 보정 단위로 사용해 잘림과 중간 진입을 해소했다.
- **전이 한계:** 이 대응은 구분자·하위 항목 수와 소비 방식이 보존된 입력에만 성립한다. 대응할 수 없으면 추정하지 말고 거부하거나 별도 처리한다.
- **관련 판단 기준:** `references/strategy/text-extraction.md` §3.1·§3.3, `references/strategy/reinsertion.md` §1.1·§1.2·§2.

## SATURN-016

- **관측 범위:** Saturn 마법기사 레이어스의 메시지 텍스트와 내장 16×16 4bpp 글리프 풀.
- **사고 맥락:** 글리프 풀이 메시지의 첫 등장 순서로 보였기 때문에, 파일 전체에서 새 코드가 나타날 때마다 다음 글리프 슬롯을 배정하는 전역 표를 만들었다. 초반 표본은 맞았지만 뒤의 한자 메시지는 다른 글자로 해석됐다.
- **검증 근거:** 전역 검색에서 찾은 코드 수보다 글리프 풀이 컸고 같은 코드가 범위에 따라 다른 글리프를 가리켰다. 잘못된 표로 메시지를 표시하면 문장이 깨졌으며, 실행 중에는 각 메시지가 서로 다른 글리프 연속 구간을 읽는 것도 확인했다.
- **확정 결과:** 파일 전체를 설명하는 단일 대응표는 기각됐다. 범위 전환 규칙이 미확정이므로 전역 매핑을 추출·재삽입 기준으로 채택하지 않았다.
- **전이 한계:** 범위 전환 규칙과 소비자의 인덱스 계산이 확인된 범위만 매핑·변환한다.
- **관련 판단 기준:** `references/strategy/text-extraction.md`, `references/strategy/font-strategy.md`, `references/strategy/debugging.md`.

## SATURN-017

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전의 캐릭터 선택 뒤 상태별 폰트 적재.
- **사고 맥락:** 캐릭터 선택 전만 관찰하고 대체 파일을 이미지에 등록하지 않은 실험 때문에, 선택 뒤에는 폰트가 다시 적재되지 않는다고 오판했다.
- **검증 근거:** 선택값 확정 뒤부터 게임이 원래 실행하는 폰트 적재까지를 추적했다. 대체 파일의 구분 표식이 기존 열기·해제 경로를 거쳐 실제 화면 폰트 영역에 도달함을 확인했다.
- **확정 결과:** 캐릭터 선택 뒤 해당 경로의 폰트 자산을 읽는 기존 적재 경로가 있었다. 대체 자산도 그 경로를 거쳐 실제 화면의 폰트 영역에 도달했다.
- **전이 한계:** 선택 뒤의 적재 결과를 다른 진입·복귀·재적재 경로에 확장하지 않는다. 사용할 수 있는 글리프 수는 각 상태의 실제 자산 배정과 소비 경로를 확인한 뒤 산정한다.
- **관련 판단 기준:** `references/strategy/font-strategy.md` §3·§5, `references/strategy/runtime-assets.md` §2.

## SATURN-018

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전의 확장된 압축 폰트와 별도 고정 해제 크기 값.
- **사고 맥락:** 압축 해제 파일 끝에는 새 글리프가 있었지만 실제 폰트 메모리 끝부분은 0으로 남았다. 파일과 압축 크기가 바뀌었으므로 전체가 적재됐다고 보기 쉬웠다.
- **검증 근거:** 해제 파일과 실제 화면이 사용하는 메모리를 비교해 누락 경계를 찾고, 별도 고정 해제 크기가 확장 전 값에 머문 것을 확인했다. 이를 실제 해제 크기로 갱신하자 전체 범위가 일치했다.
- **확정 결과:** 압축 자산이 커지면 파일·컨테이너 크기뿐 아니라 게임 로더가 사용하는 해제 크기 값도 실제 해제 결과와 맞아야 했다.
- **전이 한계:** 크기 필드의 단위와 파일 끝부분을 읽는 방식은 대상 로더에서 다시 판정한다.
- **관련 판단 기준:** `references/strategy/compression.md` §5, `references/strategy/reinsertion.md` §1.2·§3·§5, `references/strategy/runtime-assets.md` §2.

## SATURN-019

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전에서 UI가 준비되기 전 문자열 소비만 확인한 경로와, 같은 표시기를 써 실제 표시·조작까지 확인한 진입 선택창의 파일 끝 추가 문자열 대조.
- **사고 맥락:** 주소 범위에 든 값을 모두 포인터로 옮긴 빌드는 원본 복원과 적재 크기 검사를 통과해도 게임 진행이 멈췄다. 직접 포인터 하나를 안전하게 옮길 수 있더라도 문자열 적재, 창 크기, 표시와 선택 동작은 별개의 검증 대상이었다.
- **검증 근거:** UI가 준비되기 전 경로에서는 원본 구조를 유지하고 확인된 직접 포인터 하나만 파일 끝 문자열로 보내 던전 진입과 16비트 문자 읽기까지 확인했다. 실제 선택창에서는 직접 포인터·적재 크기·창 위치·폭을 함께 적용해 전체 표시, 커서 왕복, 취소와 선택 후 진행을 확인했다.
- **확정 결과:** 주소 범위만으로 고른 광범위한 포인터 이동은 기각됐다. 직접 포인터 하나의 재배치는 실제 선택창에서 표시·조작·진행까지 입증됐고, UI가 준비되기 전 경로에서는 문자열 도달과 문자 소비까지만 입증됐다.
- **전이 한계:** 한 선택창의 성공은 다른 파일이나 이벤트의 표시를 증명하지 않는다. 직접 포인터, 추가 영역의 경계·정렬·종료자, 적재 크기와 실제 표시·조작·진행을 경로마다 다시 확인한다.
- **관련 판단 기준:** `references/strategy/reinsertion.md` §1.2·§2·§3·§6, `references/strategy/runtime-assets.md` §2, `references/strategy/build-and-verify.md` §5.

## SATURN-020

- **관측 범위:** Saturn 와쿠와쿠 뿌요뿌요 던전의 추가 문자열 주소에 걸린 읽기 중단점.
- **사고 맥락:** 추가 문자열 영역의 주소 읽기가 관측돼 선택지 표시 루틴이 그 문자열을 소비했다고 판단했다. 실제로는 다음 압축 자산이 같은 물리 RAM을 재사용한 뒤 해제 역참조가 그 주소를 읽고 있었다.
- **결정 실험:** 적중 시점의 실행 위치·호출 경로·읽기 출발지·도착지와 그때의 버퍼 용도를 연결했다. 읽기는 선택지 처리 뒤의 압축 해제 복사였고, 같은 빌드의 선택지 소비 경로와 분리됐다.
- **확정 결론:** 주소 읽기 적중만으로는 그 주소를 문자열로 읽었다고 볼 수 없었다. RAM 재사용 뒤의 압축 역참조가 만든 거짓 단서였다.
- **전이 한계:** 읽기 중단점은 실행 단계, 호출 경로, 그때의 버퍼 용도와 해제 결과를 함께 연결한 범위에서만 소비 증거로 쓴다.
- **관련 판단 기준:** `references/strategy/debugging.md` §2·§4, `references/strategy/compression.md` §3·§4, `references/strategy/runtime-assets.md` §2.
