# PC Engine 국소 사례

## PCE-001

- **관측 범위:** PC Engine CD 마도물어 1의 로딩 화면과 SNES 뿌요뿌요 2 Remix의 복수 배경 타일맵.
- **사고 맥락:** PC Engine 인코더는 0이 아닌 원본 타일 기준을 0으로 가정했다. SNES 인코더는 배경 계층별 논리 타일 번호를 물리 CHR 번호로 그대로 써 보호해야 할 배경 타일까지 바꿨다.
- **결정 실험:** 원본 화면 데이터를 무수정 재인코딩해 비교하고 실제 업로드 목적지와 물리 CHR을 대조했다. 각 논리 번호를 원본의 물리 타일 좌표로 바꾸자 원본 왕복과 보호 영역이 함께 일치했다.
- **확정 결론:** 두 인코더가 타일맵 번호의 실제 기준과 물리 저장 좌표를 확인하지 않고 자체 기본값을 적용한 것이 화면 손상의 원인이었다.
- **전이 한계:** 화면·배경 계층마다 논리 번호에서 실제 업로드 좌표로 이어지는 변환을 다시 구한다.
- **관련 판단 기준:** `references/platforms/pce.md` §2, `references/strategy/graphics-text.md` §2·§4.

## PCE-002

- **관측 범위:** PC Engine CD 이미지의 사용자 데이터 스트림과 원시 섹터 이미지.
- **사고 맥락:** 선행 패치의 그래픽 오프셋은 프리갭 없는 2048바이트 사용자 데이터 ISO 기준이었고, 빌드 대상은 프리갭을 포함한 2352바이트 Mode 1 BIN이었다. 좌표계를 구분하지 않으면 다른 섹터를 고치게 된다.
- **결정 실험:** 분리해 낸 사용자 데이터 스트림에서 일본어판 원본 바이트열이 한 번만 나타나는 위치를 찾고 CUE의 INDEX 차이에서 프리갭을 계산했다. 두 좌표의 차이가 계산한 프리갭과 일치함을 확인한 뒤 변경 섹터만 다시 썼다.
- **확정 결론:** 선행 패치의 2048바이트 사용자 데이터 오프셋을 대상 트랙의 2352바이트 원시 섹터 좌표로 변환하자 계산한 프리갭 차이와 원본 바이트열이 함께 일치했다.
- **전이 한계:** 보정값은 대상 이미지의 섹터 표현과 트랙 기준에서 다시 계산한다.
- **관련 판단 기준:** `references/platforms/pce.md` §4, `references/strategy/build-and-verify.md` §2.

## PCE-003

- **관측 범위:** PC Engine CD 마도물어 1의 텍스트 출력 핸들러가 주소와 X 즉시값을 BIOS 호출에 넘기는 경로.
- **사고 맥락:** 여러 핸들러의 X 즉시값이 뱅크 번호처럼 보여 하위 스크립트를 고르는 값으로 해석했다. 그러나 HuC6280 논리 주소만 보면 실제 호출 대상과 현재 MPR 매핑을 구분할 수 없었다.
- **검증 근거:** 출력 루틴을 추적하면서 MPR 상태까지 기록하자 내부에는 MPR 변경이 없었고 호출 대상은 현재 MPR에 매핑된 System Card BIOS 영역이었다. X 값은 호출 직후 덮어써져 이후 뱅크 선택으로 전파되지 않았다.
- **확정 결과:** X 즉시값은 하위 뱅크 식별자가 아니라 BIOS 태스크 스케줄러에 전달되는 인자였고 이후 뱅크나 하위 스크립트 선택에는 쓰이지 않았다.
- **전이 한계:** 다른 진입점과 간접 경로는 MPR 매핑과 실제 소비를 따로 추적한다.
- **관련 판단 기준:** `references/strategy/initial-survey.md` §2.2·§3, `references/strategy/debugging.md` §2·§4, `references/platforms/pce.md` §1.

## PCE-004

- **관측 범위:** PC Engine CD 마도물어 1과 PlayStation 와쿠와쿠 뿌요뿌요 던전의 BIOS 글리프 공급 호출 뒤 1bpp→4bpp 변환·VRAM 업로드 경로.
- **사고 맥락:** 한글 표시를 위해 텍스트 파서부터 VRAM 전송까지 별도 표시 루틴으로 바꿔야 한다고 보기 쉬웠다. 두 원본 경로는 BIOS가 돌려준 1bpp 글리프를 게임 코드가 4bpp로 확장해 VRAM으로 보내고 있었다.
- **검증 근거:** 두 게임 모두 BIOS 글리프 공급 호출을 호환 공급 함수로 바꾸고 기존 텍스트 파서·1bpp→4bpp 변환·VRAM 업로드를 유지했다. PC Engine에서는 서로 다른 두 한글 글리프가 화면에 표시됐고, PlayStation에서는 한글 범위만 대체하고 나머지 문자를 원래 BIOS로 보내 기존 캐시까지 재사용했다.
- **확정 결과:** 두 소비 경로에서는 글리프 공급 인터페이스만 대체해 원본의 뒤쪽 변환·업로드를 재사용할 수 있었다.
- **전이 한계:** 다른 호출자는 공급 규약·비트 배열·버퍼 수명·캐시 식별값과 뒤쪽 변환을 다시 확인한다. 이 성공만으로 별도 자산의 적재 상태나 다른 실행 상태까지 보존됐다고 볼 수는 없다.
- **관련 판단 기준:** `references/strategy/font-strategy.md`, `references/strategy/reinsertion.md`, `references/strategy/runtime-assets.md`, `references/strategy/poc.md`.
