# PC Engine / PCE CD-ROM² 한글 패치 참조

PC Engine(NEC/Hudson, 1987)과 CD-ROM² 확장(1988) 타이틀의 한글화에 필요한 플랫폼 사실을 정리한다. 플랫폼 사실과 특정 게임에서 나온 수치는 구분해 읽고, 텍스트 엔진·로더·디스크 배치는 대상 게임에서 다시 실측한다.

---

## 1. 플랫폼 개요

핵심 칩 구성은 다음과 같다.

| 칩 | 역할 | 비고 |
|---|---|---|
| HuC6280 | CPU + PSG + 타이머 + IRQ + I/O + MMU | 65C02 슈퍼셋, 8비트 |
| HuC6270 (VDC) | Video Display Controller | 64KB VRAM, 타일/스프라이트 |
| HuC6260 (VCE) | Video Color Encoder | 9비트 RGB 팔레트 |
| System Card (CD) | CD-ROM² BIOS HuCard | 부팅 + CD/ADPCM/폰트 라이브러리 |

HuC6280 요점:
- 65C02 슈퍼셋, 리틀 엔디언. 클럭은 1.7897725MHz(저속)/7.15909MHz(고속)이며 `CSL`/`CSH` 명령으로 런타임 전환한다. 많은 게임이 부팅 직후 `CSH`로 7.16MHz로 올리지만, 실제 클럭 상태는 초기화 코드를 확인한다.
- 65C02 확장 외 PCE 전용 명령: `TAM`/`TMA`(MPR 제어), `TII`/`TDD`/`TIN`/`TIA`/`TAI`(7바이트 블록 전송, 사이클 = 17 + 6×len. 방향: TII 양쪽 증가, TDD 양쪽 감소, TIN 소스만 증가, TIA 소스 증가·목적 2주소 교대(16비트 포트용), TAI 소스 2주소 교대·목적 증가. 어느 명령이 보이는지로 데이터 흐름을 읽는다), `ST0`/`ST1`/`ST2`(VDC 직접 쓰기), `CSL`/`CSH`, T 플래그(메모리-메모리 연산).
- 스택·zero page 표기는 도구와 버스 주소 표기 관례에 따라 혼동되기 쉽다. PCE 코드 분석에서는 MPR 설정 뒤 work RAM이 보이는 논리 페이지를 기준으로 관측되는 경우가 많으므로, 프로젝트 문서에는 초기화 코드의 MPR 값과 디버거가 보여주는 논리 주소를 함께 기록한다. 논리 주소만 떼어 플랫폼 고정 스택 위치로 기록하지 않는다.
- 6502와 달리 `abs,X` 페이지 경계 크로싱 패널티(+1 사이클)가 없다.

CD-ROM² 시스템은 System Card HuCard로 부팅하며 카드 요구사항에 따라 RAM 모델이 다르다: 원본 CD-ROM²는 일반 64KB + ADPCM 64KB + 세이브 2KB, Super CD-ROM²(Card 3.0)는 일반 256KB, Arcade Card는 Super 구성에 2MB 확장 RAM을 더한다. BIOS는 `$E000-$FFFF`에 점프 테이블(항목당 3바이트)로 노출되고 `cd_read`($E009), `ex_getfnt`($E060), `ex_joysns`($E063), `ex_vsync`($E07B) 등을 제공한다. 단, 게임이 BIOS CD 읽기를 쓰지 않고 자체 로더를 복제해 넣은 경우가 있으므로 섹터 배치를 바꿀 때는 자체 로더의 하드코딩 섹터 번호를 추적해야 한다. 카드 요구사항은 이름·릴리즈 연도·폴더명으로 추정하지 말고 부팅 요구, 에뮬레이터 모듈, 초기 로더, Arcade Card I/O 접근 여부로 확인한다.

ADPCM 음성은 64KB 전용 RAM(CPU 주소 공간 밖)에서 OKI 계열 4비트 ADPCM으로 재생된다. 재생률은 고정 32kHz가 아니라 ADPCM 하드웨어/게임 코드의 레지스터 설정에 좌우되므로, 음성 분석 문서에는 해당 씬의 설정 값을 관측해 기록한다. BGM은 CDDA 오디오 트랙으로 공급되는 경우가 많아 텍스트 패치에서 건드리지 않는 경우가 많지만, 트랙 구성은 CUE와 게임 로더에서 확인한다.

## 2. 메모리 맵과 MPR 페이징

CPU 논리 주소는 16비트(64KB), 물리 주소는 21비트(2MB)다. 논리 공간을 8KB 단위 8페이지로 나누고, MPR0~MPR7 레지스터가 각 페이지의 물리 뱅크(상위 8비트)를 결정한다.

| 논리 주소 | 페이지 | MPR | TAM/TMA 마스크 |
|---|---|---|---|
| `$0000-$1FFF` | 0 | MPR0 | `%00000001` |
| `$2000-$3FFF` | 1 | MPR1 | `%00000010` |
| `$4000-$5FFF` | 2 | MPR2 | `%00000100` |
| `$6000-$7FFF` | 3 | MPR3 | `%00001000` |
| `$8000-$9FFF` | 4 | MPR4 | `%00010000` |
| `$A000-$BFFF` | 5 | MPR5 | `%00100000` |
| `$C000-$DFFF` | 6 | MPR6 | `%01000000` |
| `$E000-$FFFF` | 7 | MPR7 | `%10000000` |

`TAM #$ii`로 A를 마스크 비트의 MPR에 쓰고, `TMA #$ii`로 읽는다. RESET 시에는 MPR7만 `$00`(ROM 뱅크 0)으로 설정되어 ROM 선두 뱅크의 `$E000+offset`이 매핑되고, 그 안의 인터럽트 벡터(`$FFF6-$FFFF`)로 부팅한다. 나머지 MPR은 초기화되지 않으므로 부트 코드가 직접 설정한다.

물리 뱅크 레이아웃(뱅크 1개 = 8KB):

| 뱅크 | 영역 |
|---|---|
| `$00-$7F` | HuCard ROM (최대 1MB) |
| `$68-$87` | CD 일반 RAM (Super CD-ROM², 256KB) — 원본 CD-ROM²는 `$80-$87` 64KB |
| `$F7` | BRAM (세이브 2KB) |
| `$F8` | Work RAM (8KB, `$F9-$FB`는 미러) |
| `$FF` | 하드웨어 페이지 (VDC/VCE/PSG/Timer/I/O/IRQ) |

CD 모드의 `$E000-$FFFF`는 System Card BIOS 점프 테이블의 안정적인 entry anchor다. 다만 BIOS ROM bank·함수 본체·데이터가 항상 MPR7에만 보인다고 가정하지 않는다. 게임이나 BIOS가 MPR을 바꾼 뒤에는 다른 논리 슬롯에도 System Card bank가 노출될 수 있으므로, BIOS 경로 분석은 호출 주소와 함께 현재 MPR0-MPR7 상태를 기록한다.

### MPR 매핑 기준 포인터

CD 게임의 스크립트 데이터는 8KB 페이지 단위로 특정 논리 슬롯에 swap-in될 수 있으며, 이 경우 포인터 값은 파일 오프셋이 아니라 **매핑된 상태의 CPU 버스 주소**다. 파일 오프셋은 `섹션 베이스 + (포인터 값 − 실측한 논리 슬롯 베이스)`로 환산한다. 슬롯 베이스와 동시에 보이는 페이지 수는 로더의 MPR 설정에서 대상 게임별로 확정한다.

- 페이로드는 로더가 동시에 노출하는 매핑 슬롯의 가시 범위를 벗어날 수 없다. 여러 region이 슬롯을 공유하면 각 region의 최대치가 아니라 공유 시점의 총 가시 범위가 상한이다.
- 번역 페이로드가 상한을 넘으면 저장 공간뿐 아니라 로더의 페이지 전환과 인터프리터의 포인터 규약도 함께 확장해야 한다.
- 포인터 테이블이 low/high 바이트 평행 배열이면 두 배열을 같은 엔트리 집합으로 검증하고, 재배치 뒤에는 실측한 논리 슬롯 베이스로 전수 재계산한다.

## 3. 비디오 시스템

VDC(HuC6270)는 자체 VRAM 64KB를 가지며 16비트 워드 단위로 접근한다(VRAM 1주소 = 2바이트). 백그라운드 1레이어 + 스프라이트 64개, 픽셀은 4bpp(16색 팔레트, BG/스프라이트 각 16개)다.

- 타일: 8×8, 4bpp 플레이너. 16×16 글리프 1자 = 타일 4개 = 128바이트.
- BAT(타일맵) 엔트리는 16비트 — 비트 0-11 타일 인덱스(4096슬롯), 비트 12-15 팔레트 번호.
- 타일 인덱스 필드는 화면에 올린 타일셋의 VRAM 베이스를 이미 포함한 값일 수 있다. 베이크드 그래픽이나 타일맵을 재인코딩할 때 타일 번호가 0부터 시작한다고 가정하지 말고, 원본 BAT의 하위 12비트와 업로드 대상 VRAM 주소로 base tile/loadAddr를 확정한다. 원본 타일맵을 디코드→재인코드해 바이트가 일치하는지 확인하면 base tile, 행 stride, 팔레트 라인 오해를 초기에 잡을 수 있다.
- VDC 접근은 `$FF:0000`(레지스터 셀렉트/상태), `$FF:0002/0003`(데이터 LSB/MSB). MAWR($00)에 주소를 쓰고 VWR($02)로 데이터를 흘린다. `TIA src,$0002,len` 블록 전송은 VRAM 대량 쓰기 경로로 자주 쓰인다.
- VCE 팔레트는 512 엔트리 × 9비트(3R/3G/3B). 표준 해상도는 256×224가 가장 흔하다.

텍스트 렌더에서 중요한 것: 글리프는 1bpp로 받아 4bpp로 expand한 뒤 VRAM에 전송하는 패턴이 일반적이다. 1bpp 바이트를 두 플레인에 동시에 쓰면 색 인덱스 3이 된다.

PCE 베이크드 그래픽은 한 포맷으로 고정하지 않는다. 선형 4bpp 타일, BAT 타일맵(맵 + 고유 타일셋 + base tile), 16×16 스프라이트 시트처럼 여러 경로가 섞일 수 있다. 어느 경로든 게임이 예약한 VRAM 영역을 넘는 고유 타일 수를 만들면 뒤따르는 그래픽이 깨지므로, 원본 업로드 크기와 VRAM 배치 안에서 수용되는지 타일 예산을 검사한다. 포맷 선택은 파일명이나 선행 도구가 아니라 업로드 경로와 원본 라운드트립으로 확정한다.

## 4. 디스크 포맷

PCE CD는 BIN/CUE 멀티트랙 이미지가 표준이다. 데이터 트랙은 MODE1/2352, BGM은 CDDA 오디오 트랙이다. 데이터 트랙이 하나라고 가정하지 말고 CUE에서 모든 MODE1/2352 트랙을 열거한다. 그중 실제 로더가 참조하는 데이터 트랙만 수정하고, 나머지 데이터 트랙과 오디오 트랙은 byte-exact로 보존한다. 트랙 번호나 파일명보다 CUE의 track type과 게임 로더의 참조가 우선이다.

MODE1/2352 섹터 구조(2352B: Sync 12 + Header 4 + User data 2048 + EDC 4 + Reserved 8 + ECC 276)와 EDC/ECC 재계산 알고리즘·오프셋은 `references/strategy/build-and-verify.md` §3이 정본이다. PCE 데이터 트랙은 MODE1/2352이므로 §3의 Mode 1 섹터 도표가 그대로 적용된다.

- 섹터 N의 사용자 데이터 파일 오프셋 = `N × 2352 + 16`(raw BIN 기준), 논리(2048B 기준) 오프셋 = `N × 0x800`. Sync 패턴·Header(MSF + 모드 바이트) 등 Mode 1 섹터 상세는 §3을 본다.

외부 도구가 보고한 2048바이트 ISO 오프셋을 raw 2352 BIN에 그대로 적용하지 않는다. ISO 추출물은 트랙 pregap/INDEX 배치를 제외한 사용자 데이터 스트림일 수 있고, raw BIN은 CUE의 pregap까지 포함한 섹터열일 수 있다. 외부 오프셋을 받아 쓸 때는 CUE의 TRACK/INDEX/PREGAP을 반영해 raw 섹터 위치로 변환하되, 안전한 방법은 원본 바이트 시퀀스를 2048 deinterleave 스트림이나 raw BIN에서 byte-search해 실제 앵커를 확정하는 것이다.

### EDC/ECC 재계산

데이터 트랙 섹터를 수정하면 해당 섹터의 EDC/ECC를 재계산한다. EDC(CD용 CRC-32 변형)·ECC(Reed-Solomon P/Q 프로덕트 코드)의 다항식 상수·패리티 바이트 수·입력 범위·저장 오프셋(ECMA-130 정의)과, 변경 섹터만 재계산하고 원본의 의도적 오류 섹터는 보존하는 정책은 `references/strategy/build-and-verify.md` §3이 정본이다. 실행 환경의 부팅 성공을 섹터 정합 증거로 대신하지 말고 변경 섹터를 독립 검증한다.

## 5. 텍스트 엔진 패턴

### 5.1 op-code 디스패치 분석법

PCE 텍스트 인터프리터에서 관찰되는 패턴 중 하나는 "바이트가 임계값 미만이면 op-code, 이상이면 문자"인 구조다. 한 사례에서 확인된 재사용 가능한 단서는 다음과 같다.

- op-code 영역이 연속 저값 구간이고 그 위를 문자 lead byte로 해석할 수 있다. 경계값과 미사용 구간은 타이틀마다 다시 측정한다.
- 디스패처는 op 바이트를 인덱스로 **low 바이트 핸들러 테이블 + high 바이트 핸들러 테이블** 두 평행 배열에서 핸들러 주소를 조립하고, 자기 수정 코드로 간접 점프한다. `LDA table_lo,Y / STA operand / LDA table_hi,Y / STA operand+1` 패턴을 찾으면 테이블 위치가 확정된다. 임계값 판정 + 핸들러 테이블 인덱싱은 PCE 텍스트 엔진 분석의 유력한 출발점이지만, low/high 평행 배열 + 자기수정 점프는 여러 구현 중 하나다. 다른 게임은 단일 주소 테이블이나 점프 테이블 등 다른 형태를 쓰므로 디스패처 형태는 게임별로 확인한다.
- op 전부가 고유 핸들러인 경우가 있다 — 공유 핸들러가 없으면 핸들러 주소를 정렬해 op별 의미 분석의 출발점으로 삼는다.

확정한 op의 숫자·이름·인자 수와 스크립트 콜 스택 구조는 대상 프로젝트의 포맷 문서가 소유한다. 플랫폼 문서에는 이 표를 복제하지 않는다.

### 5.2 빈도 통계로 의미를 추정하는 기법

핸들러 디스어셈블만으로 의미가 안 잡히는 op는 전수 덤프의 통계로 좁힌다. 실전에서 통한 추론 순서:

1. **빈도 자체가 신원이다.** end의 출현 수는 스크립트 엔트리 수와 정확히 일치한다(엔트리당 종결 1회). br·clear처럼 엔트리당 1회 이상 나오는 op는 줄바꿈/클리어 같은 핵심 렌더 명령 후보가 된다.
2. **인자 분포를 본다.** 특정 대기 op의 인자가 한 값에 몰리면 프레임·틱 단위 가설을 세우고 실제 실행 시간과 대조한다. 다중 바이트 인자의 상위 바이트가 거의 0이면 작은 카운터일 가능성이 있지만, 핸들러의 산술로 확정한다.
3. **주변 컨텍스트를 본다.** 반복적으로 `{op}{박스 op}{clear}<텍스트>` 위치에 나오는 op는 화자/씬 식별자 후보이고, 텍스트 사이에 끼는 op는 표정 전환·SE 트리거 후보가 된다. 인자 값별로 직후 텍스트를 모아 보면 화자 매핑이 잡힌다.
4. 빈도가 0회인 op도 핸들러 자체는 존재할 수 있는데, 미사용 op라면 패치에서 무시해도 된다.
5. **음성 동기 op는 보존한다.** ADPCM 종료까지 진행을 멈추는 마커를 제거하면 음성 도중 박스가 넘어간다. 의미를 모르는 op도 인자 포함 바이트 시퀀스 보존을 우선한다 — 핸들러가 BIOS 태스크 스케줄러 호출이어도 바이트가 같으면 동작이 보존된다.

### 5.3 컷신 음성 전사와 자막 추가

PCE CD 컷신은 화면 텍스트 없이 일본어 음성만으로 정보를 전달하는 경우가 있다. 한글 패치에서 이 내용을 플레이어에게 전달하려면 JP ADPCM 음성을 추출·디코드해 전사하고, 별도 자막 렌더 경로를 설계해야 한다. 기존 스크립트에 자막 슬롯이 없으면 베이크드 그래픽/스프라이트 캡션/오버레이 텍스트 중 하나를 새 자막 트랙으로 추가하는 작업이 되며, 이는 일반 텍스트 번역이 아니라 `references/strategy/graphics-text.md`와 검증 루프를 공유하는 별도 서브트랙이다.

전사 목적의 ADPCM 디코드는 정확한 피치보다 식별 가능한 음성이 우선이다. 재생률은 씬별 레지스터 설정으로 확정하되, 전사용 초벌 디코드에서는 여러 후보 레이트를 비교해 사람이 듣고 전사할 수 있는 산출물을 만든다. 자막을 추가할 때도 음성 동기 op와 기존 컷신 진행 제어코드는 원문 바이트 시퀀스 보존을 기본값으로 둔다.

### 5.4 텍스트 박스 시스템

한 사례에서는 폭이 다른 여러 고정폭 박스가 같은 좌표 시스템을 공유하고, 박스 선택과 커서 초기화가 서로 다른 op에 속했다. 이 패턴에서는 박스 전환만으로 커서가 초기화된다고 가정하면 안 된다. 대상 게임에서 박스별 가로·세로·줄 높이, 커서 상태와 이를 리셋하는 op를 실측하고 정적 레이아웃 검사의 입력으로 둔다. 정확한 치수와 op 값은 프로젝트 문서에 기록한다.

### 5.5 인라인 리터럴 주의

스크립트 region 밖, 핸들러 코드 옆에 층수·빈 슬롯·숫자 표기 같은 짧은 일본어 문자열이 직접 박혀 있을 수 있다. 코드 뱅크의 리터럴을 블록 전송이나 테이블 fetch로 출력하는 경로는 region 번역만으로 잡히지 않으므로 인라인 리터럴 후보를 별도로 전수 검색한다. 실제 문자열·주소·교체 바이트는 프로젝트 문서가 소유한다.

## 6. 한글 표시 경로

### 6.1 원본 글리프 경로: BIOS `ex_getfnt`

BIOS 폰트에 의존하는 게임에서는 일본어 글리프가 게임 데이터가 아니라 **System Card BIOS의 `ex_getfnt`($E060)**에서 온다. 자체 폰트를 디스크에 내장한 게임도 있으므로 글리프 출처를 먼저 실측한다. 호출 규약:

- 입력: `_AL`($F8) = SJIS trail, `_AH`($F9) = SJIS lead, `_BL/_BH`($FA/$FB) = 결과 버퍼 주소, `_DH`($FF) = 컬러 속성(0 = 단색)
- 출력: `_BX`가 가리키는 RAM에 16×16 1bpp 글리프 32바이트

한 사례에서는 게임 코드가 SJIS 코드를 BIOS에 그대로 전달하고, 받은 1bpp 글리프를 4bpp 타일로 변환해 IRQ 컨텍스트에서 VRAM으로 전송했다. 이 경로를 재사용하려면 대상 게임에서도 호출 규약·변환·전송 소비자가 같은지 확인한다.

한글 글리프는 어떤 System Card BIOS 버전에도 없다. 따라서 한글 표시의 본질은 **`ex_getfnt` 호출을 가로채 ROM에 임베드한 한글 글리프를 같은 규약으로 돌려주는 것**이다.

### 6.2 최소 PoC: BIOS 폰트 훅

BIOS `ex_getfnt`에 의존하는 게임에서 통하는 최소 개입 경로:

1. 한글 글리프를 BIOS가 반환하는 것과 같은 16×16 1bpp 형식으로 만들고, 읽기 참조가 없음을 확인한 저장 영역에 배치한다.
2. 텍스트 경로에서 BIOS 폰트 함수를 호출하는 지점을 전수화하고, 대표 경로의 호출을 훅으로 우회한다.
3. 훅은 대상 게임에서 미사용임을 전 코퍼스로 확인한 한글 코드면 임베드 글리프를 기존 결과 버퍼에 복사하고, 그 밖의 코드는 원래 BIOS 함수로 넘긴다.
4. 스크립트의 SJIS 한 글자를 한글 코드로 바꿔 빌드하면 expand/DMA는 원본 코드가 그대로 처리해 한글이 화면에 출력된다.

훅을 호출 지점과 같은 뱅크에 둘 수 있으면 뱅크 트램폴린 비용을 피할 수 있다. 다른 뱅크를 쓰면 `TMA`/`TAM` 전후의 MPR·레지스터 보존을 함께 검증한다. 한글 코드 범위는 표준의 사용자 정의 명칭만 믿지 말고 대상 게임의 전 코퍼스·글리프·제어코드 사용량으로 확정한다(`references/strategy/font-strategy.md` §2).

### 6.3 확장

- 훅의 단일 글리프 복사를 테이블 룩업(lead/trail → 글리프 인덱스)으로 바꾸면 풀 한글로 확장된다.
- 글리프 시트는 번역 수요와 저장·활성 메모리 예산에 따라 서브셋 또는 전량 공급을 고르고, 8KB 뱅크 경계를 넘을 때의 MPR 전환을 빌드와 런타임에서 검증한다(`references/strategy/font-strategy.md` §3).
- 16×16 고정폭이면 원본 변환·DMA 경로를 재사용할 가능성이 높다. 가변폭이나 합성이 필요하면 리터럴 판정, 렌더러, 전송 큐와 IRQ 소비 경로의 추가 개입 범위를 조사한 뒤 조건부 PoC로 결정한다.

## 7. 빌드 (BIN/CUE 재구성)

1. 원본 BIN/CUE에서 모든 데이터 트랙(MODE1/2352)을 열거하고, 각 트랙의 섹터별 사용자 데이터 2048바이트를 추출한다(`N × 2352 + 16`).
2. 외부 오프셋이나 선행 패치 추출물을 입력으로 받을 때는 원본 디스크에서 byte-search로 앵커를 재확인하고, pregap/INDEX 차이로 raw BIN 위치가 어긋나지 않았는지 기록한다.
3. 게임 로더가 참조하는 데이터 트랙의 추출본에만 스크립트 페이로드 교체·실측한 논리 슬롯 베이스 기준의 포인터 재계산·훅/글리프 바이트 패치를 적용한다.
4. 변경된 섹터만 EDC/ECC를 재계산해 2352바이트 섹터로 되감는다. 어떤 섹터가 변했는지 추적하는 구조로 만들면 재계산 범위와 diff 검증이 쉬워진다.
5. 수정한 데이터 트랙만 신규로 쓰고, 수정하지 않은 데이터 트랙과 오디오 트랙(CDDA BGM)은 원본 그대로 복사 또는 참조하는 CUE를 생성한다. 멀티트랙 BIN을 합본 single-bin으로 낼 수도 있다.
6. 산출물의 CRC32/MD5와 변경 섹터 목록을 기록한다.

게임이 자체 CD 로더를 쓰는 경우 섹터 배치를 바꾸면 로더의 하드코딩 섹터 번호도 갱신해야 한다. 기존 섹터 안에서만 바이트를 바꾸는 패치라면 이 문제가 없다.

## 8. 검증 (에뮬레이터 디버깅)

검증 환경은 HuC6280 단계 실행·코드/메모리 브레이크포인트·RAM/VRAM readback을 제공하고, MPR 전환과 CD I/O를 관측할 수 있어야 한다. 제품명보다 이 기능 집합이 선택 기준이다.

- 게임이 요구하는 System Card 세대와 리전, CD 장치 구성을 실제 배포 조건과 맞춘다. BIOS 파일명과 배치 위치는 선택한 실행 환경의 프로젝트 설정으로 기록한다.
- BIOS 글리프 호출 또는 게임 자체 로더와 VRAM 전송 루틴을 함께 추적해 글리프 데이터가 버퍼→변환→VRAM으로 흐르는 것을 확인한다.
- 시각 검증 경로: 부팅 화면 → 첫 플레이 가능 지점 → 텍스트 박스 출력 확인. 박스 폭/줄 한도 초과는 에뮬레이터에서 글자가 박스 밖으로 흘러나오는 형태로 드러나므로 빌드 단계의 정적 overflow 검사와 이중으로 잡는다.
- 에뮬레이터가 어떤 섹터 검사를 수행하는지에 기대지 않는다. 변경 섹터의 EDC/ECC와 트랙 구조는 별도 검사기로 확인하고, 실행 검증은 로더·렌더러 동작 증거로 사용한다.

### 실기 구동 경로

실광학 매체, 이미지 로더, 하드웨어 재구현 중 프로젝트가 실제로 지원할 경로를 고른다.

- **실광학 매체**: INDEX/pregap/CUE 재현, 변경 섹터의 EDC/ECC, 타이틀별 디스크 구조와 요구 System Card를 보존한다. 드라이브 상태와 미디어 품질 실패를 패치 결함과 분리한다.
- **이미지 로더**: 원본의 트랙 분할·MODE1/2352·CDDA·INDEX/pregap을 보존해 읽고, 요구 System Card와 본체의 CD 장치·버스 구성에서 충돌 없이 동작해야 한다. CDDA 채널 구성도 대상 출력과 맞는지 확인한다.
- **하드웨어 재구현**: HuC6280·MPR·비디오뿐 아니라 CD 인터페이스와 혼합 트랙 재생까지 이번 변경 경로를 덮을 때만 중간 검증 근거로 쓴다.

**빌드 포맷에 미치는 영향**: 오디오+데이터 혼합 구조에서 INDEX·pregap을 보존해야 하므로 **멀티트랙 BIN/CUE 유지를 우선 선택한다**. 데이터 트랙만 ISO로 뽑으면 CDDA가 들어간 게임이 깨진다. 굽기용과 ODE용이 같은 BIN/CUE를 공유할 수 있으면 포맷 변환 비용이 낮다(7절 BIN/CUE 재구성 산출물을 실기 검증 대상으로 삼는다).

자주 빠지는 함정으로, 게임이 요구하는 System Card 세대와 실제 검증 장치의 CD·오디오 능력을 명시해야 한다. 중간 환경의 통과는 그 환경이 구현하지 않은 광학·버스·오디오 동작을 증명하지 않으므로, 배포를 주장하는 대상 경로에서 최종 확인한다. 검증 티어 운용은 `references/strategy/build-and-verify.md` §4를 따른다.

## 9. 사례 요약 — PCE 마도물어 1

- 멀티트랙 이미지에서 게임 로더가 실제 참조하는 데이터 트랙만 수정하고, 별도 데이터·CDDA 트랙은 역할을 확인한 뒤 원본 그대로 보존했다.
- 게임이 BIOS `cd_read`를 쓰지 않고 자체 CD 로더를 내장. 메인 던전 블록은 단일 섹터 구간에서 통째로 CD RAM에 로드된 후 8KB 페이지 단위로 MPR swap-in.
- 텍스트 엔진은 연속 제어코드 구간, low/high 평행 핸들러 테이블과 자기 수정 간접 디스패치를 사용했다. 전수 덤프의 빈도·인자 분포·주변 문맥으로 op 의미를 좁혔다.
- 폭이 다른 고정폭 박스들이 같은 좌표 상태를 공유했고, MPR 매핑 슬롯의 가시 범위가 한글 페이로드의 강한 크기 한도였다.
- 한글 PoC는 BIOS 폰트 호출을 가로채 같은 결과 버퍼에 한글 글리프를 공급하고, 원본의 변환·VRAM 전송 경로를 재사용했다.
- 베이크드 그래픽은 선행 패치 추출물에 의존하지 않고 원본 디스크에서 byte-search로 위치를 잡아 self-source했고, 원본 디코드→재인코드 라운드트립으로 BAT base tile과 타일 예산을 검증했다(레퍼런스 툴 일치가 원본 라운드트립을 대신하지 못한다는 원본 라운드트립 우선 원칙은 `references/strategy/text-extraction.md` §5).
- 음성 동기 마커(wait_for_voice)와 미해석 op의 바이트 시퀀스는 전량 보존. 일본어 음성은 유지하고, 자막 없는 음성 컷신은 ADPCM 추출·전사 뒤 별도 한글 캡션 경로를 추가하는 정책.
