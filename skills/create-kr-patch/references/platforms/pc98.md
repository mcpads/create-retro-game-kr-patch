# PC-98 (NEC PC-9801/9821) 한글 패치 참조

## 1. 플랫폼 개요

NEC PC-9801은 1982년 출시된 일본 국내 표준 16비트 PC 라인업이다. IBM PC와 호환되지 않는 자체 아키텍처이며, CPU는 8086 또는 NEC V30(8086 슈퍼셋, 80186 명령어 포함)이고 후기 모델은 80286/80386을 탑재한다. 1990년 전후 게임은 모델 호환성을 위해 공통분모인 8086 명령어 셋으로 빌드된 경우가 많다. 디스어셈블 중 80186+ 명령어(`PUSHA`, 즉시값 시프트 등)가 보이면 V30 이상 전용 빌드라는 단서다. 패치 코드도 8086 호환을 유지하려면 V30 고유 명령어를 쓰지 않는다.

화면은 텍스트 plane과 그래픽 plane이 분리된 dual-GDC(µPD7220 ×2) 구조다. master GDC가 텍스트 plane(80×25 문자 그리드, 시스템 한자 ROM 합성), slave GDC가 그래픽 plane(640×400, 4 plane = 16색)을 담당하고, 텍스트 plane이 그래픽 plane 위에 오버레이된다. 게임 텍스트가 어느 plane에 그려지는지 식별하는 것이 텍스트·폰트 분석의 첫 단계다.

콘솔과 달리, 코드가 ROM이 아니라 **디스크에서 RAM으로 적재되어 실행**된다. 패치 대상은 ROM 바이너리가 아니라 디스크 이미지 안의 파일/섹터 데이터이고, 디스어셈블은 어떤 파일이 어떤 메모리 주소에 적재되는지부터 알아내야 한다.

## 2. 메모리 모델

8086 리얼 모드는 모든 주소를 세그먼트:오프셋 쌍으로 표현한다. 물리 주소 = `SEG × 16 + OFF`(20비트, 1MB 공간). flat 주소 공간이 아니므로 같은 물리 주소를 여러 (seg, off) 조합으로 표현할 수 있다.

| 세그먼트:오프셋 | 물리 주소 | 용도 |
|---|---|---|
| `0000:0000`– | `0x00000`– | 인터럽트 벡터 테이블 (256 × 4B) |
| `0060:0000`–`9FFF:000F` | `0x00600`–`0x9FFFF` | 메인 RAM (~640KB conventional) |
| `A000:0000`– | `0xA0000`–`0xA3FFF` | 텍스트 VRAM (TVRAM) |
| `A400:0000`– | `0xA4000`– | CG 윈도우 (한자 ROM 액세스) |
| `A800:0000`– | `0xA8000`– | 그래픽 VRAM plane 0 (B) 32KB |
| `B000:0000`– | `0xB0000`– | 그래픽 VRAM plane 1 (R) 32KB |
| `B800:0000`– | `0xB8000`– | 그래픽 VRAM plane 2 (G) 32KB |
| `E000:0000`– | `0xE0000`– | 그래픽 VRAM plane 3 (I) 32KB |
| `F800:0000`– | `0xF8000`– | BIOS / IPL ROM |

패치 코드 작성 시 주의점:

- near `JMP`/`CALL`은 16비트 displacement로 같은 CS 안 ±32KB까지만 직접 도달한다. 더 멀면 `JMP FAR seg:off`(5바이트)가 필요하므로 트램폴린의 점프 거리를 항상 확인한다.
- 조건 분기는 8비트 displacement(-128~+127)만 허용한다.
- 텍스트 처리 루틴은 거의 항상 `LODSB`/`STOSB`/`MOVSB` string 명령으로 짜이므로, 문자열 디코더를 찾는 단서가 된다.
- `OUT DX, AL` 시퀀스 주변은 GDC/FDC/사운드 칩 제어 코드다.

자주 쓰는 BIOS 인터럽트: `INT 18h`(CRT/한자 표시), `INT 1Bh`(디스크 read/write), `INT 21h`(DOS API). 디스크→RAM 적재 매핑은 `INT 1Bh` 호출 인자(트랙·섹터·길이·대상 주소)에서 직접 읽어낸다.

## 3. 그래픽

그래픽 VRAM은 32KB × 4 plane = 128KB의 planar 구성이다. 각 plane이 픽셀당 1비트를 담당하고, 4개 plane의 같은 비트 위치가 합쳐져 4비트 색 인덱스(16색)가 된다.

```
픽셀 N의 색 = (B비트N) | (R비트N << 1) | (G비트N << 2) | (I비트N << 3)
```

폰트 비트맵도 이 구조를 따른다. 글자가 단색이면 plane 한 개에만 데이터가 있는 1bpp이고, 컬러 글자면 4 plane 모두에 비트맵이 있다.

| 용도 | 크기 | 1글리프 데이터량 (1bpp) |
|---|---|---|
| 전각(한자) | 16×16 | 32바이트 (16행 × 2바이트) |
| ANK 반각 | 8×16 | 16바이트 |

식별법: 후보 데이터의 첫 32바이트를 1bpp 16×16으로 시각화해 글자 모양이 보이면 1bpp planar 폰트다. 한글은 정보량 때문에 16×16을 우선 검토한다. PC-98 게임 자체 폰트가 16×16 격자라면 한글 글리프를 같은 비트맵 포맷으로 변환할 수 있지만, 이것은 **디스크 저장 포맷**이 맞는다는 뜻일 뿐이다. 실제 표시는 인코딩 분기, 폰트 로딩량, 외자/사용자 폰트 등록 수, 활성 버퍼, 렌더러 경로를 별도 게이트로 확인해야 한다.

텍스트 출력 경로는 셋 중 하나(또는 혼합)다.

1. **텍스트 plane(TVRAM)** — SJIS 또는 JIS 코드를 TVRAM에 쓰면 시스템 폰트·외자 등록 경로가 글리프를 합성한다. 한글 1자 외자 등록 PoC가 통과해도 본문 대사 경로가 이 plane을 쓴다는 뜻은 아니다.
2. **자체 폰트 비트맵을 그래픽 plane에 직접 그리기** — RPG/AVG에서 자주 보이는 경로다. 한글 패치는 폰트 데이터 교체뿐 아니라 로더가 몇 글리프를 읽는지, 런타임 버퍼가 몇 글리프를 보유하는지, 드로 루틴이 어떤 인덱스 폭을 갖는지까지 확인한다.
3. **한자 ROM 또는 font hardware 글리프를 fetch해 그래픽 plane에 복사** — BIOS 호출, CG 윈도우, font/kanji hardware 포트 액세스가 단서다. PC-98 한자 ROM에는 한글이 없으므로 한글 패치는 해당 fetch 경로를 자체 한글 시트 lookup으로 바꾸거나, 렌더러 전체를 우회해야 한다.

## 4. 디스크 포맷

### 4.1 D88 컨테이너

D88은 물리 디스크의 트랙·섹터 구조를 보존하는 컨테이너다. 모든 정수는 little-endian.

디스크 헤더(선두 0x2A0 또는 0x2B0 바이트):

| 오프셋 | 크기 | 필드 |
|---|---|---|
| `0x000` | 16 | 디스크 이름 (`0x00` 종결) |
| `0x01A` | 1 | Write protect (`0x10`=보호) |
| `0x01B` | 1 | Media type (`0x20`=2HD 1.2MB) |
| `0x01C` | 4 | 디스크 총 크기 (헤더 포함) |
| `0x020` | 4×164 | 트랙 오프셋 표 (`0`=미포맷), 인덱스 = `cylinder × 2 + head` |

트랙 오프셋 표는 160개(헤더 0x2A0) 또는 164개(0x2B0) 두 변형이 있다. 파서는 첫 트랙 오프셋 값이 0x2A0인지 0x2B0인지 보고 표 길이를 판단한다.

각 섹터는 16바이트 헤더 + 데이터다: C(cylinder)/H(head)/R(sector ID)/N(size code, 실제 크기 = `128 << N`; 2HD 표준은 N=3 → 1024B), 트랙당 섹터 수(WORD), density, DDAM, FDC status, 실데이터 길이(WORD, 오프셋 0x0E). 보호 디스크는 N과 실데이터 길이를 일부러 다르게 두기도 하므로 두 필드 모두 그대로 보존한다.

### 4.2 HDM (raw 포맷)

HDM은 헤더가 전혀 없는 NEC raw 이미지다. 1024B 섹터가 트랙 0 헤드 0 섹터 1부터 평탄하게 연결된다. PC-98 2HD HDM에는 77 cylinder × 2 head × 8 sector × 1024B = 1,261,568B와 80 cylinder × 2 head × 8 sector × 1024B = 1,310,720B 같은 변형이 있다. geometry는 파일 크기와, FAT 디스크라면 BPB의 total sectors/bytes per sector로 판정한다. HDM→D88은 geometry가 확정된 raw 섹터에 합성 섹터 헤더를 붙이는 변환이고, D88→HDM은 비표준 정보(혼합 섹터 크기, 보호 패턴, 섹터 헤더 상태)를 잃을 수 있다. HDM으로 덤프되어 유통된다는 사실만으로 보호 패턴이나 타이틀별 디스크 검사가 없다고 단정하지 않는다.

### 4.3 재빌드 전 필수 검증

디스크 이미지를 읽고 다시 쓴 결과가 원본과 **byte-identical**해야 한다(무손실 round-trip). D88은 헤더의 디스크명·reserved·write protect, 트랙 오프셋 표의 0 위치, 섹터 헤더 전 필드, 트랙 내 섹터 순서(인터리빙), 트랙 데이터 영역의 물리 배치 순서를 모두 보존한다. HDM은 헤더 없는 raw이므로 판정한 geometry의 sector-linear byte stream이 그대로 serialize되는지를 확인한다. 대상 디스크 전수가 이 테스트를 통과한 뒤 다음 단계로 넘어간다.

### 4.4 FAT12 파일시스템

PC-98 부트 마커는 IBM PC의 `0x55 0xAA`와 다르다. 첫 섹터가 `EB ?? 90` 점프 + OEM 이름 + BPB로 시작하면 DOS FAT 디스크다. PC-98 FAT12의 함정은 **섹터당 1024바이트**(PC의 512가 아님)이며, 클러스터는 보통 1섹터다. BPB 핵심 필드: bytes per sector(`0x0B`), sectors per cluster(`0x0D`), number of FATs(`0x10`), root directory entries(`0x11`), sectors per FAT(`0x16`). 디렉토리 엔트리는 32바이트(파일명 8+3, 속성, first cluster `0x1A`, 크기 `0x1C`)이고 FAT 엔트리는 12비트가 3바이트에 2개씩 packed된다. 일부 게임 개발사는 자체 DOS 호환 미니 OS(예: Compile의 MEGDOS)로 부팅하는데, 파일시스템은 그대로 FAT12이므로 표준 FAT12 파서로 파일 추출이 가능하다.

## 5. 텍스트 엔진 패턴

PC-98 게임 텍스트는 거의 예외 없이 Shift_JIS다. 시스템 한자 ROM이 SJIS로 직접 인덱싱되고 동시대 도구체인이 SJIS를 가정하기 때문이다. SJIS 2바이트 문자의 1번째 바이트는 `0x81`–`0x9F` 또는 `0xE0`–`0xFC`, 2번째 바이트는 `0x40`–`0x7E` 또는 `0x80`–`0xFC`다.

스크립트 파일 구조 예:

```
0x0000-0x0220 : 헤더
0x0220-0x0620 : 포인터 테이블 (512 엔트리 × 2바이트 = 1KB)
0x0620-0x4910 : 텍스트 영역 1 — 메뉴/UI/회복/아이템 (~15,600바이트)
0x4910-       : 텍스트 영역 2 — 이벤트 dialog (포인터 테이블이 가리키는 영역)
```

포인터 테이블 식별법: 텍스트 영역 직전에 16비트 워드들이 군집해 있고, 값이 모두 텍스트 영역 범위 안에 들어가면(예: 512개 전부 0x4910–0x7C85 범위) 포인터 표다. 포인터 검증 없이 워드 군집 전체를 표로 오인하면 텍스트 영역을 포인터로 잘못 읽으므로, "전 엔트리가 valid 범위" 조건으로 표의 끝을 끊는다.

제어코드는 1바이트 코드가 아니라 **ASCII `$` + 1글자의 `$X` 패밀리**일 수 있다:

| 코드 | 의미 |
|---|---|
| `$e` | Wait (입력 대기) |
| `$r` | Newline (줄바꿈) |
| `$c` | PageClear (페이지 지움) |
| `$(` / `$)` | 따옴표 열기/닫기 |
| `$` + `0x00` | End (메시지 종결) |

같은 엔진 가족의 콘솔판이 `0xF8`(변수), `0xFC`(WAIT), `0xFD`(줄바꿈), `0xFE`(END), `0xFF`(PAGE) 같은 1바이트 제어코드를 쓰는 것과 대비된다. PC-98 원전이 ASCII 제어코드를 쓰고 콘솔 이식판이 1바이트 코드로 변형된 사례가 실재하므로, 양쪽 패턴을 모두 검색한다. 메시지 분류(대사/메뉴/시스템)에는 "제어코드 1개 이상 포함 = dialog" 같은 휴리스틱이 유효하다.

## 6. 한글 인코딩 설계 — free prefix 탐색법

게임이 SJIS를 그대로 쓴다면 한글 음절은 SJIS의 **미사용 lead byte(free prefix)** 에 2바이트로 끼워 넣는다. trail은 SJIS 규칙 그대로 `0x40`–`0x7E`(63개) + `0x80`–`0xFC`(125개) = **prefix당 188 값**을 쓴다.

```
prefix #1 + trail = 음절 #0–187
prefix #2 + trail = 음절 #188–375
prefix #3 + trail = 음절 #376–563
→ N prefix × 188 = (N×188) 음절
```

인코딩 공간 상한은 「확보한 free prefix 수 × trail 188」 공식의 출력이다. 전 코퍼스 기준 0회인 prefix가 몇 개냐에 따라 한글 코드 공간이 정해지고, prefix를 더 확보하면 188 단위로 늘어난다. 단 이 값은 실제 표시 가능한 글리프 수가 아니다. 최종 글리프 예산은 인코딩 공간, 디스크 저장량, 외자/사용자 폰트 등록 루프, 활성 폰트 버퍼, 렌더러 슬롯의 최솟값으로 산정한다(`references/strategy/font-strategy.md` 3절).

### 6.1 가설을 글리프 통계로 검증해 정정한 사례

free prefix 선정은 반드시 **전체 코퍼스 합산 통계**로 검증해야 한다. 한 사례에서 일어난 정정 과정:

1. **최초 가설**: 주 스크립트 파일 하나의 lead byte 분포만 sweep한 결과 `0xEB`–`0xFC` 구간이 전부 0회 → 디코더의 range 검사가 단순해지는 연속 3바이트 `0xFA`/`0xFB`/`0xFC`를 prefix로 채택했다.
2. **글리프 전수 통계로 반증**: 전 디스크 + 전 실행 파일을 합산해 SJIS pair 단위로 집계하자 `0xFA`/`0xFB`/`0xFC`가 모두 **cp932 외자(gaiji) 글리프**로 실사용 중이었다. 게임은 외자 영역(lead `0xED` 이후)에서 외자 글리프를 캐릭터 마크/UI 심볼 등으로 적극 쓰고 있었고, 한글 prefix가 이 영역을 잡으면 외자 글리프가 한글로 오해석되어 게임이 깨진다.
3. **정정**: 전 코퍼스에서 진짜 0회인 lead는 `0xEB`/`0xEC`/`0xEF` 셋뿐 → 이를 최종 prefix로 채택했다. prefix 수가 같으므로 음절 상한은 동일하게 유지된다. 단 연속 범위가 아니므로 디코더 분기가 단순 range 검사보다 약간 복잡해진다.

단일 파일 분포만 보면 false negative가 생긴다. prefix 후보는 **모든 디스크의 모든 텍스트·코드 영역을 합산한 글리프 사용 통계**로 0회임을 확인한 뒤에 확정한다.

### 6.2 산정 결과의 운용

확보한 prefix 수로 정해지는 인코딩 공간 상한은 KS X 1001 표준 한글 2,350자의 일부에 그칠 수 있다. 이 경우 번역 코퍼스의 음절 빈도를 집계해 상한 안에서 빈도순으로 동적 매핑한다. 이후 실제 빌드에서는 외자 등록 수·폰트 파일 로딩량·렌더러 경로까지 합친 글리프 공급 상한과 다시 맞대야 한다. 부족하면 먼저 공급 확장(추가 외자 row, 폰트 파일 성장, 로더/버퍼 확장)을 검토하고, 확정된 제약으로 남은 음절만 번역 단계에서 윤문하거나 자모 분해 출력으로 확장한다. 커버리지는 게임 분량과 문체에 따라 달라지므로 게임마다 다시 산정한다.

## 7. 재빌드 정책

번역 텍스트를 디스크에 다시 써넣는 정책은 세 가지다.

| 정책 | 방법 | 트레이드오프 |
|---|---|---|
| (a) 길이 보존 | 각 메시지를 원본 바이트 길이 안에 맞춤. 길면 자르거나 `$r`로 분할 | 포인터 표를 건드리지 않아 안전. 번역 표현력 제약 |
| (b) 포인터 재배치 | 텍스트 영역을 통째로 재배열하고 포인터 표 전 엔트리 재계산 | 길이 자유. 포인터 표 + 텍스트 영역 양쪽 갱신 필요, 접미사 공유 최적화가 있으면 보존/해제 결정 필요. 파일 크기가 늘면 FAT 클러스터 체인까지 영향 |
| (c) 하이브리드 | 고정 폭 UI(메뉴/아이템명)는 (a), 가변 길이 dialog는 (b) | 영역별 위험·이득에 맞춘 절충. 실전 권장 |

한국어는 일본어보다 같은 내용의 바이트 수가 다른 경우가 많아 순수 (a)는 빠듯할 수 있다. 코드가 길이를 하드코딩해 참조하는 메뉴/UI 영역은 (a)로 묶고, 포인터 테이블이 명시적으로 가리키는 dialog 영역은 (b)로 푸는 (c)를 우선 검토한다. 어느 정책이든 재빌드 후 디스크 이미지가 §4.3의 round-trip 인프라 위에서 생성되어야 한다.

## 8. 검증

| 환경 | 역할 |
|---|---|
| **np2debug** (Neko Project II 디버그 빌드) | 대화형 분석 환경. 단계실행, 코드/메모리 브레이크포인트, ASM 뷰어, SJIS 메모리 뷰어, 스택 뷰어 |
| **MAME / emucap** (`pc9801` 계열 드라이버) | 자동화. 디버거 + Lua 스크립팅 + 트레이스 로그로 회귀 테스트 |
| **Neko Project 21/W** | 최종 QA. 일반 사용자 환경에서 패치 동작 확인 |

대화형 디버거 표준 절차:

1. **출력 함수 식별** — 메시지 윈도우가 열리기 직전에 일시정지, 그래픽 VRAM(`0xA8000`)을 관찰하며 프레임 전진, 변화 직후의 CS:IP에서 호출 스택을 거슬러 함수 진입점을 찾는다.
2. **텍스트 RAM 위치 식별** — 화면 첫 글자의 SJIS 바이트(예: "ま" = `0x82 0xDC`)를 RAM 전체에서 검색, 다음 글자로 후보를 좁힌다.
3. **디스크→RAM 매핑** — 그 주소가 부팅 직후 비어 있으면 `INT 1Bh`에 브레이크포인트를 걸어 어느 트랙·섹터가 어느 주소로 적재되는지 표를 만든다.

패치 빌드 후 자동 회귀: 미리 녹화한 입력 시퀀스로 진행 → 정해진 프레임의 VRAM 캡처 → 기준 스크린샷과 비교해 한글 글리프 렌더링 깨짐을 잡는다. MAME은 machine별로 노출되는 플로피 드라이브 수와 HDD 컨트롤러 구성이 다르므로, 실행 전 대상 machine의 drive slot과 launcher/status 출력을 확인한다. 3매체 흐름이 필요한 게임을 2드라이브 machine에서 검증하려면 부팅 디스크 재팩, 임시 파일 삽입, 디스크 스왑, HDD/HDI 경로 중 하나를 프로젝트 문서에서 별도로 설계한다.

PC-98 검증에서 특히 주의할 점은 출력 경로 분리다. 부트 프롬프트나 에러 화면에서 text-plane 외자 1자가 보였다고 해서, 본문 대사·전투 메시지·메뉴가 같은 경로를 쓴다고 결론내리지 않는다. TVRAM, GVRAM, decoded overlay, font/kanji hardware 호출을 각각 추적해 실제 본문 renderer가 어느 경로인지 확인한다.

### 실기 구동 경로

수단은 세 갈래다.

- **플로피 이미지 → 실디스크**: 이미지를 실제 플로피로 굽는다. 노후 플로피·드라이브라 신뢰성이 낮다.
- **GOTEK + FlashFloppy**: FDI·HDM을 직접 지원한다. raw IMG는 `host=pc98` 설정이 필요하다(D88 직접 지원 여부는 확인 필요).
- **HDD 대체**: CF→IDE 변환, SCSI 경로는 BlueSCSI 등으로 대체한다.

제약 — IDE BIOS의 용량 한계가 있다(A-Mate 등은 약 540MB, 후기 기종은 4.3GB까지 — 모델별 확인 필요). GOTEK 핀아웃은 기종별로 다르고, 실기 입수성 자체가 어렵다.

**빌드 포맷에의 영향**: **이미지 포맷이 GOTEK 호환선(FDI/HDM)에 맞아야** 실기 변환이 매끄럽다. HDM/FDI를 1차 배포 포맷으로 두면 실기가 직접 인식하지만, D88 위주로 내면 변환이 한 단계 더 든다. HDD 설치형은 HDI로 만들어 SCSI·CF로 배포한다(7절 재빌드 정책에서 배포 포맷을 이 호환선에 맞춰 정한다).

함정 — 포맷 다양성(FDI/HDM/D88/NHD/HDI 등)이 이 플랫폼의 큰 함정이다. 어느 포맷이 어느 솔루션에서 직접 인식되는지 명시하지 않으면 사용자가 막힌다. IDE 540MB 벽도 주의한다. 실기 검증 기기 확보 난이도가 8종 중 가장 높은 데다, MiSTer PC-98 코어가 미완성이라 에뮬레이터와 실기 사이를 메울 성숙한 FPGA 중간 검증 수단이 사실상 없어, MAME 계열 정확 에뮬레이터가 검증의 중심이 된다.

## 9. 사례 요약 — PC-98 마도물어 1·2·3 합본

- **대상**: 합본 재발매판 7장(HDM, 게임별 System+Sampling 쌍 + 공유 Data 1장) + 1편 단독판 4장(D88, 영문 팬 패치 포함). HDM/D88 모두 geometry와 BPB를 실측해 처리.
- **파일시스템**: Compile MEGDOS(DOS 호환 미니 OS) 부팅 + FAT12. 표준 FAT12 파서로 파일 추출 가능.
- **폰트**: 게임 자체 폰트 파일(16×16 1bpp 격자) + 시스템 한자 ROM/외자 경로 병용. 한글은 비트맵 포맷 변환, 외자 등록 루프 확장, prefix lookup, 실제 메뉴/본문 renderer 표시를 별도 게이트로 확인.
- **텍스트**: SJIS. 스크립트 파일은 헤더 + 512 엔트리 포인터 테이블(0x0220–0x0620) + 텍스트 영역 2개(0x0620–0x4910 메뉴/UI, 0x4910+ 이벤트 dialog). 제어코드는 ASCII `$X` 패밀리(`$e` Wait, `$r` Newline, `$c` PageClear, `$(`/`$)` 따옴표, `$`+`0x00` End).
- **한글 인코딩**: free prefix `0xEB`/`0xEC`/`0xEF` × trail 188. 최초 가설 `0xFA`–`0xFC`는 글리프 전수 통계에서 외자 글리프 점유가 확인되어 폐기.
- **분석 지렛대**: 1편 단독판의 일어판↔영문 패치판 diff가 텍스트 인코딩·엔진의 일차 단서. 영문 패치가 System disk만 변경했다는 사실에서 텍스트가 System disk에 집중됨을 역산.
- **검증**: HDM/D88 round-trip byte-identical 확인 후 대화형 디버거와 MAME/emucap으로 부팅·텍스트 표시 검증, 동일 디스크의 복수 덤프(alt dump) 간 일치 비교.

같은 Compile/마도물어 계열이라도 이 구조를 그대로 이식하지 않는다. 후속작이나 별도 합본은 `MENUDAT*.BIN`이 아닌 overlay·chapter DAT·압축 테이블·graphics renderer 경로를 쓸 수 있으므로, 포인터 표와 제어코드는 새 게임에서 다시 식별한다.

## 10. HDI 하드디스크 이미지와 FAT12/FAT16

PC-98의 `.hdi`는 단순한 플로피 raw 이미지일 수도 있고, 헤더·IPL·파티션 테이블을 가진 하드디스크 이미지일 수도 있다. 확장자만 보고 FAT12 또는 고정 섹터 크기를 가정하지 않는다.

대표적인 하드디스크 HDI 배치는 다음과 같다.

```
HDI 헤더 → 섹터 0 IPL → 섹터 1 PC-98 파티션 테이블 → 파티션 안 DOS 부트섹터 → FAT 볼륨
```

- HDI 헤더에는 헤더 크기, 데이터 크기, 섹터 크기, 헤드·실린더 수가 들어갈 수 있다. 256바이트 물리 섹터와 2,048바이트 FAT 논리 섹터처럼 계층별 섹터 크기가 다를 수 있다.
- PC-98 파티션 테이블은 보통 32바이트 엔트리로 구성되며 파티션 종류, IPL CHS, 시작·끝 CHS, 이름을 담는다.
- DOS 부트섹터의 BPB와 클러스터 수로 FAT 종류를 판정한다. 데이터 클러스터 수가 4,085 미만이면 FAT12, 그 이상이면 FAT16을 우선 의심한다. EOC 기준도 FAT12 `0xFF8`, FAT16 `0xFFF8`로 다르다.
- FAT16 볼륨을 FAT12로 읽으면 실제 손상이 없어도 “클러스터 체인 순환” 같은 오류가 날 수 있다. 파일시스템 오류가 보이면 이미지 손상 판정보다 먼저 헤더 크기, 파티션 시작점, bytes per sector, FAT 폭을 다시 확인한다.

부트섹터 위치가 불명확하면 이미지 앞부분의 정렬된 후보 오프셋을 순회하며 BPB 필드 타당성, `EB ?? 90`/`E9` 점프, `FAT12`/`FAT16` 문자열, 루트 디렉터리의 정상 8.3 엔트리를 함께 점수화한다. 단, 자동 탐지는 후보 생성 수단일 뿐이며 최종 채택한 파티션 시작점과 BPB 값은 수동 파싱 결과로 교차 검증한다.

### 10.1 파일 교체와 클러스터 확장

번역·재압축으로 파일이 커지면 파일 데이터만 덮어써서는 안 된다. 필요한 만큼 빈 클러스터를 연결하고 다음 항목을 함께 갱신한다.

1. 파일의 클러스터 체인과 EOC
2. 모든 FAT 사본
3. 디렉터리 엔트리의 시작 클러스터와 파일 크기
4. 컨테이너 내부의 엔트리 오프셋·크기 표

세이브 파일이 같은 볼륨에 생성되는 게임은 빈 클러스터를 모두 소비하면 진행 중 저장이 실패할 수 있다. 빌드 전에 원본 빈 공간을 측정하고, 패치 후에도 프로젝트가 정한 수의 빈 클러스터를 예약한다. 파일 축소 시 기존 체인을 유지하는 구현도 가능하지만, 이 정책을 round-trip 및 무결성 보고서에 명시한다.

## 11. 텍스트 위치 탐색 절차

전체 이미지를 넓게 Shift_JIS 스캔하는 방식은 첫 후보 수집에는 쓸 수 있지만 최종 추출 방식으로 삼지 않는다. DOS 시스템 파일, 드라이버, 그래픽, 압축 데이터에서 우연한 일본어 바이트열이 대량으로 검출되기 때문이다.

권장 순서는 다음과 같다.

1. 이미지·파티션·FAT 종류를 확정하고 파일 목록을 만든다.
2. 파일별 문자열 수와 자연문 비율을 집계해 후보 파일을 좁힌다.
3. 컨테이너 또는 압축 시그니처를 검사한다. “알 수 없는 raw”는 무압축이라는 뜻이 아니라 독자 인코딩·그래픽·미지 압축일 수 있다.
4. 실행 파일은 자연문이 모인 구간만 scan window로 고정한다.
5. 메뉴·화자명처럼 1~3글자인 문자열은 별도 저임계 스캔으로 찾고, 넓은 저임계 결과를 그대로 번역 목록에 넣지 않는다.
6. 추출 CSV와 전체 후보를 다시 대조해 미커버 문자열을 찾는다.

오탐의 전형적인 신호는 같은 희귀 한자의 반복, 문장 구조가 없는 글리프 나열, 앞뒤 문맥이 이어지지 않는 후보, 시스템 실행 파일에 집중된 결과다. 후보 개수가 늘었다는 사실은 텍스트를 더 찾았다는 증거가 아니다.

### 11.1 화면의 깨진 한글로 누락 원문 찾기

한글 폰트가 기존 JIS 한자 셀을 덮는 방식에서는 미번역 한자가 의미 없는 한글로 보인다. 이때 깨진 한글의 EUC-KR 바이트 `(b0, b1)`에서 각각 `0x80`을 빼면 원래 JIS 행·셀을 복원할 수 있다.

복원한 일본어 문자열을 다음 순서로 추적한다.

- 추출 최소 길이 때문에 빠진 짧은 라벨·단독 한자인가
- 문자열 앞의 아이콘·색상·포인터 escape 때문에 스캐너가 시작점을 놓쳤는가
- 같은 문자열의 복사본이 여러 파일 또는 여러 테이블에 존재하는가
- 패킹 EXE, 미해독 컨테이너, 세이브 데이터, 런타임 생성 문자열인가

읽을 수 있는 가타카나와 깨진 한자가 한 화면에 함께 보이면 인코딩 전체가 잘못된 것보다 해당 한자 문자열이 미번역으로 남았을 가능성을 먼저 확인한다.

## 12. Shift_JIS 밖의 텍스트 표현

§5의 Shift_JIS 규칙은 기본 가설이지 절대 규칙이 아니다. 실제 PC-98 게임에서는 다음 변형이 확인된다.

| 표현 | 식별 단서 | 재삽입 시 핵심 |
|---|---|---|
| 고정 2바이트 Shift_JIS 리더 | 반각 ASCII 삽입 뒤 정렬·종료자 인식이 깨짐 | ASCII를 전각화하고 홀수 바이트가 생기지 않게 한다 |
| 독자 16비트 JIS 레코드 | 선두 u16 오프셋 표, `(low, high)` 문자, `0x00` 종료 | JIS↔SJIS 변환 후 오프셋 표 전체를 재계산한다 |
| 단바이트 가나 치환 | 히라가나·탁음이 일정한 1바이트 범위에 밀집 | 확정된 치환표만 사용하고 미확정 가타카나는 화면 대조한다 |
| 제어코드 혼합 SJIS | 문자열 사이에 색상·대기·이름 삽입 바이트 | 제어 바이트를 `{XX}` 같은 왕복 가능한 토큰으로 보존한다 |
| gaiji 포함 JIS | cp932로 디코드되지 않지만 유효 JIS 행·셀 | 레코드를 버리지 말고 `⟦RRCC⟧` 같은 가역 토큰으로 보존한다 |

독자 레코드 포맷의 첫 워드가 첫 레코드 오프셋이면 `첫 오프셋 ÷ 2`가 포인터 엔트리 수인 경우가 많다. 단 이 역시 후보 규칙이므로 모든 오프셋의 단조 증가, 파일 경계, 레코드 종료 토큰을 함께 검증한다.

고정 2바이트 리더는 바이트 수준 audit만으로 판별하기 어렵다. 원문에 없던 반각 ASCII 한 글자를 넣은 실험에서 게임이 멈추거나 뒤 제어코드를 놓친다면 2바이트 정렬 의존성을 의심한다. 이 경로에서는 반각 공백도 무조건 안전하지 않으므로 원문과 렌더러 동작을 확인해 전각 공백 `0x8140` 사용 여부를 정한다.

## 13. 컨테이너·압축·패킹 실행 파일

PC-98 게임은 텍스트가 파일시스템의 평문 파일에 바로 있지 않고 다음처럼 중첩될 수 있다.

```
HDI/FAT → 아카이브 → 압축 항목 → 스크립트 VM 레코드 → 표시 문자열
```

각 계층은 “교체 없이 parse→build했을 때 byte-identical”인 round-trip을 먼저 통과시킨다. 항목 크기 변경을 허용한다면 안쪽 스크립트부터 압축 크기, 아카이브 오프셋, FAT 파일 크기와 클러스터 체인까지 바깥 방향으로 재계산한다. 해독하지 못한 엔트리는 원본 바이트를 그대로 보존하고 번역 가능 범위에서 명시적으로 제외한다.

### 13.1 LZEXE 계열

LZEXE로 패킹된 DOS 실행 파일은 정적으로 언팩한 EXE가 논리적으로 같은 프로그램 이미지를 담더라도 원래처럼 실행된다고 보장할 수 없다. 게임이 자가압축 로더가 만든 초기 메모리 상태에 의존할 수 있으므로 최종 배포본은 원래 패킹 형식으로 재조립하는 것을 우선한다.

16비트 자가압축기는 출력 포인터가 `ES:DI`로 움직인다. 64KB 경계를 넘는 스트림에 세그먼트 전환 마커가 없으면 평면 디코더에서는 정상인데 실제 로더에서는 깨질 수 있다. 재패킹 검증은 최소한 다음을 모두 통과해야 한다.

1. 평면 디코더로 원문 round-trip
2. `ES:DI`와 세그먼트 마커를 모사한 16비트 디코더로 round-trip
3. 새 압축 스트림이 원본 압축 영역과 메모리 여유 한도 안에 들어감
4. 번역하지 않은 재패킹본이 에뮬레이터에서 원본과 동일하게 부팅·진행됨

## 14. 재삽입 전에 확정할 텍스트 VM 불변식

문자열을 추출했다는 사실만으로 재삽입 규칙이 정해지지 않는다. 빌드 전에 다음 세 질문에 답한다.

1. **문자 폭** — 1바이트와 2바이트를 혼용하는가, 모든 표시 문자를 2바이트로 읽는가?
2. **주소 방식** — NUL 종료 순차 스캔, 포인터 테이블, 레코드 상대 오프셋, 컴파일된 바이트코드의 절대 오프셋 중 무엇인가?
3. **종료 조건** — `0x00`, 길이 필드, 구분자, 별도 제어코드 중 실제 렌더러가 멈추는 조건은 무엇인가?

### 14.1 절대 오프셋과 스팬 정렬

컴파일된 스크립트가 문자열 시작점을 절대 u16 오프셋으로 참조하면 파일 전체 크기만 보존해도 충분하지 않다. 엔트리 시작과 각 메시지 구분자 뒤를 앵커로 잡고, **모든 앵커의 바이트 오프셋을 원문과 동일하게** 유지해야 한다. 앵커 사이 스팬 안에서는 번역 길이를 조정할 수 있지만 다음 앵커까지의 총 바이트 예산은 고정된다.

남는 공간은 렌더러가 안전하게 무시하거나 공백으로 그리는 값으로 뒤쪽 패딩한다. 전각 문자 중심 스팬에서 홀수 1바이트가 남으면 그 위치와 의미를 별도 검증한다. 앞쪽 패딩은 화면상 들여쓰기로 보일 수 있으므로 원문 서식이 아니라면 뒤로 보낸다.

### 14.2 종료자와 공백을 추측하지 않기

원본 데이터에서 메시지 사이에 `0x20`이 보인다고 렌더러가 그 값에서 멈춘다고 단정하지 않는다. 실제 종료자가 `0x00`뿐이면 `0x20` 뒤의 다음 문자열까지 화면에 흘러나올 수 있다. 반대로 모든 `0x20`을 일괄 `0x00`으로 바꾸면 가격표와 정렬용 ASCII 공백이 깨진다.

구분자 변환은 주변 바이트가 유효한 2바이트 문자 경계인지, 실제 ASCII 필드인지, 다음 앵커가 어디인지까지 판정해 제한적으로 수행한다. 종료 조건은 원본·패치본 메모리 트레이스와 실제 화면 진행으로 확정한다.

### 14.3 화면 폭과 런타임 데이터

- 자동 줄바꿈이 없는 대사창은 원본 각 줄의 최대 셀 수를 측정하고 번역문을 그 이하로 직접 reflow한다. 제어 토큰과 gaiji 토큰은 실제 표시 셀 수로 계산한다.
- printf 지정자(`%s`, `%2d`, `%04X` 등), 색상 코드, 아이콘 코드, 플레이어명 삽입 코드는 번역문에서도 바이트 단위로 보존한다.
- 같은 이름·제목이 여러 테이블에 복제되어 있으면 표시 경로별 사본을 모두 찾는다.
- 이름이 세이브 데이터에 합류 시점 값으로 복사되는 게임은 새 게임과 기존 세이브의 결과가 다를 수 있다. 실행 파일의 원본 테이블을 고쳐도 기존 세이브의 값은 남을 수 있으므로 별도 호환 정책을 기록한다.
- PC-98 DOS 콘솔에서 LF(`0x0A`)는 열을 유지한 채 줄만 내릴 수 있다. CRLF 문자열을 CSV로 다룰 때는 필드 안의 `0x0D 0x0A`가 newline 정규화로 `0x0A` 하나가 되지 않게 원시 newline 보존 모드로 읽고 쓴다.

## 15. 검증 게이트와 완료 기준

검증은 서로 다른 실패를 잡는 층으로 나눈다.

| 게이트 | 확인 항목 | 잡지 못하는 대표 문제 |
|---|---|---|
| 컨테이너 round-trip | 무수정 parse→build의 byte-identical | 게임 화면 의미 |
| 빌드 무결성 | 패치 대상 밖 파일·섹터 불변, FAT/오프셋/크기 일관성 | 잘못 번역한 문자열 |
| 패치 audit | CSV 기대 바이트와 이미지 실제 바이트 일치, 원본 바이트 대조 | 문자 정렬, 종료자 의미, 창 폭 |
| 에뮬레이터 디버깅 | 실제 로더·렌더러·디스크 읽기 경로 | 실기 고유 타이밍·장치 차이 |
| 플레이스루 QA | 메뉴, 대사, 전투, 저장·불러오기, 디스크 교환 | 미방문 분기 |
| 실기/최종 사용자 환경 | 배포 이미지·폰트·장치 호환성 | 아직 실행하지 않은 콘텐츠 |

`audit 불일치 0`은 “의도한 바이트가 들어갔다”는 증거이지 “게임이 올바르게 표시하고 진행한다”는 증거가 아니다. 고정 2바이트 정렬, 절대 오프셋, 메시지 흘러넘침, 창 밖 출력, 반각 전용 패널은 모두 audit 뒤의 실행 검증에서만 드러날 수 있다.

최소 회귀 세트에는 다음 장면을 포함한다.

- 부팅·DOS 콘솔 메시지와 타이틀
- 짧은 메뉴·화자명·단독 한자 라벨
- 가장 긴 대사와 페이지 전환
- 이름·성별·숫자·아이템 같은 런타임 삽입 문자열
- 전투·상태창처럼 본문과 다른 렌더러를 쓰는 화면
- 저장·불러오기 및 기존 세이브/새 게임 차이
- 파일 성장 뒤의 빈 공간과 세이브 생성

## 16. 새 PC-98 타이틀 조사 체크리스트

1. 원본 이미지 해시와 매체 구성을 기록한다.
2. HDI/D88/HDM 구조, 파티션 시작점, 논리 섹터 크기, FAT 종류를 확정한다.
3. 모든 컨테이너의 무수정 byte-identical round-trip을 만든다.
4. 파일별 텍스트 분포를 조사하고 자연문 구간만 추출 범위로 고정한다.
5. 알려진 압축 감지 실패를 “무압축”으로 오판하지 않고 독자 포맷 가능성을 조사한다.
6. 짧은 라벨용 저임계 스캔과 전체 코퍼스 커버리지 대조를 별도로 수행한다.
7. 문자 폭, 문자열 주소 방식, 종료자를 PoC와 디버거로 확정한다.
8. 제어코드·gaiji·printf 지정자를 가역 토큰으로 보존한다.
9. 인코딩 공간뿐 아니라 디스크·로더·버퍼·렌더러를 합친 실제 글리프 상한을 계산한다.
10. 고정 길이, 포인터 재배치, 스팬 정렬, 컨테이너 재조립 중 맞는 빌드 정책을 선택한다.
11. 원본 대조 → 빌드 무결성 → audit → 에뮬레이터 플레이 순서로 검증한다.
12. 실패한 가설과 미해독 영역, 기존 세이브·반각 패널 같은 잔여 제약을 배포 문서에 남긴다.
