# PS1 (PlayStation) 한글 패치 참조

## 1. 플랫폼 개요

- **CPU**: MIPS R3000A 33MHz, 리틀엔디언. 하드웨어 인터록이 없어 load delay slot이 존재한다. `lw` 직후 1 instruction에서는 로드 결과를 사용할 수 없다 — 이전 레지스터 값이 그대로 읽힌다. branch delay slot도 항상 실행된다.
- **GPU**: 1MB VRAM. 글리프는 LoadImage로 VRAM에 업로드해 스프라이트/텍스처로 그린다. 4bpp/8bpp/16bpp(ABGR1555) 텍스처를 쓴다.
- **CD-ROM**: Mode2/2352 섹터(유저 데이터 2048B), ISO 9660 파일 시스템. XA 오디오와 무비 스트리밍이 같은 드라이브를 공유하므로 패치 코드가 CD를 직접 읽으면 스트리밍과 충돌할 수 있다.
- **RAM**: 메인 2MB. 한글 폰트를 올릴 공간은 EXE 미참조 영역, 디컴프레서 출력 범위의 제로 런(code cave), 디스크 끝 추가 섹터에서 확보한다.
- **실행 파일**: PSX-EXE 포맷. 헤더에 Entry Point, Load Address(통상 0x80010000), text_size, Initial SP가 있다. RAM 주소 → 파일 오프셋 변환은 `file_offset = (ram_addr - load_addr) + 0x800` (0x800 = 2KB 헤더).

## 2. 메모리 맵

| 영역 | 주소 범위 | 캐시 |
|------|-----------|------|
| KSEG0 | 0x80000000~0x9FFFFFFF | I-cache + D-cache |
| KSEG1 | 0xA0000000~0xBFFFFFFF | 없음 (항상 RAM 직접) |

KSEG0와 KSEG1은 같은 물리 RAM의 별칭이다. RAM 포인터의 물리 주소는 상위 세그먼트 비트를 제거해 얻고, 같은 물리 주소에 KSEG0 또는 KSEG1 세그먼트 비트를 붙여 캐시 사용 여부를 고른다. 하드웨어 레지스터는 KSEG1으로 접근한다 (CD 레지스터 `0xBF801800` = 물리 `0x1F801800`).

### I-cache stale 문제와 KSEG1 실행

부트 디컴프레서가 훅 코드가 놓일 RAM 범위를 먼저 실행하거나 덮은 뒤 EXE가 그 범위를 다시 적재하면, RAM 바이트와 I-cache의 명령어가 달라질 수 있다. 이때 RAM에는 패치 코드가 보여도 훅 분기는 이전 명령어를 실행한다. 캐시 플러시 루틴 자체가 같은 오염 범위에 들어가는지도 확인한다.

해결책은 **훅 코드를 KSEG1 주소로 실행**하는 것이다. KSEG1은 I-cache를 완전히 우회한다. 원래 JAL 사이트를 트램폴린으로 교체한다:

```
lui  $at, upper16(hook_kseg1)
ori  $at, $at, lower16(hook_kseg1)
jalr $at                ; uncached 실행
(delay slot)            ; 교체로 밀려난 원본 명령 1개
```

트램폴린이 I-cache 라인(16B) 2개에 걸치면 라인별로 stale/fresh가 갈려 반쪽 실행이 일어난다. **패치를 1개 캐시 라인 안에 들어가는 3 instruction으로 줄이고**, 밀려난 원본 명령은 훅 프롤로그에서 보상 실행한다. 적용 전 JAL 사이트 주소를 확인하라 — `addr % 16 <= 4`여야 12B가 한 라인에 들어간다.

### Load delay slot 버그 패턴

```mips
lw   v1, 0(v1)          ; 로드 시작
nop                      ; load delay slot — 반드시 1 cycle 대기
bnez v1, target          ; 이제 올바른 값
```

`nop` 없이 `lw` 직후 `bnez`를 쓰면 v1에 아직 주소(non-zero)가 남아 있어 분기가 항상 성립한다(taken). 명령 단위 스텝 실행으로 확인 가능한 전형적 버그다.

## 3. 폰트

### BIOS 폰트 (Krom2RawAdd)

PS1 BIOS는 ROM에 SJIS 전체 글리프를 내장하고 BIOS 함수로 노출한다:

- **B(0x51) Krom2RawAdd**: SJIS 코드 → 15×15 1bpp 글리프 데이터 포인터 반환. 실패 시 0xFFFFFFFF.

글리프 포맷은 15 halfword(30바이트)/글리프. 각 halfword의 bit 15..1이 15픽셀(MSB = 왼쪽), bit 0 = 0. BIOS 폰트를 쓰는 게임은 이 1bpp 글리프를 자체 변환 루틴으로 VRAM 텍스처에 올린다. 변환 방식(1bpp→4bpp 룩업, 캐시 슬롯 수, LoadImage 배치)은 게임별 렌더러에서 실측한다.

**활용 가능성**: 게임이 BIOS 폰트를 쓰고 호출 지점이 공통 경로로 수렴한다면 텍스트 엔진 전체(u16 파싱, 1bpp→4bpp 변환, VRAM 업로드, 캐시)를 그대로 두고 Krom2RawAdd 호출부만 훅할 수 있다. 한글 코드 범위면 자체 폰트 포인터를 반환하고, 그 외는 원래 BIOS로 폴스루한다. 호출 경로가 여러 개면 경로별 누락을 따로 처리한다.

**한계**:
- 15×15 1bpp 고정. 복잡한 한글 음절은 가독성이 한계에 가깝다. 부족하면 1bpp를 우회해 4bpp를 직접 공급하는 더 큰 훅이 필요하다.
- BIOS 함수 번호는 자료마다, BIOS 리비전마다 다르게 적혀 있다. 어떤 게임은 B(0x51)로 호출하고, 다른 자료·환경에서는 B(0x58) 등으로 적기도 한다. 어느 한쪽을 "틀린 값"으로 단정해 후보에서 빼지 말고, 자기 게임이 실제로 호출하는 함수 번호를 디스어셈블·디버거로 실측해 확정한다.
- 게임에 따라 폰트 렌더 경로가 여럿일 수 있다. 호출 사이트를 전수 확인해, 프리캐시·UI 등 별도 경로의 글리프가 주 훅에서 누락되지 않게 한다.

### 자체 폰트 경로

TTF에서 15×15 1bpp로 렌더링해 BIOS 출력 포맷과 동일하게 만든다(글리프당 30B). 총 용량은 글리프 수 × 30B로 계산한다. 적재 위치 선택지:

1. **EXE 확장**: 헤더 text_size를 늘려 미참조 영역에 폰트+훅을 포함. 로드 시 자동 적재, 추가 I/O 불필요. 단, 부트 디컴프레서가 해당 영역을 덮는 게임에서는 못 쓴다.
2. **디스크 여유 영역 + lazy load**: 폰트를 검증된 미사용 extent나 이미지 끝의 신규 섹터에 두고 첫 글리프 렌더링 전에 RAM으로 읽는다. 디컴프레서 간섭을 피할 수 있지만, 선택한 LBA·읽기 크기·목적지 버퍼·CD 상태 복원까지 함께 검증해야 한다(§7).

프리렌더 텍스처(BTX 등)에 박힌 UI 문자열은 폰트 훅으로 해결되지 않는다 — 텍스처 자체를 한글로 다시 그려 교체해야 한다.

## 4. 아카이브 포맷 (VDD)

컴파일(Compile)계 일부 PS1 게임에서 확인된 역할별 컨테이너다. 스크립트·그래픽·맵·사운드·패딩을 서로 다른 VDD에 나누는 사례가 있지만, 실제 파일명과 역할 대응은 타이틀별 디렉토리와 참조 코드를 통해 확정한다.

```
오프셋 0x00: u32 LE = 엔트리 수
각 엔트리 (24 바이트):
  [0:16]  파일명 (ASCII, null-padded)
  [16:20] 섹터 오프셋 (u32 LE) — ×2048 = 아카이브 내 바이트 오프셋
  [20:24] 파일 크기 (u32 LE)
```

파일 데이터 시작 섹터는 엔트리 테이블 크기와 정렬을 통해 실측한다. 내부 파일에 CNX v2가 확인되면 매직·해제 크기·스트림 종결 방식을 먼저 검증하고, 알고리즘 전체 사양은 같은 압축을 다루는 `references/platforms/saturn.md` §5를 따른다.

**재계산**: 내부 파일 크기가 변하면 후속 엔트리의 섹터 오프셋이 전부 밀린다. 수정된 파일을 재압축 → 2048B 섹터 정렬로 재배치 → 엔트리 테이블(섹터 오프셋 + 크기) 재기록 → VDD 풀 리빌드 순서다. EXE에 별도 파일 디스크립터나 예약 엔트리가 있으면 아카이브 배치와 함께 갱신한다. 디스크립터의 크기와 엔트리 수는 타이틀별로 실측한다.

## 5. 텍스트 엔진 패턴

### 인코딩과 바이트 순서

이하는 한 사례의 텍스트 엔진 실측 구조다. 새 게임은 1바이트 경로 유무·바이트 순서를 먼저 실측한다.

한 사례의 본문은 표준 Shift-JIS를 **BE 원시 바이트 [lead, trail]**로 저장했다. 엔진은 16비트 리틀엔디언 로드로 바이트스왑된 값을 얻고, 글리프 렌더러가 다시 스왑해 BIOS 폰트 함수에 넘겼다. 이런 구조에서는 인코더 출력 순서와 훅의 비교 시점이 다르므로, 원문 문자와 한글 양쪽을 왕복시켜 바이트 순서를 확정한다.

이 엔진은 2바이트 단위로만 전진했다. 1바이트 문자 경로가 없다면 ASCII도 엔진이 소비하는 2바이트 표현으로 바꾸고, 고정길이 패딩은 실측한 공백 코드로 채운다. 1바이트 입력이나 임의의 0 패딩은 다음 코드와 합쳐져 스트림 정렬을 깨뜨릴 수 있다.

### 제어 코드 (사례 패턴)

한 사례는 16비트 값의 특정 상위 대역을 제어 코드로 분기하고, 파일에는 리틀엔디언 순서로 저장했다. 정확한 코드값·의미·파라미터 길이는 타이틀 로컬이므로 디스패치 테이블과 각 핸들러의 포인터 증가량으로 다시 확정한다.

추출/재삽입 시에는 종료자와 trailing 제어 시퀀스를 raw 토큰으로 보존하고, 절단이 필요하면 종료자 공간을 먼저 확보한다. 제어 코드 뒤의 RAM 주소·좌표·타이밍 인자는 텍스트가 아니므로 파라미터 길이에 따라 건너뛴다. 코드값별 의미표와 실제 바이트열은 프로젝트 문서가 소유한다.

### SEQ 포인터 테이블 (스토리 스크립트 — 한 사례의 포맷)

스토리 SEQ는 RAM에 고정 베이스로 적재되는 로더블 모듈이다:

```
[모듈 헤더와 RAM 포인터]
[이벤트 디스패치/인덱스 테이블]
[절대 RAM 포인터 테이블]
[연속 배치된 텍스트 데이터]
[정렬 패딩과 MIPS 초기화 코드]
```

- 헤더 포인터와 파일 내 알려진 위치의 관계로 모듈 RAM 베이스를 유도하고, 모든 포인터 타겟을 파일 오프셋으로 역변환해 검증한다.
- 메시지가 갭 없이 연속되면 한 엔트리의 성장도 후속 포인터 전부를 이동시킨다. 인덱스 기반 디스패치 테이블은 타겟 포인터와 분리해 다룬다.
- 텍스트 뒤 초기화 코드가 절대 주소를 하드코딩하면 텍스트 성장 시 코드 블록과 내부 주소 상수를 함께 재배치한다. 블록 크기·정렬·상수 위치는 프로젝트 분석 결과가 소유한다.

### VM 바이트코드 SEQ (메뉴/시스템)

사례의 메뉴 계열 SEQ는 바이트코드·포인터 테이블·텍스트가 인터리브된 구조다. 텍스트 영역에 RAM 포인터 참조가 광범위하게 산재해 포인터 전수 보정 비용이 크므로 **고정길이 교체**(전각 공백 패딩, 초과분 절단)를 우선 검토한다. 파일 끝에 위치한 영역(설명 텍스트 등)은 테일 코드 재배치 조건을 만족하면 성장시킬 수 있다. 추출은 영역 경계를 수동 지정해 바이트코드 오인을 차단한다.

## 6. 한글 매핑 설계 사례

**사례 전략: SJIS 코드 공간 재사용(원문이 SJIS일 때 성립).** 새 인코딩을 만들지 않고 한자 영역 코드에 한글 음절을 대입하면 엔진 무수정으로 동작한다.

- 원문과 시스템 문자열에서 쓰이지 않고 BIOS 폴스루와 충돌하지 않는 lead 범위를 실측해 후보 코드 공간을 만든다. 후보 슬롯 수가 대상 번역의 고유 음절 수를 덮는지 코퍼스로 확인한다.
- SJIS 유효 하위 바이트는 `0x40`~`0x7E`와 `0x80`~`0xFC`이며 `0x7F`는 유효하지 않다.
- 연속 lead 범위를 쓸 때는 룩업 테이블 없이 순서를 계산할 수 있다:

```
lead_ordinal = H - first_verified_lead
trail_ordinal = (L - 0x40) - (L >= 0x80 ? 1 : 0)
glyph_index = lead_ordinal * 188 + trail_ordinal
glyph_ptr = font_base + glyph_index * 30
```

- 후보 범위 밖의 원문 코드와 구두점은 BIOS로 폴스루시킨다.
- 음절 할당은 번역문에서 고유 음절을 수집해 유니코드 순(U+AC00부터)으로 정렬 후 인덱스 순서대로 부여한다 — 결정적·재현 가능.
- 훅은 입력 코드가 검증된 후보 집합에 속하면 인덱스를 계산해 글리프 포인터를 반환하고, 아니면 원래 BIOS 경로로 폴스루한다.
- JAL 패치 검증: `jal target` 인코딩은 `0x0C000000 | ((target >> 2) & 0x03FFFFFF)`. `jal`/`jalr`이 `$ra`에 넣는 복귀값은 호출 명령이 아니라 지연 슬롯 다음 명령 주소(PC+8)이므로, 트램폴린에서 `$ra`를 복귀에 재사용할 때 이 +8을 전제한다.

**알려진 충돌**: 재사용한 범위의 원문 코드가 남으면 훅이 한글로 오인한다. 원문·시스템 문자열·세이브 데이터까지 후보 범위 사용 여부를 조사하고, 패치본에 충돌 코드가 남지 않는지 커버리지 게이트로 검증한다.

## 7. 디스크와 빌드

### 이미지 구조와 재삽입

BIN/CUE는 Mode2/2352 raw 섹터이고 PS1 데이터 트랙은 **Mode 2 Form 1**이다 — 헤더 뒤 8B 서브헤더가 들어가 user data(2048B)·EDC·ECC 위치가 Mode 1과 어긋나므로, 섹터 레이아웃과 EDC/ECC 재계산 오프셋은 이 모드에 맞춘다. Mode 1/Mode 2 Form 1 섹터 구조와 EDC/ECC 재계산·변경 섹터만 재계산하는 정책은 `references/strategy/build-and-verify.md` §3이 정본이다. PS1 고유 처리: 파일을 수정해 재삽입할 때 LBA가 바뀌지 않는 동일 크기 교체가 가장 단순하고, 크기가 변하면 ISO 9660 디렉토리 레코드의 크기 필드와 후속 파일 LBA까지 갱신한다.

### 폰트 추가 섹터

이미지 끝에 섹터를 덧붙이면 기존 파일 배치를 건드리지 않고 데이터를 넣을 수 있다. 다만 선택한 시작 LBA, 추가 섹터 수, 이미지 총 길이와 로더의 읽기 범위를 빌드 산출물에서 서로 대조해야 한다.

### CD 하드웨어 직접 제어 (훅에서 폰트 로드)

훅이 활성 IRQ 핸들러 안에서 돌거나, 부트 시점처럼 BIOS B-table CD 함수가 아직 미초기화인 상황이면, 런타임 라이브러리(Psy-Q CdControl/CdRead) 호출이 INT 가로채기·미초기화로 충돌한다. 이 두 조건에 걸리는 훅에서는 **레지스터 직접 제어**가 안전하다.

베이스 0xBF801800. 1800 bits[1:0]로 Index 선택. Status(모든 Index에서 읽기): bit7 BUSYSTS(명령 처리 중), bit6 DRQSTS, bit5 RSLRRDY, bit4 PRMWRDY. Index 0 쓰기: 1801=COMMAND, 1802=PARAMETER, 1803=Request(0x80=BFRD). Index 1 쓰기: 1802=IRQ Enable, 1803=IRQ Clear(0x1F=전체, 0x40=ClrParam). IRQ flag(Index 1, 1803 읽기) bits[2:0]: 1=DataReady(INT1), 2=Complete(INT2), 3=Acknowledge(INT3), 5=DiskError.

N섹터 읽기 시퀀스:

```
1. I_MASK(0x1F801074) bit2 비활성화 (런타임 IRQ 핸들러 차단)
2. DPCR(0x1F8010F0) |= 0x8000              (DMA3 활성화)
3. SetMode(0x80) → INT3 → ACK
4. SetLoc(min,sec,frame BCD) → INT3 → ACK
5. ReadN() → INT3 → ACK
6. 섹터마다: INT1 대기 → Result 소비 → BFRD(0x80→1803) →
   DMA3 (MADR(0x1F8010B0) ← 목적지 RAM 주소, BCR=0x00010200 [512워드×1블록=2048B],
   CHCR=0x11000000) → CHCR bit24==0 대기 → IRQ ACK(0x1F)
7. Pause() → INT3 → ACK → INT2 → ACK
8. 원래 SetMode 복원 (BUSYSTS 대기 + ClrParam 선행)
```

주의사항:
1. **INT1 먼저, BFRD 나중** — DRQSTS만으로 새 섹터 감지 불가
2. **매 섹터 IRQ ACK 필수** — 안 하면 다음 INT 미발생
3. **Result FIFO 소비 필수** — 남으면 다음 응답과 혼합
4. **새 명령 전 BUSYSTS 대기**
5. DMA 목적지는 4바이트 정렬
6. **Pause의 INT2(완료)까지 대기**하고 SetMode를 보내라 — 감속 중 명령은 무시되어 CD 모드가 미복원된다

부작용: 훅의 직접 CD 읽기는 XA/스트리밍 상태와 간섭할 수 있다(사례: 첫 폰트 로드 시 음악 중단, 씬 전환 후 복구). 로드 시점을 신중히 고르고 모드 복원을 철저히 한다.

## 8. 검증 (런타임 훅 디버깅)

실행 환경은 MIPS 명령 단위 스텝, 브레이크포인트, 레지스터·RAM 조회와 실행 흐름 추적을 제공해야 한다. 후보 표면은 `references/conventions/tooling.md` §7.7, 채택·교정 규약은 같은 문서 §1을 본다. 다음을 점검한다.

- **훅 리턴 상태 검증**: 트램폴린 리턴 주소에 BP를 걸고 히트마다 입력 SJIS, 분기 경로(한글/BIOS), 출력 포인터, 보상 레지스터 값을 표로 기록한다. 글리프 주소는 수동 계산(font_base + index×30)과 대조한다.
- **load delay 추적**: 한 명령씩 진행하며 `lw` 직후 레지스터에 옛 값이 남는 것을 직접 관찰한다. 분기가 이상하게 항상 성립한다면(taken) 가장 먼저 의심한다.
- **I-cache stale 판별**: RAM 직접 읽기(패치 코드 존재)와 실제 명령 흐름의 PC 추적이 다르면 I-cache 문제다. KSEG0/KSEG1 양쪽 덤프가 같으면 D-cache는 무관하다.
- **디스크 vs RAM 비교**: 폰트 로드 검증은 디스크 원본 바이트와 RAM 적재 결과를 같은 오프셋에서 비교한다. 불일치하면 LBA/MSF 변환, CD 명령 선택, 호출 규약과 인자 순서를 다시 확인한다.
- **함수 역할 확정법**: 후보 함수의 호출 사이트를 전수 수집하고 전후 호출·인자·반환값 패턴으로 역할을 검증한다. 이름이나 한 호출 지점만으로 CD 함수라고 단정하지 않는다.
- **데이터 파괴 격리 테스트**: 크래시가 코드 버그인지 데이터 파괴인지는 격리 빌드로 원인 층을 분리한다 — 격리 빌드/ablation 절차는 `references/strategy/debugging.md` §2를 따른다. PS1 고유 단서로, 에뮬레이터의 "write to unknown address" 로그는 OOB 포인터 산술을 가리킨다.
- **시각 증상 사전**: 에러 글리프 연속 표시 = 패딩/종료자 오해, 전체 스트림 깨짐 = 문자 폭 또는 파라미터 길이로 인한 정렬 어긋남, VRAM 노이즈 = CD 상태 오염이나 텍스처 로드 실패를 우선 의심한다.

### 실기 구동 경로

실광학 매체와 부트·인증 우회, 소프트웨어 부트 경로, 이미지 로더 중 실제 배포 대상을 정한다. 어느 경로든 다음 능력을 확인한다.

- 원본의 단일/멀티 파일 트랙 구조와 `MODE2/2352`, CDDA, INDEX/pregap을 손실 없이 읽는가?
- 지역·디스크 인증·게임 고유 보호를 어떤 계층에서 처리하며, 그 처리가 패치 이미지의 구조를 바꾸는가?
- 장치가 별도 시트나 병합 이미지를 요구한다면 변환 뒤 LBA·트랙 시작·오디오 재생이 정본과 같은가?

**빌드 포맷에 미치는 영향**: 배포 패치는 원본의 검증된 트랙 구조를 보존한 정본 이미지 기준으로 만든다. 데이터 트랙을 수정하면 변경 섹터의 EDC/ECC를 재계산하고, 의도적 오류 섹터는 raw로 보존한다(`references/strategy/build-and-verify.md` §3). 특정 장치가 요구하는 병합·시트·컨테이너 변환은 정본 빌드 뒤의 별도 단계로 두고, 그 변환물을 다시 정본과 혼동하지 않는다.

흔한 함정은 장치가 지원하지 않는 트랙 배치를 패치 불량으로 오인하거나, 변환 과정에서 CDDA·INDEX·LBA를 잃는 것이다. 섹터 정합은 부팅 여부와 별도로 검사한다. 하드웨어 재구현 같은 중간 환경도 실제 CD 인터페이스와 이번 변경 경로를 구현한 범위에서만 증거로 쓰며, 배포 대상의 매체 동작을 대신하지 않는다. 검증 티어 운용은 `references/strategy/build-and-verify.md` §4를 따른다.

## 9. 사례 요약 (PS1 와쿠와쿠 뿌요뿌요 던전)

이 사례는 Mode 2 Form 1과 ISO 9660 위에 역할별 VDD 아카이브와 CNX v2 압축을 사용했다.

- **텍스트**: 스토리 모듈은 절대 RAM 포인터와 연속 텍스트 뒤 초기화 코드를 함께 재배치해야 했고, 포인터 참조가 광범위한 메뉴 모듈은 고정길이 교체가 더 안전했다. 같은 확장자라도 재삽입 전략을 하나로 묶지 않는 사례다.
- **폰트**: BIOS 글리프 반환 경로를 훅했으며, 부트 디컴프레서가 만든 I-cache stale 때문에 RAM 바이트 확인만으로는 충분하지 않았다. KSEG1 실행과 캐시 라인 안의 짧은 트램폴린으로 실행 경로를 분리했다.
- **한글**: 원문에서 비어 있음을 검증한 SJIS 코드 대역을 한글 슬롯으로 재사용하고, 폰트는 기존 EXE 배치와 충돌하지 않는 디스크 영역에서 지연 적재했다. 후보 코드의 원문 잔존과 CD 스트리밍 상태가 별도 회귀 위험으로 남았다.
- **재삽입**: 문자 소비 폭, 제어 코드 파라미터, 종료자와 패딩을 엔진별로 확정해야 했다. 구체 코드값·주소·파일 배치는 프로젝트 문서가 소유한다.
