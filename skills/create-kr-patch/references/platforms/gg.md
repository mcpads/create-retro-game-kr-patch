# 게임기어 (Sega Game Gear) 한글 패치 참조

## 1. 플랫폼 개요

게임기어의 CPU는 Zilog Z80A 호환이며 클럭은 3.58MHz(정확히는 3.579545MHz)다. 데이터 버스 8비트, 주소 버스 16비트로 CPU가 직접 보는 주소 공간은 64KB뿐이다. 리틀엔디언이므로 헥스 에디터에서 `00 81`로 보이는 포인터는 `$8100`이다. 16비트 포인터는 `HL`에 싣고 `(HL)`로 역참조하는 코드가 표준 관용구다.

화면 출력은 TMS9918A 계열에서 파생된 세가 VDP가 담당하며, 상용 게임기어/마스터시스템 게임의 일반적인 분석 대상은 **Mode 4**다. VRAM 16KB, 8×8 픽셀 4bpp 타일, 팔레트 2개×16색. 게임기어 팔레트는 색당 2바이트(채널당 4비트, 4096색)로 마스터시스템(색당 1바이트, 64색)과 다르다.

게임기어 특유의 제약은 **가시 영역**이다. 내부 네임테이블은 마스터시스템과 동일한 32×28타일이지만, LCD에는 중앙 160×144픽셀 = **20×18타일**만 표시된다. 스크롤 레지스터가 0일 때 대략 열 6~25, 행 3~20이 보이는 범위다. 텍스트 창 좌표를 계산하거나 타일맵을 덤프해 분석할 때 이 오프셋을 항상 보정해야 한다.

분석 단계에서 자주 쓰는 Z80 헥스 시그니처:

| 패턴 | 의미 |
|------|------|
| `3E xx 32 FF FF` | `LD A,xx / LD ($FFFF),A` — 슬롯 2 뱅크 전환 |
| `D3 BF` / `D3 BE` | VDP 컨트롤/데이터 포트 출력. 렌더링 루틴 단서 |
| `7E 23 B7 C8` | `LD A,(HL) / INC HL / OR A / RET Z` — 문자열 읽기 루프 |
| `5E 23 56 EB` | 16비트 포인터 역참조 — 포인터 테이블 코드 단서 |
| `ED B3` (OTIR) | VRAM 블록 전송 루프 |
| `54 4D 52 20 53 45 47 41` | "TMR SEGA" ROM 헤더 매직 |

## 2. 메모리 맵과 뱅킹

### 2.1 SEGA 매퍼와 16KB 슬롯 3개

ROM은 16KB(0x4000) 뱅크 단위로 잘려 세 슬롯에 매핑된다. 매퍼 제어 레지스터는 RAM 최상단 주소에 있다.

```
0x0000-0x3FFF : 슬롯 0 (레지스터 0xFFFD, 사실상 뱅크 0 고정.
                 0x0000-0x03FF의 첫 1KB는 인터럽트 벡터 보호를 위해 항상 뱅크 0)
0x4000-0x7FFF : 슬롯 1 (레지스터 0xFFFE)
0x8000-0xBFFF : 슬롯 2 (레지스터 0xFFFF) — 데이터 뱅크 전환의 주 통로
0xC000-0xDFFF : 워크 RAM 8KB
0xE000-0xFFFF : RAM 미러 (0xFFFC-0xFFFF는 매퍼 레지스터가 인터셉트)
```

물리 ROM 오프셋 = 뱅크 번호 × 0x4000 + 슬롯 내 오프셋. 디버거에서 본 논리 주소를 ROM 파일 오프셋으로 옮길 때 항상 현재 뱅크를 함께 기록해야 한다. 매퍼는 뱅크 번호의 하위 비트만 보므로 ROM 크기를 넘는 뱅크 번호는 wrap-around된다.

### 2.2 ROM 헤더와 확장

오프셋 0x7FF0에 16바이트 TMR SEGA 헤더가 있다. 0x7FFA에 16비트 체크섬, 0x7FFF 상위 니블에 리전(0x5=GG Japan, 0x7=GG International), 하위 니블에 크기 코드(0x0=256KB, 0x1=512KB, 0x2=1MB)가 들어간다. ROM을 수정하면 빌드 단계에서 체크섬을 재계산한다.

512KB(32뱅크) ROM은 끝에 512KB를 덧붙여 1MB(64뱅크)로 확장할 수 있다. 추가 영역은 0xFF로 패딩하고 헤더의 크기 코드와 체크섬을 결과에 맞춘다. 한 사례에서는 확장 뱅크를 렌더 코드와 글리프 데이터로 나눴다. 구체 뱅크 번호는 고정하지 않고 빌드 레이아웃이 선택하며, 4bpp 글리프는 1자당 32바이트이므로 `ceil(글리프 수 × 32 / 0x4000)`으로 필요한 데이터 뱅크 수를 계산한다.

코드(고정 슬롯 0)와 글리프 데이터(슬롯 2 경유)가 다른 뱅크에 있으므로 렌더링 중 뱅크 전환이 일어난다. 전환 전 현재 뱅크를 RAM에 보존하고, VDP 접근 구간은 `DI`/`EI`로 인터럽트를 막는다.

## 3. 비디오 시스템

### 3.1 4bpp 인터리브드 비트플레인 타일

타일 1개 = 8×8픽셀 = 32바이트. 행마다 4바이트가 연속 배치되며 각 바이트가 비트플레인 0~3을 맡는다(행 단위 인터리브). 픽셀 (x,y)의 색 인덱스는 네 플레인의 비트 (7-x)를 모은 4비트 값이다.

단색 폰트는 비트플레인 0만 쓰면 된다(인덱스 0=투명, 1=전경). 1bpp 비트맵 8바이트를 4bpp 32바이트로 펼치는 변환은 다음과 같다.

```python
def to_gg_tile(bitmap_8bytes, fg=1):
    """1bpp 8바이트 → GG 4bpp 32바이트 (전경색 = 팔레트 인덱스 fg)"""
    tile = bytearray(32)
    for row in range(8):
        b = bitmap_8bytes[row]
        for plane in range(4):
            tile[row * 4 + plane] = b if (fg >> plane) & 1 else 0
    return bytes(tile)
```

### 3.2 VRAM 레이아웃과 타일 수 한계

```
0x0000-0x37FF : 타일 패턴 (타일 N의 주소 = N × 32)
0x3800-0x3EFF : 네임테이블 32×28 = 896 엔트리 × 2B = 1,792B
0x3F00-0x3FFF : 스프라이트 속성 테이블(SAT)
```

네임테이블이 기본 위치 0x3800에 있을 때 사용 가능한 타일은 **최대 448개**다. 배경·UI가 상당수를 점유하므로 폰트에 쓸 수 있는 타일은 그보다 적다. 한글 완성형 수백 자를 상주시키기는 어렵기 때문에, 대사 본문은 표시 시점에 필요한 글리프만 VRAM에 올리는 동적 전송을 우선 검토한다. 짧은 UI 전용 서브셋은 정적 상주도 가능하므로 화면별 타일 점유를 먼저 산정한다.

네임테이블 엔트리는 16비트 리틀엔디언: 타일 인덱스 9비트(0~511) + H/V 플립 + 팔레트 선택 + 우선순위(priority, 텍스트를 배경 위에 그릴 때 사용). 좌표 (col,row)의 엔트리 주소는 `0x3800 + (row*32 + col)*2`다.

### 3.3 VDP 포트 프로토콜

VRAM 접근은 포트 두 개로만 이루어진다. 0xBF에 주소 하위/상위(쓰기 모드는 상위에 bit6 셋)를 차례로 출력한 뒤, 0xBE로 데이터를 읽고 쓴다(주소 자동 증가). 블록 전송은 `OUTI`/`OTIR` 루프를 쓰되, VDP 쓰기 타이밍을 맞추기 위해 루프 안에 `PUSH IX / POP IX` 같은 지연을 끼우는 패턴이 흔하다. CRAM(팔레트) 쓰기는 주소 상위에 bit7+bit6을 셋한다.

주의: 화면 조립이 항상 "소스 데이터 → 즉시 VRAM"으로 이어지지는 않는다. 일부 게임은 워크 RAM에 네임테이블/타일 행을 먼저 조립하고, 별도 섀도 버퍼나 dirty 행 추적을 거쳐 변경된 행만 VDP 포트로 복사한다. 이 구조에서는 VRAM write 브레이크포인트가 늦은 복사 루틴만 잡고, 실제 값·좌표를 만든 조립 루틴은 놓친다. 숫자나 HUD 값의 출처를 추적할 때는 VRAM 전송 루프에서 멈추는 것만으로 끝내지 말고, 전송 원본 RAM 버퍼를 역추적해 어느 코드가 그 버퍼를 채웠는지 확인한다.

## 4. 텍스트 엔진 패턴

### 4.1 자체 테이블 인코딩

게임기어 게임의 텍스트는 ASCII/Shift-JIS가 아닌 게임 고유 테이블로 인코딩된다. 문자→타일 변환 공식·다이그래프 구성·기본 문자 대역은 게임마다 다르므로, 한 게임의 인코딩 표를 다른 게임에 보편 규칙으로 가정하지 말고 렌더 루틴의 변환 코드를 직접 확인해 게임별로 재확정한다.

게임기어처럼 저해상도 타일 폰트와 자체 테이블을 쓰는 플랫폼에서는 구두점·기호·탁음 계열 글리프를 오독하기 쉽다. 번역 착수 전 문자 테이블은 `references/strategy/text-extraction.md` §2의 라운드트립·HITL 화면 대조 게이트를 통과해야 한다.

- **다이그래프·2바이트 대역**: 자체 테이블은 1바이트가 두 글자 조합(th, he, an ...)으로 풀리는 다이그래프/2바이트 대역을 두기도 한다. 추출기는 이 대역을 반드시 2글자로 복원(2-for-1 확장)해야 한다

### 4.2 선행 패치 베이스와 레이아웃 상속

선행 패치를 베이스로 삼으면 그 패치가 원본 대비 바꿔 둔 레이아웃 메트릭(행 stride·폰트 높이·페이지 줄 수·커서/좌표 초기값·창 클리어 범위)까지 상속하므로 원본판과 비교해 감사한다. 베이스 선택과 선행 패치 활용(디프 분석·문제 지도·라이선스/버그/전제 주의)의 범용 절차는 `references/strategy/initial-survey.md` §4를 따른다.

### 4.3 텍스트 엔진 밖 표시 루틴

메뉴·상점의 숫자(가격·소지금·능력치)는 대사 텍스트 포인터를 거치지 않고 고정 버퍼/네임테이블 좌표에 직접 쓰는 경로가 흔하다 — GG 가시영역 20×18 좌표를 전제로 박혀 있으면 텍스트 줄간격만 바꿔도 어긋나므로, 화면에만 있고 추출 텍스트엔 없는 값은 변수 치환·숫자 렌더·그래픽 자산으로 분리해 추적한다. 베이크드/HUD 그래픽 텍스트와 숫자 렌더의 범용 처리는 `references/strategy/graphics-text.md`를 따른다.

## 5. 한글 인코딩

### 5.1 2바이트 프리픽스 인코딩

한글 완성형을 8×8 1타일로 넣을 때, 원본 인코딩의 **미사용 바이트를 프리픽스로 삼아 2바이트로 한글 음절을 표현**하는 접근을 쓸 수 있다. 프리픽스 대역·영문 유지 대역·변수/제어 대역이 어디인지는 **게임 원본 인코딩마다 다르므로 대상 게임에서 다시 정한다.** 한 사례에서는 기존 영문·다이그래프, 변수, 제어코드 대역을 보존하고 서로 충돌하지 않는 미사용 바이트 여러 개를 한글 프리픽스로 배정했다.

음절 상한은 「프리픽스 수 × 256」이다. 미사용 대역에서 프리픽스를 더 확보하면 256 단위로 는다(산정 일반론: `references/strategy/font-strategy.md` 3절). 음절→코드 매핑은 고정 코드표가 아니라 빌드 시 번역 텍스트의 출현 빈도순으로 동적 생성해, 자주 나오는 음절을 낮은 프리픽스에 배정한다(번역이 바뀌면 매핑도 재생성). 프리픽스 대역이 원본의 미사용 대역이어야 하므로, 원본에서 그 대역을 쓰던 문자(탁음 합성 등)는 사전에 정리한다.

### 5.2 글리프 운용

- 번역 전량에서 실제 사용된 음절만 글리프로 만든다. 한 사례에서는 실사용 음절 수가 산정 상한 안에 들었지만, 게임마다 번역 코퍼스에서 다시 집계한다
- 글리프는 8×8 4bpp 타일(32바이트)로 사전 렌더링해 전용 뱅크에 배치한다. 필요 뱅크 수는 `음절 수 × 32B`로 계산한다
- 한글은 고정폭 8px 1문자=1타일이므로, 창 폭 예산(타일 수)을 한글 기준으로 다시 계산해야 한다(고정폭 한글이 가변폭 폰트보다 타일을 더 쓰는 일반 사례는 `references/strategy/initial-survey.md` §4)
- 8×8 한 타일에 초성·중성·종성을 다 그려야 하므로 가독성 한계가 뚜렷하다. 획이 많은 글자를 피하는 번역어 선택도 실질적인 대응 수단이다

## 6. ASM 패치 패턴

### 6.1 트램폴린 → 디스패치 → 렌더 3단 구조

원본 코드를 최소로 건드리면서 한글 경로를 끼워 넣는 구조로, 세 층으로 나뉜다. **트램폴린** — 뱅크 0 고정 영역에서 텍스트 시작 루틴의 목적지를 교체해 한글 디스패처로 보내고, 타일 카운터를 리셋한 뒤 원래 루틴으로 돌아온다. **디스패처** — 문자 바이트가 대상 게임에서 정한 한글 프리픽스면 두 번째 바이트를 읽고 확장 뱅크의 한글 렌더러로 보내며, 아니면 원본 영문 경로로 가른다. **한글 렌더러** — 확장 뱅크에서 글리프 VRAM 전송과 네임테이블 기록을 처리한다.

요점은 **원본 코드 개입을 필요한 분기와 복귀에 한정하고 본체 로직은 확장 뱅크로 빼는** 배치다. 원본에서 손대는 지점(텍스트 시작 루틴, 타일 매핑, 그리고 선행 패치가 VWF 엔진을 얹었다면 그 엔진의 리턴·초기화 및 read-ahead 가드)의 주소·바이트 예산·RAM 변수·뱅크 번호는 대상 게임에서 다시 찾고 프로젝트 기록으로 관리한다.

### 6.2 한글 렌더러와 타일 할당

핵심은 한글 렌더러가 게임의 타일 관리 체계에 그대로 편입되어 출력 타일을 순차 할당받게 하는 것이다 — 그래야 배경 타일과 충돌할 위험이 준다. **선행 패치가 VWF 엔진을 얹은 경우** 그 엔진과 상태(타일 카운터·타일 베이스)를 공유하는 병렬 경로로 붙일 수 있다(구체 사례: §10). 흐름은 대략 (1) 레지스터·뱅크를 RAM 슬롯에 저장 → (2) 렌더 세션이 미시작이면 타일 카운터·베이스를 초기화 → (3) 할당 규약대로 타일 인덱스를 정해 VRAM 주소를 계산하고 4bpp 글리프를 DI/EI 보호 하에 전송 → (4) 다음 문자가 새 타일에서 시작하도록 합성·카운터 상태를 맞춘 뒤 → (5) 원본 네임테이블 기록 루틴으로 복귀한다.

반대로 카운터 초기화 책임이 (공유 대상 엔진과 한글 경로) 양쪽에 분산되면 부팅 직후 첫 한글 문자가 엉뚱한 타일을 덮어쓰는 버그가 난다. 세션 미시작 시 어떤 상태 변수를 초기화해야 하는지, 카운터·베이스가 어느 RAM 주소인지는 대상 엔진에서 실측한다.

### 6.3 자유 공간 발굴 주의점

뱅크 0의 NOP(0x00) 연속 영역이라도 코드가 아니라 **데이터로 쓰일 수 있다**. 실제 사례에서는 NOP처럼 보인 영역의 일부를 게임이 RAM 버퍼 초기화용 제로 데이터로 복사했다. 따라서 참조되는 앞부분은 보존하고 검증된 나머지에서만 새 코드를 시작했다. 자유 공간 후보는 반드시 그 주소를 읽는 코드(`LD HL,주소`)가 없는지 교차 확인한다.

## 7. 텍스트 공간 전략

### 7.1 다중 포인터 테이블

텍스트가 하나의 테이블이 아니라 뱅크별·용도별 복수 테이블로 쪼개져 있는 구조가 흔하다. 한 사례에서도 전투·상태·메뉴와 스토리·이벤트 테이블이 서로 다른 뱅크와 논리 base를 썼다. 테이블 식별자는 용도, 물리 뱅크, 논리 base, 진입점, 포인터 폭을 함께 기록해 같은 이름의 테이블이 섞이지 않게 한다.

그 사례의 포인터는 16비트 리틀엔디언 **테이블 base 기준 오프셋**이었다(논리 주소 = base + 포인터 값). 다른 게임에는 절대 주소나 다른 폭의 포인터가 있을 수 있으므로 표현을 먼저 확정한다. 같은 뱅크의 테이블이라도 base가 제각각이면 테이블마다 base와 Z80 진입점을 따로 기록하며, 진입점이 다른 테이블을 하나로 합치면 일부 텍스트만 깨지는 형태로 드러난다.

### 7.2 접미사 공유 트레이드오프

원본 텍스트는 **복수 포인터가 동일 텍스트 블록의 중간 지점을 가리켜 접미사를 공유**하는 최적화를 쓸 수 있다(예: 공통 종결구와 종료 마커를 여러 엔트리가 공유). 이를 무시하고 엔트리마다 전문을 펼치면 데이터가 여러 배로 불어나 한 뱅크에 들어가지 않을 수 있다.

따라서 접미사 공유를 보존하거나, 공유를 해제해도 확인된 뱅크 예산에 수납된다는 증거를 남긴다. 보존하는 경우의 요령:

- 추출 시 어느 포인터들이 같은 블록을 공유하는지 그래프로 기록한다
- 번역 후에도 공유 가능한 꼬리(공통 종결구 + [END])는 다시 공유시킨다
- 미번역 엔트리가 참조하는 바이트는 **보호 바이트**로 표시하고 그 위에 한글 텍스트를 덮지 않는다
- 텍스트 뱅크 안에 게임 로직이나 레벨 데이터가 섞여 있을 수 있다. 텍스트가 아닌 영역은 분석 결과에서 보호 범위로 기록하고 재배치기가 절대 침범하지 않게 한다

## 8. 빌드

배포 포맷(IPS/BPS) 생성 이전에, 빌드 자체는 **ROM 바이너리를 직접 재조립**하는 단일 파이프라인으로 만든다. 원본 ROM 비커밋과 차분 패치 배포 규약은 `references/conventions/project-conventions.md` §6과 SKILL.md 불변식을 따른다.

```
1. 베이스 ROM 로드 (원본 또는 분석·권리 검토를 통과한 선행 패치판)
2. 번역 데이터 로드 (테이블별 JSON 등, 다중 테이블 인식)
3. 음절 빈도 집계 → 프리픽스 매핑 동적 생성 → 필요한 글리프 렌더링
   (1bpp → 4bpp 변환) → 빌드가 할당한 확장 데이터 뱅크에 삽입
4. Z80 패치 어셈블·삽입 (트램폴린/디스패치/가드/한글 렌더러/리턴 패치)
5. 테이블별 한글 텍스트 인코딩 → 뱅크 재구성:
   원본 뱅크 전체 복사 → 보호 바이트 회피 → 한글 텍스트 배치 → 포인터 테이블 갱신
6. TMR SEGA 헤더 크기 코드·체크섬 재계산
7. 패치 ROM 저장 (배포는 패치 파일로, 원본 ROM 미포함)
```

베이스를 원본판으로 잡을지 선행 패치판으로 잡을지의 판단(인프라 재사용 가치·권리·2단계 적용 절차·레이아웃 상속 비용 비교)은 범용 절차이므로 `references/strategy/initial-survey.md` §4를 따른다.

빌드가 결정적(같은 입력 → 같은 출력)이어야 디버깅 중 세이브 스테이트를 재활용할 수 있다. 인코딩 매핑이 빈도순 동적 생성이므로 번역 한 줄만 바뀌어도 매핑 전체가 바뀔 수 있다는 점을 인지하고, 디버깅 세션 중에는 번역을 고정한다.

Z80 패치 코드는 핸드 어셈블보다 어셈블러(WLA-DX 등) 또는 빌드 도구 내장 인코더로 생성하고 단위 테스트를 붙인다. `JR` 상대 오프셋(기준 = 명령 다음 바이트, signed 8비트) 계산 실수가 단골 버그다.

## 9. 검증

### 9.1 수동 디버거 요건

수동 분석·검증 도구는 특정 제품명보다 기능 요건으로 고른다. Z80 디스어셈블·스텝 실행, RAM/VRAM/CRAM 뷰어, VDP 포트/VRAM 쓰기 추적, 타일 뷰어, 브레이크포인트를 갖춘 에뮬레이터가 필요하다. 어떤 도구를 쓰든 GG의 VDP 쓰기가 CPU 메모리 쓰기가 아니라 포트 I/O라는 점을 먼저 확인하고, 그 도구의 "VRAM write" 관측이 실제로 어느 계층을 잡는지 검증한다.

- **타일 뷰어**: 한글 글리프가 VRAM에 올바른 비트플레인 배열로 올라왔는지 시각 확인
- **메모리 뷰어 + VRAM/VDP 쓰기 관측**: 글자가 깨질 때, 해당 VRAM 주소에 쓰는 순간 멈추고 콜스택을 역추적해 글리프 데이터 문제인지(폰트 변환 버그) 네임테이블 인덱스 문제인지(렌더러 버그) 구분
- **RAM 버퍼 추적**: 화면이 RAM 프레임버퍼/섀도 버퍼에서 조립된 뒤 VDP로 복사되는 구조라면, VRAM 쓰기 지점에서 멈춘 뒤 전송 원본 버퍼를 역추적한다

### 9.2 자동 검증 (프로그램 제어)

에이전트/스크립트 기반 자동 검증의 요건은 메모리 읽기·입력 주입·스크린샷·세이브 스테이트를 프로그래밍으로 호출할 수 있는 에뮬레이터다. 구현은 도구마다 다르므로, 특정 도구명을 절차의 전제로 삼지 말고 아래 표면을 확보했는지로 판단한다.

- **메모리 읽기**: 워크 RAM, VRAM, CRAM, 전체 ROM을 구분해 읽는다. 워크 RAM 논리 주소는 플랫폼 메모리 맵의 RAM 시작 주소를 빼 도구의 RAM 오프셋으로 변환하고, 네임테이블은 VDP 레지스터에서 확인한 base와 크기로 읽는다. 매퍼 레지스터는 RAM 미러와 혼동하지 않도록 별도 표면에서 확인한다
- **디버깅**: 논리 주소 브레이크포인트, 스텝 실행, VDP 쓰기·뱅크 전환 트레이스 로그. GG의 VDP 쓰기는 CPU 메모리 쓰기가 아니라 포트 I/O이므로, 일반 memory-write 브레이크포인트가 VRAM 쓰기를 잡는다고 가정하지 않는다. 사용하는 자동화 표면이 VDP 포트 쓰기를 어떻게 관측하는지 먼저 확인한다
- **상태 검사**: Z80 레지스터/VDP 레지스터 조회로 디스패치 분기·뱅크 상태를 직접 확인한다. 한글·영문 렌더링이 공유하는 세션 플래그와 타일 카운터의 실제 RAM 위치는 대상 게임에서 찾아 프로젝트 관측점으로 두고, 두 경로 전환 전후의 값을 비교한다
- **자동 진행**: 컨트롤러 입력(press_and_release가 안정적), 배속, 세이브 스테이트(ROM 빌드와 1:1 대응 — 다른 빌드의 스테이트 로드 금지), 스크린샷(base64 PNG)으로 화면 단위 회귀 검증
- **자동화 표면 검증**: 입력 주입, pause/freeze, 브레이크포인트 이벤트, 메모리 read가 수동 디버거에서 관찰한 상태와 같은 시점을 보고 있는지 작은 장면으로 먼저 교차 확인한다. 자동화 표면의 타이밍이 불명확하면 그 결과를 게임 로직의 증거로 승격하지 않는다

### 9.3 체크리스트

```
[ ] 수정한 대표 글리프·텍스트가 깨짐 없이 표시
[ ] 수정 화면 이탈·재진입 뒤 타일·카운터·베이스 상태 정상
[ ] 수정하지 않은 대표 경로가 기준 동작을 유지
```

영문·한글 혼용, 20×18 가시영역 경계, 제어코드 종류, 전투·메뉴·스토리의 뱅크 전환, 부팅 직후 초기화, 장시간 종료 처리는 해당 기능·별도 테이블·위험 신호가 확인될 때 조건부 항목으로 추가한다. 존재하지 않는 기능을 플랫폼 최소 조건으로 만들지 않는다.

### 9.4 실기 구동 경로

- **수단**: 최종 배포물을 실제 게임기어 또는 목표와 동등하다고 입증된 실행 경로에서 검증한다. 로더·카트·재현 코어는 최종 ROM 크기, 대상 매퍼, 헤더·리전, 저장 방식 등 패치가 의존하는 기능을 지원해야 한다.
- **제약**: ROM 용량과 매퍼 지원은 제품명이나 자동 감지 표기만으로 가정하지 않는다. 실제 사용할 장치·펌웨어 조합에서 최종 ROM을 읽고 모든 확장 뱅크에 접근하는지 확인한다.
- **빌드 포맷에 미치는 영향**: 확인된 대상의 ROM 상한과 매퍼 조건을 빌드 입력으로 두고, 산출물이 이를 벗어나면 실패시킨다. 공간 절약은 이 확인된 호환 목표를 지키기 위한 선택지이지, 특정 소비자 장치의 고정 용량을 플랫폼 규칙으로 만들 근거는 아니다.
- **함정**: 로더가 이미지를 거부하지 않았더라도 상위 뱅크를 잘못 매핑하거나 저장 영역과 충돌할 수 있다. 부팅 확인만으로 끝내지 말고 각 확장 뱅크의 텍스트·폰트 경로와 저장 기능을 실행한다. 실물 게임기어는 LCD·전원 회로 상태도 검증 변수다.
- **중간 검증(FPGA)**: 재현 코어가 패치에서 변경한 매퍼·VDP·저장 경로를 실제로 포함할 때만 중간 검증 증거로 사용한다. 검증 티어의 근거와 운용은 `references/strategy/build-and-verify.md` §4를 따른다.

## 10. 사례 요약 (GG 마도물어 1)

일본판 512KB ROM에 대해 1MB로 확장된 선행 영문 패치판이 존재했고, 한글 패치는 그 위에 구축되었다. 영문 패치가 이미 ROM 확장과 가변폭(VWF) 텍스트 엔진을 갖추고 있어 인프라를 재활용한 사례다.

- **인코딩**: 영문·다이그래프와 변수·제어 대역을 유지하고, 검증된 미사용 바이트 여러 개를 한글 프리픽스로 배정한 2바이트 방식. 음절은 확보한 프리픽스 슬롯에 빈도순으로 동적 매핑
- **폰트**: 8×8 1타일 완성형 글리프(4bpp)를 빌드가 할당한 확장 데이터 뱅크에 배치. 고정폭 8px
- **패치 코드**: 트램폴린 → 디스패치 교체 → read-ahead 가드 → 한글 렌더러 + VWF 엔진 미세 패치. 원본 영역 수정은 분기·복귀에 한정하고 본체는 확장 뱅크에 배치
- **공존 설계**: 영문 VWF 엔진과 한글 렌더러가 타일 카운터·타일 베이스를 공유해 출력 타일을 순차 할당. read-ahead 가드가 영문→한글 전환 시 합성을 강제 완료시켜 두 경로가 한 문장 안에서 안전하게 섞인다
- **레이아웃**: 선행 영문 패치판이 영어 글자 높이에 맞춘 행간·페이지 메트릭을 갖고 있어, 한글 가독성과 원본 UI 좌표 가정에 맞는지 원본 일본판 대비 감사해야 했다. 한글은 영문보다 원본 일본어 행 배치에 가까운 메트릭이 필요할 수 있다
- **UI 표시**: 가격·소지금 같은 숫자 루틴은 대사 텍스트 포인터가 아니라 고정 좌표 버퍼에 직접 쓰는 경로가 있어, 텍스트 레이아웃 변경과 함께 좌표 가정을 확인해야 했다. 돈 단위 같은 HUD 글자는 별도 그래픽 업로드 경로로 추적했다
- **텍스트**: 복수 포인터 테이블 구조. 접미사 공유 최적화를 보존(해제하면 텍스트가 부풀어 16KB 뱅크를 초과)하고, 미번역 엔트리 참조 바이트와 텍스트 뱅크 내 게임 데이터 구간을 보호하며 재배치
- **렌더 추적**: 일부 화면은 워크 RAM에서 조립된 뒤 변경 행만 VRAM으로 복사되는 구조라, VRAM 전송 루틴뿐 아니라 전송 원본 버퍼를 채우는 코드까지 역추적해야 했다
- **빌드**: 원본에서 시작하는 단방향 빌드가 폰트 생성 → Z80 패치 어셈블 → 다중 테이블 텍스트 삽입 → 체크섬 재계산을 한 번에 재현했다
- **검증**: Z80/VDP 상태 관측으로 경로를 확정하고, 메모리·브레이크포인트·입력·화면 증거를 반복 수집해 회귀를 자동 판정했다

이 사례가 남긴 교훈은 이렇다. 우선 선행 영문 패치가 확장 영역과 현대화된 텍스트 엔진을 이미 갖고 있다면 재사용 후보가 되지만, 베이스 선택은 작업량·배포성·권리 조건뿐 아니라 레이아웃 상속 비용까지 비교해 결정한다. 또 기존 엔진을 대체하기보다 **상태(카운터·세션 플래그)를 공유하는 병렬 경로**로 붙이면 패치 코드를 작게 유지할 수 있다. 끝으로 read-ahead처럼 엔진이 텍스트를 미리 읽는 구조에서는 새 인코딩 대역이 기존 경로에 새어 들어가는 지점을 가드로 차단해야 하며, 텍스트 엔진 밖 숫자/HUD 경로도 별도 검증 대상으로 둔다.
