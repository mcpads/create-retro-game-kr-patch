# 세가 새턴 (Sega Saturn) 한글 패치 참조

## 1. 플랫폼 개요

새턴(1994)은 다중 프로세서 아키텍처를 채택한 2D/3D 콘솔이다. 한글 패치 관점에서 핵심 프로세서는 다음과 같다.

| 프로세서 | 역할 | 클럭 |
|----------|------|------|
| Master SH-2 (SH7604) | 메인 CPU, 게임 로직 | 28.6363 MHz |
| Slave SH-2 (SH7604) | 보조 CPU, 병렬 처리 | 28.6363 MHz |
| SH-1 (SH7034) | CD-ROM 컨트롤러 | 20 MHz |
| MC68EC000 | 사운드 CPU (SCSP 제어) | 11.2896 MHz |
| SCU DSP | DMA/연산 보조 | 14.3182 MHz |

SH-2 분석 시 핵심 특성:

- **Big-endian**, 명령어 고정 16비트(2바이트)다. 모든 명령어가 2바이트 경계에 정렬된다.
- 즉시값 로드가 8비트로 제한되어 32비트 상수는 `MOV.L @(disp,PC), Rn`으로 코드 근처의 리터럴 풀에서 읽는다. 주소/상수를 패치할 때 리터럴 풀 위치를 반드시 확인한다. 참조 주소 계산: `(PC & 0xFFFFFFFC) + 4 + disp * 4`.
- `BRA`·`BSR`·`JMP`·`JSR`·`RTS`·`RTE`·`BT/S`·`BF/S`는 delay slot을 가진다(단순 `BT`/`BF`는 갖지 않는다. 레지스터 상대 `BRAF`/`BSRF`도 갖는다). 분기 직후 1개 명령어가 분기 전에 실행되므로 함수 호출 무효화 시 delay slot까지 함께 NOP(`0x0009`) 처리한다. delay slot에는 다른 분기·PC 상대 리터럴 풀 로드(`MOV.L @(disp,PC)`, `MOVA`)·`TRAPA`를 둘 수 없다(illegal slot 예외). delay slot을 재배치할 때 리터럴 풀 로드를 그 자리로 옮기지 않는다.
- 조건 분기 반전: `BT(0x89xx) ↔ BF(0x8Bxx)`, `BT/S(0x8Dxx) ↔ BF/S(0x8Fxx)`.
- 바이너리 분석기는 SH-2, Big-endian으로 설정하고, 베이스 주소는 IP.BIN의 1st Read Address나 실제 로더가 지정한 주소에서 가져온다. 구현 후보와 설정 예시는 `references/conventions/tooling.md`의 새턴 부록을 본다.

부팅 흐름: BIOS가 디스크 선두 16섹터의 IP.BIN을 `0x06002000`에 로드해 실행하고, IP.BIN이 헤더에 기록된 1st Read Address/Size에 따라 메인 실행 파일(1ST_READ.BIN 등)을 Work RAM High에 로드한다. 게임 코드 디스어셈블은 이 로드 주소를 기준으로 시작한다.

## 2. 메모리 계층

새턴은 CPU RAM / VDP1 / VDP2의 삼중 메모리 구조를 가지며, 텍스트 데이터는 이 계층을 단계적으로 거친다.

| 주소 범위 | 크기 | 영역 |
|-----------|------|------|
| `0x00200000` - `0x002FFFFF` | 1 MB | Work RAM Low — 저속 DRAM, CD 로딩 버퍼·데이터 테이블 용도 |
| `0x06000000` - `0x060FFFFF` | 1 MB | Work RAM High — SH-2 직접 버스, 게임 코드·스택·메인 데이터 |
| `0x05C00000` - `0x05C7FFFF` | 512 KB | VDP1 VRAM (스프라이트 텍스처 + 커맨드 테이블) |
| `0x05C80000` - `0x05CBFFFF` | 256 KB ×2 | VDP1 프레임버퍼 (더블 버퍼) |
| `0x05E00000` - `0x05E7FFFF` | 512 KB | VDP2 VRAM (128 KB 뱅크 A0/A1/B0/B1) |
| `0x05F00000` - `0x05F00FFF` | 4 KB | VDP2 CRAM (팔레트) |

- CD에서 로드된 실행 파일과 스크립트는 대부분 `0x06000000`대(Work RAM High)에 배치된다.
- 일부 게임은 스크립트 파일을 Work RAM Low(`0x0020xxxx`)에 로드하고, 파일 내부 포인터가 이 RAM 베이스 주소를 그대로 사용한다. 포인터 패턴 분석의 출발점이 된다(6절).
- VDP2 VRAM은 캐시 스루 주소 `0x25E00000`대로도 접근된다. 폰트 데이터 흐름의 전형: CD → 압축 해제 → Work RAM 버퍼 → CPU memcpy로 스테이징 버퍼 → VDP2 VRAM.

## 3. 비디오 시스템과 글리프 한계

### VDP1 / VDP2 역할 분담

- **VDP1**: 스프라이트·폴리곤. VRAM 내 32바이트 커맨드 테이블을 순차 실행한다. 텍스트를 Normal Sprite로 그리는 게임에서는 이 경로의 텍스처·커맨드 예산을 따로 계산한다.
- **VDP2**: 배경 스크롤 플레인. NBG0-NBG3(일반), RBG0/1(회전). 셀(타일) 기반이며 셀 크기는 8x8 또는 16x16, 색상 모드는 16색/256색 등.

대화 텍스트가 어느 하드웨어로 렌더링되는지는 엔진 조사 착수 전 1단계 게이트에서 확정한다. 레이어 토글로 Sprite/VDP1을 끌 때 텍스트가 사라지면 VDP1 스프라이트 경로이고, NBG/RBG 레이어를 끌 때 사라지면 VDP2 배경 경로다. 바이너리에 VDP1/VDP2 텍스트 경로가 모두 존재할 수 있으므로 실제 화면의 레이어 반응을 우선하고, 한 경로에서 얻은 예산·콜체인을 다른 경로에 일반화하지 않는다.

### 렌더 경로별 글리프 예산

글리프 예산은 렌더 경로에 종속된다. VDP2 NBG 텍스트는 PND character number 비트 수와 셀 크기가 1차 병목이지만, VDP1 스프라이트 텍스트는 VDP2 PND 상한을 쓰지 않는다. VDP1 경로의 병목은 VDP1 VRAM 안의 텍스처/커맨드 테이블 배치, 메시지별 적재 크기, 파일 컨테이너의 글리프 풀 크기다.

가능하면 디버거의 비디오 상태 관측 기능으로 다음 값을 먼저 확정한다.

- 텍스트가 VDP1인지 VDP2인지
- VDP2라면 NBG/RBG 번호, PND character number 유효 비트 수, 셀 바이트 수, plane/name-table base
- VDP1이라면 스프라이트 커맨드 테이블 위치, 텍스처 source address, 색 모드, 팔레트/CLUT 참조
- 화면 좌표 하나를 실제 타일/스프라이트 소스 주소로 역해결하고, 원본 VRAM/VDP 메모리 readback 값과 대조

### VDP2 PND character number 상한과 글리프 슬롯 산정법

VDP2 타일맵의 PND(Pattern Name Data)는 1워드 또는 2워드 형식을 쓰며, character number의 유효 비트 수는 PND 모드·색상 모드·보조 모드 설정에 따라 달라진다. 해당 설정과 writer의 마스크를 런타임에서 확인한 뒤 참조 가능한 타일 수를 계산한다. 16x16 글리프가 8x8 타일 4개를 쓰는 배치라면 예약된 비글리프 타일을 뺀 뒤 4로 나눈 값이 슬롯 상한이다.

일반식:

```
글리프 슬롯 = (2^(character number 비트 수) − 게임 예약 타일 수) ÷ 글리프당 타일 수
```

(`references/strategy/font-strategy.md` 3절의 "타일 인덱스 폭" 병목.) 예약 타일 수는 게임마다 다르므로 슬롯 수는 게임별로 재산정한다. 이 산정은 VDP2 1워드 PND 모드 기준이며, 2워드 PND 모드는 더 큰 character number를 지원하므로 비트 수 입력 자체가 달라진다. 폰트 파일을 해당 모드의 타일 상한을 넘게 확장하면 화면이 깨진다.

### VDP2 글리프 슬롯 운용 전략

PND character number 상한이 완성형 2,350자보다 작게 나오는 설정이라면 다음 전략을 조합한다.

1. **동적 수집 할당**: 번역 전체에서 실제 사용되는 한글만 수집(정렬된 집합)하여 슬롯에 할당한다. 수요가 슬롯 한계를 넘으면 번역 어휘를 조정해 미할당 0으로 맞춘다.
2. **보존 슬롯 분리**: 게임 UI 전용 픽셀아트(아이콘, 버튼 표기, 게이지 바, 음표 등)는 원본 비트맵을 보존하고 할당에서 제외한다.
3. **재렌더링 자리 유지**: 한국어에서도 쓰는 문자(숫자, 영문, 괄호, 기호)는 한글 폰트로 다시 렌더링하되 동일 타일 코드에 배치해 기존 스크립트 참조를 그대로 유지한다.
4. **슬롯 회수**: 일본어 전용 문자(가나, 한자, 장음 부호)와 미사용 와이드 문자 슬롯을 한글에 재할당한다.
5. **직접 매핑**: 와이드(16x8) 영역에 재렌더링한 문자는 16x16 슬롯을 따로 쓰지 않고 와이드 타일 코드를 직접 사용해 슬롯을 절약한다.
6. **투명 타일 주의**: all-zero 타일이라도 VDP2 배경 패턴이 투명 타일로 참조 중일 수 있다. 덮어쓰면 배경에 글리프가 노출되므로 참조 분석 없이 회수하지 않는다.

폰트 파일의 16x16 글리프는 보통 8x8 타일 4개(TL, TR, BL, BR)로 분해 저장된다. 4bpp 기준 타일당 32바이트, 글리프당 128바이트. 인터리브 배치(앞 절반 타일 = 상반부, 뒤 절반 = 하반부)를 쓰는 게임도 있으므로 블록 구조를 먼저 파악한다.

## 4. 텍스트 엔진 패턴

### 인코딩은 렌더 경로별로 갈린다

새턴 게임의 텍스트 인코딩은 하나로 수렴하지 않는다. 먼저 §3의 레이어 라우팅 게이트로 VDP1/VDP2 경로를 확정하고, 그 경로가 어떤 글리프 공급 모델을 쓰는지 분리한다.

- **VDP2 NBG + 마스터 폰트 파일**: 텍스트 코드가 VDP2 PND character number나 폰트 파일 타일 인덱스를 직접 참조한다. 2바이트 BE 코드, 16비트 제어코드, 압축 폰트 파일이 한 패밀리로 나타날 수 있다.
- **VDP1 스프라이트 + 파일 내장 글리프 풀**: 메시지/스크립트 파일 안에 텍스트 코드와 비압축 글리프 비트맵 풀이 함께 들어 있고, 코드 값은 파일 또는 메시지 스코프의 slot을 가리킨다. 이 경우 별도 마스터 폰트 파일·VDP2 PND 예산·압축 절차가 없을 수 있다.
- **1바이트 스코프 코드/재사용 코드**: 코드 값이 전역 문자 코드가 아니라 현재 메시지나 로드 컨텍스트 안의 glyph slot이다. 같은 코드가 다른 메시지에서 다른 글리프를 가리킬 수 있으므로, 전역 2바이트 타일 인덱스 디코더로 읽으면 값이 폰트 한계를 벗어나거나 의미가 맞지 않는다.

따라서 "2바이트 BE 타일 인덱스 직접참조"는 새턴 일반 규칙이 아니라 아래 VDP2 NBG 패턴 중 하나다.

### VDP2 NBG 패턴: 2바이트 BE 타일 인덱스 직접 참조

Shift-JIS가 아니라 폰트 파일 타일 인덱스를 2바이트 big-endian으로 직접 인코딩하는 게임이 있다. 코드 공간은 작은 셀, UI 그래픽, 와이드 문자, 2x2 타일 글리프, 제어 코드처럼 여러 구간으로 나뉠 수 있지만 경계값과 변환식은 타이틀별이다. writer와 폰트 배치를 함께 추적해 각 구간의 시작값·stride·예약 슬롯을 프로젝트 문서에 기록한다.

SH-2 코드에서 `SHLL8`/`OR`로 lead/trail 바이트를 결합해 16비트 타일 인덱스를 만드는 패턴이 단서가 된다. SJIS 스캐너가 일부만 복원하고 화면 글리프 순서와 맞지 않으면 타일 인덱스 디코더를 별도로 검증한다.

### VDP1 패턴: 파일 내장 글리프 풀

VDP1 스프라이트 텍스트 경로에서는 파일 하나가 텍스트 코드와 글리프 비트맵을 함께 담는 자기완결 컨테이너일 수 있다. 전형적인 구조는 다음과 같다.

```
[메시지/제어 스트림] [코드→slot 매핑 또는 slot 사용 순서] [비압축 글리프 비트맵 풀]
```

이 패턴의 특징:

- 글리프 배열은 파일 안에 비압축으로 들어 있고, 메시지 로드 시 VDP1 VRAM 텍스처 영역으로 복사된다.
- 텍스트 코드는 전역 문자 코드가 아니라 파일/메시지 스코프의 slot 번호일 수 있다.
- 같은 1바이트 코드가 다른 메시지에서 재사용될 수 있으므로, 정적 "첫 등장 순서" 스캔만으로 code→glyph 매핑을 확정할 수 없다.
- 글리프 수가 256을 넘거나, 코드 수와 글리프 수가 맞지 않으면 코드 재사용·다단계 매핑·페이지별 풀을 의심한다.
- 한글화는 별도 마스터 폰트 확장보다 파일 단위 글리프 풀 교체와 텍스트 스트림 재작성으로 풀릴 수 있다.

트레이스할 때는 범용 `memmove`/블록 복사 루프를 매핑 로직으로 오인하지 않는다. 그 루프는 이미 결정된 버퍼를 옮기는 sink일 가능성이 높다. 실제 code→slot 매핑은 메시지 로드 파서, glyph pool 구성 루틴, 또는 스프라이트 커맨드 생성 직전의 인덱스 계산에 있다. 후보 코드가 보이면 로드 직후 RAM 버퍼에서 텍스트 스트림, slot 배열, 글리프 비트맵이 어떤 순서로 만들어지는지 추적한다.

### VDP1 스프라이트 텍스트 플레이북

VDP1 텍스트로 확정되면 VDP2 PND writer가 아니라 VDP1 커맨드와 텍스처 주소를 본다.

1. 텍스트가 사라지는 Sprite/VDP1 레이어를 확정한다.
2. 해당 프레임의 VDP1 command table에서 대화 글리프 스프라이트 명령을 찾는다.
3. command의 texture source address, width/height, color mode, CLUT/palette 참조를 읽는다.
4. texture source address가 가리키는 VDP1 VRAM 바이트를 RAM/디스크의 어느 버퍼에서 복사했는지 역추적한다.
5. 글리프 pool이 파일 내장형이면 디코드→무수정 재인코드 라운드트립을 먼저 통과시킨 뒤 파일 단위로 pool과 텍스트 코드를 함께 교체한다(라운드트립 우선 원칙은 `references/strategy/text-extraction.md` §5).

VDP1 경로의 예산은 "VDP2 character number 몇 비트인가"가 아니라 한 메시지 또는 화면에서 동시에 필요한 sprite 텍스처 바이트와 VDP1 VRAM 배치다. 한글 글리프가 커져도 메시지별 pool을 다시 만들 수 있으면 PND 12비트 한계보다 훨씬 여유가 있을 수 있다.

### SEQ 스크립트 파일 구조

이하는 한 사례의 이벤트 스크립트 포맷(SEQ)이다. 자기기술 메타데이터가 없는 전형적인 실행 전용 포맷이다.

```
[스크립트 코드와 텍스트 포인터]
[제어 토큰을 포함한 텍스트 블록과 구조적 gap]
[이벤트/NPC/맵 데이터와 선택적 추가 포인터 뱅크]
```

- 자기기술형 텍스트 시작 필드가 없으면 포인터 타겟 역방향 스캔 + 제어코드 밀도 + 정렬 검증의 다층 휴리스틱으로 영역을 찾는다.
- 블록 사이 gap과 씬 포인터가 가리키는 위치는 타이틀별 문법이다. 크기나 바이트 패턴을 플랫폼 규칙으로 고정하지 않고 원본 여러 샘플과 파서 소비량으로 확정한다.
- 대사 스트림은 글리프 코드와 개행·대기·종료 토큰이 섞일 수 있으므로 제어 토큰의 파라미터 길이를 포함해 파싱한다.
- 코드 영역의 2바이트 필드값이 글리프 코드 범위와 광범위하게 겹쳐 거짓양성을 만든다. 제어코드도 와이드 문자도 없는 추출 엔트리는 강한 노이즈 후보로 분류하되, 자동 삭제 전에 화면 대조나 주변 구조로 한 번 더 확인한다.
- 일부 파일은 단일 구분자로 항목을 나열하는 이름 테이블을 코드/데이터 영역에 둔다. 길이 헤더가 없고 외부 참조가 확인되지 않은 경우 원본 길이에 맞춘 고정길이 교체가 후보지만, 구분자값과 패딩 코드는 프로젝트에서 확정한다.

### 제어 코드 디스패치

일부 엔진은 16비트 값을 경계값과 비교해 글리프 코드와 제어 코드를 나누고, 코드 하위 부분을 디스패치 테이블 인덱스로 사용한다. 정확한 경계값과 핸들러 수는 게임별로 다르므로 비교 명령, 테이블 참조, 각 핸들러의 스트림 포인터 증가량을 함께 추적한다.

같은 숫자 코드가 게임마다 종료·개행·렌더링 모드·화자·페이지 전환처럼 다른 의미와 파라미터 길이를 가질 수 있다. **제어 코드의 파라미터 개수를 정확히 파악하지 못하면 파서가 파라미터를 글리프로 오인한다.** trailing 제어 시퀀스가 종료 처리와 함께 소비된다면 패딩은 그 시퀀스 앞에 둔다. 일반 판정 절차는 `references/strategy/reinsertion.md` §6.3을 따른다.

### VDP2 NBG 텍스트 렌더링 콜체인

VDP2 NBG 경로에서 확인할 콜체인 구조:

```
Master Text Render Dispatcher        ← 텍스트 오브젝트 배열 순회
  → VDP2 Text Wrapper
    → VDP2 Text Engine (메인 루프)   ← 16비트 BE tile code 읽기, 제어코드/글리프 분기
      → VDP2 Pattern Name Writer    ← tile code를 VDP2 PNT에 기록
      → Bounds Check + Dispatch     ← VDP1 스프라이트 경로 (플래그 기반)
      → Control Code Dispatch Table ← 게임별 핸들러
```

Pattern Name Writer의 처리 단계:

1. 폰트 디스크립터 룩업: 텍스트 오브젝트의 폰트 셋 인덱스로 디스크립터에서 VRAM character base와 맵 베이스를 얻는다. 엔트리 크기와 필드 오프셋은 프로젝트에서 실측한다.
2. character number 계산: VRAM base를 PND 모드의 character 단위로 변환하고 tile code나 glyph index를 가산한다. 주소 보정과 shift 값은 셀 크기·색상 모드·writer 코드로 확정한다.
3. 화면 좌표 → PNT 주소: `(Y/8 * row_stride + X/8) * 2 + map_base`.
4. 렌더링 모드별 쓰기. 16x16 모드는 4개 PNT 엔트리를 쓴다:

```
TL = tile_code
TR = tile_code + horizontal_stride
BL = tile_code + vertical_stride
BR = tile_code + vertical_stride + horizontal_stride
```

모드(8x8 / 8x16 / 16x16)는 제어 코드가 사전에 플래그로 설정할 수 있다. 폰트 파일의 타일 배치와 writer가 사용하는 수평·수직 stride가 일치하면 기존 엔진을 재사용할 수 있지만, stride와 인터리브 방식은 VRAM readback으로 다시 확인한다.

## 5. 압축 — CNX v2 (Greedy LZ77)

폰트·스크립트 파일이 CNX v2(컴파일계 게임들이 공유하는 공통 포맷)로 압축된 사례가 확인됐다. 이 절만으로 재구현이 가능하도록 기술한다.

이 절은 CNX v2가 확인된 파일에만 적용한다. 새턴 텍스트가 항상 별도 압축 폰트 파일을 가진다는 뜻은 아니다. §4의 VDP1 파일 내장 글리프 풀처럼 메시지 컨테이너 안에 비압축 비트맵 배열이 들어 있으면, CNX 재압축 대신 파일 컨테이너 라운드트립과 글리프 pool 재작성 경로를 따른다.

### 컨테이너 헤더 (16바이트)

| 오프셋 | 크기 | 내용 |
|--------|------|------|
| 0 | 4 | 매직 `"CNX\x02"` (BE u32 `0x434E5802`) |
| 12 | 4 | 해제 후 크기 (big-endian u32) |

게임 디컴프레서는 압축 크기 필드를 읽지 않고 플래그 바이트 종결자에 의존한다. 압축 스트림은 오프셋 16부터 시작하며, 해제 루프는 출력 누계가 해제 크기에 도달할 때까지 반복된다.

### 스트림 구조

```
[플래그 바이트] [op0 데이터] [op1 데이터] [op2 데이터] [op3 데이터] [플래그 바이트] ...
```

- 플래그 바이트 1개가 2비트 모드 코드 4개를 담는다. 처리 순서는 하위 비트부터다: bits [1:0] → [3:2] → [5:4] → [7:6] (각 op 처리 후 우측 2비트 시프트).
- 플래그 바이트가 `0x00`이면 스트림 종료.

### 모드별 동작

**모드 0 (`00`) — 스킵/브레이크**

```
skip_count = src[0]            // 포인터 전진 없이 읽음
src += skip_count + 1          // skip_count 바이트 + 자기 자신을 건너뜀
내부 루프 강제 종료 (다음 플래그 바이트로)
```

스트리밍(부분 해제) 모드에서는 모드 0 발생 횟수를 카운터로 사용해 지정 횟수 도달 시 함수를 빠져나간다.

**모드 1 (`01`) — 단일 리터럴**: 소스에서 1바이트 읽어 출력에 쓴다.

**모드 2 (`10`) — LZ 매치**

```
pair     = (src[0] << 8) | src[1]      // 2바이트 big-endian
length   = (pair & 0x1F) + 4           // 4..35
distance = (pair >> 5) + 1             // 1..2048
source   = output_pos - distance
output_pos부터 length 바이트를 source에서 전방(byte-by-byte) 복사
```

전방 복사이므로 자기참조 매치(distance < length)는 앞 distance 바이트의 순환 반복을 생성한다. 압축기에서 매치 검증 시 `src[i % distance]`로 모델링한다.

**모드 3 (`11`) — 다중 리터럴**: 카운트 바이트 1개를 읽고, 그 수만큼 리터럴 바이트를 출력에 복사한다 (카운트 ≤ 0이면 스킵).

### 압축기 파라미터

| 요소 | 값 |
|------|-----|
| 알고리즘 | Greedy LZ77 |
| 최소 매치 길이 | 4 바이트 |
| 최대 매치 길이 | 35 바이트 (5비트 + 4) |
| 윈도우(매치 거리 상한) | 2,048 바이트 |
| 플래그 바이트 | 2비트 코드 ×4 |

### 함정: 거리 상한과 출력 위치

게임 디컴프레서는 링 버퍼를 쓰지 않고 출력 버퍼에서 직접 `output_pos - distance`를 읽는다. 따라서 압축기가 `distance > 현재까지 출력된 바이트 수`인 매치를 생성하면 게임은 출력 버퍼 앞쪽 미정의 메모리를 읽어 데이터가 깨진다. 0으로 초기화된 링 버퍼를 쓰는 자체 디컴프레서로는 라운드트립 테스트가 통과해 버려 이 버그가 은폐된다.

- **올바른 매치 탐색 범위**: `distance ∈ 1..=min(pos, 2048)`.
- 실측 영향: 선두가 0x00 4바이트 이상으로 시작하는 파일(스프라이트·배경 등)이 잘못된 압축기로 재압축 시 조용히 손상됐다.
- 검증은 자체 디컴프레서 라운드트립만으로 부족하며, 게임 디컴프레서의 동작(출력 버퍼 직접 참조)을 그대로 모사한 검증기가 필요하다.

## 6. 포인터 체계 — 다중 패턴 분류와 일괄 수정

번역으로 텍스트 길이가 바뀌면 후속 블록이 이동하지만 스크립트 코드의 포인터는 원래 오프셋을 유지해, 빈 텍스트 박스·소프트락이 발생한다. 포인터가 파일 유형마다 완전히 다른 규약으로 섞여 있으면 유형별 전용 스캐너로 나눠 처리한다. 한 규약의 스캐너로 전부 잡으려 하면 누락이 생긴다.

### 패턴 분류

한 게임 안에서도 포인터는 다음처럼 여러 문법으로 나타날 수 있다.

- 로드된 RAM 베이스와 파일 오프셋을 합친 절대 주소
- 명령 opcode·고정 서픽스가 포인터를 감싸는 이벤트 레코드
- 공용 데이터의 다단계 간접 테이블
- 제어 코드 파라미터 안에 들어간 주소
- 큰 파일에서 bank selector와 짧은 오프셋을 결합한 포인터

상위 비트가 로드 세그먼트, 하위 비트가 파일 오프셋이라는 가설은 RAM 적재 주소와 실제 타겟을 왕복해 확정한다. 파일 유형명, 프리픽스·서픽스 바이트, 뱅크 번호는 프로젝트 문서가 소유하며 유형별 전용 스캐너로 분리한다.

### 일괄 수정 알고리즘

1. **원본** 파일에서 유형별 포인터 필드 위치·타겟·표현 규약을 기록한다.
2. 각 패치의 `(offset, orig_len, new_len)`으로 원본→신규 오프셋 이동 맵을 계산한다.
3. 포인터 타겟과 포인터 필드 자체가 각각 이동했는지 계산한 뒤, 데이터 재배치가 끝난 신규 필드 위치에 값을 쓴다.
4. 포인터 폭·bank selector가 표현할 수 있는 범위를 넘으면 실패한다.
5. 컨테이너가 엔트리 정렬을 요구하면 실측한 정렬 단위로 패딩한다. 패딩 위치는 4절의 제어코드/종료자 분석과 `references/strategy/reinsertion.md` §6.3 기준으로 정한다.

패치 자체는 오프셋 역순 splice(뒤에서부터 적용)로 수행해 앞쪽 오프셋이 유효하게 유지되도록 한다.

### 거짓양성 방어

포인터 패턴은 짧아서 데이터 영역에서 우연히 출현한다(4바이트 패턴은 거짓양성이 실제 포인터보다 훨씬 많을 수 있다). 필수 방어책:

- **범위 검증**: 타겟이 파일 크기 이내인지.
- **정렬 검증**: 스크립트 포인터의 정렬을 확정한 뒤, 맞지 않는 타겟은 후보에서 배제한다. 좌표·색상·플래그 같은 짧은 데이터가 포인터 프리픽스와 우연히 겹칠 수 있다.
- **서픽스 검증**: 모호한 매치(뱅크 경계 넘는 경우 등)는 고정 서픽스 일치를 요구한다. 반대로 서픽스 블랙리스트 방식은 거짓음성(NPC 미표시)을 유발해 폐기됐다.

### 듀얼 뱅크 (64KB 초과 파일)

짧은 오프셋과 뱅크 선택자를 결합하는 형식에서는 표현 범위를 넘는 파일이 다음 뱅크 프리픽스를 쓸 수 있다. 텍스트 축소/확장으로 타겟이 뱅크 경계를 넘으면 오프셋뿐 아니라 selector도 함께 전환한다. selector 값과 뱅크 크기는 로더 계산식으로 확정한다.

## 7. 디스크 포맷 — ISO 9660, LBA 재배치, EDC/ECC

### BIN/CUE와 섹터 구조

새턴은 Mode 1 데이터 트랙 + CD-DA 오디오 트랙 구성이 일반적이다. BIN 파일은 raw 2352바이트 섹터의 연속이다. Mode 1 섹터 레이아웃(Sync/Header/User Data 2048B/EDC/Reserved/ECC의 오프셋·크기)은 `references/strategy/build-and-verify.md` §3 「CD 매체의 EDC/ECC」가 정본이다.

새턴 고유 LBA/트랙 변환:

```
BIN 오프셋(User Data 시작) = LBA * 2352 + 16
```

CUE의 `INDEX MM:SS:FF`는 `(MM*60+SS)*75+FF` 섹터다. 디스크 레이아웃: LBA 0-15 = IP.BIN(System Area, 32 KB), LBA 16 = ISO 9660 PVD(`"CD001"` 시그니처), LBA 18 이후 파일시스템과 데이터.

### ISO 9660 파일 접근

- PVD(LBA 16) 오프셋 `0x9C`의 Root Directory Record에서 루트 디렉토리 LBA/크기를 얻는다. 멀티바이트 정수는 both-endian(LE 4B + BE 4B) 기록.
- Directory Record: `+0x02` extent LBA(8B both-endian), `+0x0A` 데이터 크기(8B both-endian), `+0x19` 플래그(bit1 = 디렉토리), `+0x21` 파일명(`NAME.EXT;1` 형식).
- 각 파일은 연속 섹터(단일 extent)에 저장된다. 파일 읽기/쓰기는 섹터마다 User Data 2048바이트만 추출/기록한다.

### 파일 재배치 (LBA 갱신)

번역으로 압축 파일이 원본 섹터 할당을 초과하면 그 자리에서 늘릴 수 없다(다음 파일이 바로 이어짐). 해결 절차:

1. CD-DA 트랙 직전의 빈 영역에서 필요한 섹터 수만큼 새 LBA를 확보한다 (가용 여유는 디스크별로 실측한다).
2. 새 LBA에 파일 데이터를 기록한다.
3. ISO 9660 디렉토리 엔트리의 extent LBA와 크기를 both-endian으로 동시 갱신한다.
4. 게임이 자체 파일 크기 테이블을 가진 경우(메인 실행 파일 내 하드코딩) 그 테이블도 패치한다.

크기가 섹터 할당 내에서만 변하면 디렉토리 엔트리의 크기 필드만 갱신하면 된다.

### EDC/ECC 재계산

섹터 User Data를 수정하면 EDC/ECC가 무효화된다. EDC(CD 전용 CRC-32)·ECC(Reed-Solomon P/Q parity)의 오프셋·다항식·반전 상수·재계산 정확성 검증법, 그리고 의도적으로 틀린 EDC/ECC를 카피 프로텍션으로 쓰는 게임에서는 전 섹터 일괄 재계산 대신 변경 섹터만 재계산하고 원본의 의도적 오류 섹터를 보존한다는 규칙까지 `references/strategy/build-and-verify.md` §3 「CD 매체의 EDC/ECC」가 정본이다. 실행 환경의 검사 관대성에 기대지 말고 변경 섹터를 독립 검증한다.

## 8. 패치 포맷과 빌드

- 빌드 산출물은 패치된 BIN + CUE다. CUE는 원본과 트랙 레이아웃이 동일하므로 자동 생성한다.
- 배포는 **BPS 패치**로 한다. 원본 BIN → 패치 BIN의 diff를 빌드 완료 시 자동 생성한다. 새턴 디스크 이미지는 100 MB 이상이므로 이미지 자체 배포는 부적절하며, BPS는 원본 체크섬 검증을 내장해 잘못된 원본 적용을 차단한다.
- BIN이 트랙 전체(데이터 + CD-DA)를 담은 단일 파일인 경우 BPS도 그 단일 BIN 기준으로 만든다. 원본 덤프의 트랙 분할 방식(단일 BIN vs 트랙별 BIN)이 다르면 패치가 적용되지 않으므로, 대상 원본의 정확한 크기·체크섬을 명시한다.
- 빌드 파이프라인 예시: 번역 JSON 로드 → 사용 한글 수집·글리프 테이블 생성 → 폰트 파일 패치(압축 해제 → 글리프 교체 → 재압축) → 각 스크립트 패치(추출 → splice → 포인터 수정 → 재압축) → 디스크 기록(재배치 포함) → ISO 디렉토리 갱신 → EDC/ECC 재계산 → BPS 생성.

## 9. 검증 — 새턴 디버깅

검증 환경은 SH-2 실행 추적과 VDP1/VDP2 상태·VRAM readback을 제공해야 한다. 환경 채택·교정 규약은 `references/conventions/tooling.md` §1을 따른다.

- **레이어 토글**: 대화 텍스트의 렌더링 하드웨어(VDP1 스프라이트 vs VDP2 NBG 레이어)를 확정하는 가장 빠른 방법. 레이어를 하나씩 꺼서 텍스트가 사라지는 레이어를 찾는다. VDP2 PND character number 한계가 적용되는지 여부가 여기서 갈리므로 패치 설계 전에 반드시 확인한다.
- **비디오 상태 관측**: 가능하면 VDP2 plane base, cell size, PND character number 유효 비트 수, VDP1 command table, sprite texture address를 런타임에서 읽어 §3의 예산 입력으로 쓴다. 화면 좌표 하나를 타일/스프라이트 소스 주소로 역해결한 뒤, 해당 주소의 raw 값을 직접 읽어 계산 결과와 대조한다.
- **VDP2 readback 검증**: PNT 주소를 계산했다면 그 주소의 raw PND word를 읽고, 디코더가 계산한 팔레트/character number와 일치하는지 확인한다. 이 검증이 통과하기 전에는 수작업 PNT 공식이나 plane base 계산을 예산 산정의 근거로 쓰지 않는다.
- **VDP1 readback 검증**: VDP1 텍스트라면 command table의 texture source address와 width/height가 가리키는 VRAM 바이트를 읽고, 파일 내장 glyph pool 또는 로드 버퍼의 해당 글리프 바이트와 일치하는지 확인한다. 스프라이트 레이어가 사라진다는 사실만으로 글리프 공급 경로가 확정되는 것은 아니다.
- **VRAM dump 바이트 순서**: 세이브스테이트나 오프라인 덤프가 VDP VRAM 16비트 word를 어떤 바이트 순서로 저장하는지는 도구마다 다를 수 있다. 덤프 파서로 결론을 내리기 전에 같은 주소를 런타임 메모리 readback과 비교해 endian/word-swap을 확인한다.
- **회귀 격리 테스트**: 격리 빌드(ablation)로 원인 단계를 좁히는 방법론은 `references/strategy/debugging.md` §2가 정본이다. 새턴 적용 예 — 특정 SEQ만 패치·재압축만 수행 식으로 패치 단계를 나눠, 한 사례에서 CD 행(hang)의 원인이 포인터 누락임을 확정했다.
- **증상별 원인 패턴**:
  - 빈 텍스트 박스 → 포인터 미수정 (타겟이 이동한 블록).
  - 하드락 → 패딩이 제어코드 파라미터로 오인됨, 또는 거짓양성 포인터 수정으로 코드 손상.
  - 특정 콘텐츠(미니게임 등)만 오동작 → 해당 파일 유형의 포인터 패턴 누락.
  - 화면 깨짐 → 폰트 타일 수가 해당 PND 모드의 character number 상한을 넘었는지 확인(§3).
  - 재압축 파일만 깨짐 → 압축기 거리 상한 버그(5절).
- 실행 환경의 부팅 통과는 EDC/ECC 증거가 아니다. 변경 섹터의 계산값과 보존해야 할 의도적 오류를 독립 검사한다.

### 실기 구동 경로

실광학 매체와 적법한 부트·인증 경로 또는 이미지 로더 중 프로젝트가 실제로 지원할 대상을 정한다. 리전 처리와 디스크 인증은 별도 계층이므로 각각의 적용 위치와 원본 보존 범위를 기록한다. 기계적 스왑처럼 장치를 손상시킬 수 있는 방식은 검증 절차로 두지 않는다.

대상 경로는 원본의 데이터/CDDA 트랙 분할, Mode 1 raw 섹터, INDEX/pregap, 리전·보호 처리와 필요한 확장 카트리지의 공존을 지원해야 한다. 단일 병합 파일이나 별도 장치용 컨테이너가 필요하면 원본 트랙 정본에서 변환하고, LBA·트랙 시작·CDDA 재생을 다시 검증한다.

**빌드 포맷에의 영향**: 패치 정본은 원본 BIN/CUE의 트랙 배치를 보존한다. 데이터 트랙의 변경 섹터는 EDC/ECC를 재계산하고, 장치별 병합·분할·리전 변환은 정본 뒤의 별도 산출물로 둔다. 로더 호환 실패와 패치 데이터 결함을 구분할 수 있도록 변환 전후 해시와 트랙 메타데이터를 남긴다.

중간 환경은 CPU·VDP뿐 아니라 이번 변경이 닿는 CD·카트리지 경로를 구현한 범위에서만 증거가 된다. 배포 대상 매체의 동작을 대신하지 않으며, 검증 티어 운용은 `references/strategy/build-and-verify.md` §4를 따른다.

## 10. 사례 요약

### 새턴 마도물어

- 텍스트: 여러 SEQ가 2바이트 BE 타일 인덱스를 사용했고, 레이어 토글로 VDP2 NBG 경로임을 확정했다. NBG 번호와 코드 경계는 프로젝트 좌표로 남긴다.
- 폰트: CNX v2 압축 폰트를 확장하되 실제 PND character number 상한을 먼저 측정하고, 예약 영역 회수와 직접 매핑을 조합해 수요를 흡수했다.
- 포인터: 이벤트 레코드·간접 테이블·제어코드 인자처럼 서로 다른 포인터 문법을 유형별 스캐너로 나눴다. 짧은 오프셋이 뱅크 경계를 넘으면 selector도 함께 전환했다.
- 빌드: 성장한 파일을 검증된 빈 영역으로 재배치하고 ISO 9660 메타데이터와 변경 섹터 무결성을 함께 갱신했다.
- 검증: 레이어 토글과 런타임 메모리 관측으로 검증.

### 새턴 와쿠와쿠 뿌요뿌요 던전

- 폰트: 기존 PND 타일 예산에 근접해 파일 확장보다 존(Zone) 재활용을 택했다. 슬롯을 보존/재렌더링/회수로 분류하고 일부 와이드 영역을 16x16 인터리브로 전환했다.
- 렌더링: Master Dispatcher → VDP2 Text Engine → Pattern Name Writer 콜체인을 확정하고, writer에서 실측한 수평·수직 stride에 맞춰 타일을 배치해 엔진을 재사용했다.
- 부수 효과 처리: 폰트 타일을 배경 타일맵·블록 그래픽으로 재사용하는 스크립트를 함께 패치(회수된 타일 참조를 공백 타일로 교체). 폰트 타일이 텍스트 외 용도로 참조될 수 있음을 보여주는 사례.
- 검증: 레이어 토글과 런타임 메모리 관측으로 검증.

### VDP1 스프라이트 텍스트 계열

- 라우팅: 대화 텍스트가 VDP2 NBG가 아니라 VDP1 스프라이트 레이어에서 사라지는 사례가 있다. 이 경우 PND character number 상한, VDP2 Pattern Name Writer, NBG plane base 계산은 본문 텍스트에 적용되지 않는다.
- 컨테이너: 메시지 파일 안에 텍스트 코드와 비압축 글리프 비트맵 풀이 함께 들어 있는 자기완결 구조가 가능하다. 별도 마스터 폰트 파일이나 CNX 압축을 전제로 삼지 않는다.
- 인코딩: 1바이트 코드가 전역 타일 인덱스가 아니라 파일/메시지 스코프의 glyph slot일 수 있고, 코드 재사용 때문에 정적 첫등장 스캔만으로 code→glyph 매핑이 확정되지 않을 수 있다.
- 분석: 범용 복사 루프보다 메시지 로드 파서와 스프라이트 커맨드 생성 직전의 인덱스 계산을 추적한다. 글리프 예산은 VDP1 VRAM과 메시지별 pool 크기에서 산정한다.
